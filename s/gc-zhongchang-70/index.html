1.实现一个函数，输入是一组合法的 Linux cd 命令字符串数组，模拟执行后返回最终 pwd 路径。

我用栈来模拟目录切换：遇到’..‘就弹出栈顶，遇到普通目录就压入，遇到’/‘就清空栈；最后拼接路径时注意根目录开头和斜杠分隔。特别处理连续斜杠、单点’.‘这些合法但无影响的情况。

回答要点
  1. 正确处理 '..' 回退到父目录
  2. 正确处理绝对路径 '/' 清空当前路径
  3. 忽略 '.' 和多余 '/'
  4. 最终路径以 '/' 开头且无结尾斜杠
完整解析（含追问与踩坑）→
2.如何实现浏览器的前进后退功能？

我用两个栈：后退栈存已访问页，前进栈存后退时弹出的页。每次跳转，把当前页压入后退栈，清空前进栈；点击后退，从后退栈弹出压入前进栈；前进则反向操作。关键要保证前进栈只在后退时更新，避免状态错乱。

回答要点
  1. 后退栈和前进栈严格隔离，互不交叉更新
  2. 新导航必清空前进栈
  3. 支持多次后退后仍能前进
  4. 时间复杂度 O(1) 每次操作
完整解析（含追问与踩坑）→
3.HTTP 和 HTTPS 有什么区别？
回答要点
  1. HTTPS = HTTP + TLS，默认 443 端口
  2. HTTP 明文传输，HTTPS 加密，防窃听、防篡改、防冒充
  3. HTTPS 通过证书链验证服务端身份，HTTP 没有身份验证
  4. 代价：握手增加 RTT，有加解密开销，需要证书维护
完整解析（含追问与踩坑）→
4.非对称加密和对称加密分别用在 TLS 握手的哪个环节？它们如何配合？

非对称加密只用在握手初期：客户端用服务器公钥加密预主密钥传过去；服务器用私钥解密。之后所有通信都用这个预主密钥派生的对称密钥加密——因为对称加密快，适合大量数据。

回答要点
  1. 非对称加密仅用于安全传递预主密钥
  2. 对称密钥由预主密钥+随机数通过 PRF 派生
  3. 后续全部应用层数据用对称密钥加密
  4. 明确区分两种加密的性能与用途差异
完整解析（含追问与踩坑）→
5.TLS 握手过程中，对称加密的密钥是如何安全确定的？

客户端和服务器各自生成随机数，加上协商好的预主密钥，一起输入 TLS 的伪随机函数 PRF，输出主密钥；再用主密钥和双方随机数派生出实际的对称密钥、MAC 密钥等。全程没有密钥明文传输。

回答要点
  1. 密钥由预主密钥+client_random+server_random 共同派生
  2. 使用标准 PRF（如 SHA256）确保不可逆
  3. 主密钥不直接用于加密，而是二次派生会话密钥
  4. 强调随机数防止重放攻击

6.有一台内存极小的 Linux 服务器，A、B 两文件各含 5000 万个 UUID 字符串，求交集并输出到文件 C，内存不足以加载任一文件，如何设计？

我用哈希分片：对每个 UUID 取模 1000，把 A、B 分别拆成 1000 个小文件；然后逐对读取同编号的 A_i 和 B_i，用哈希集合求交写入 C。内存只存一个分片，峰值约 5 万条 UUID，完全可控。

回答要点
  1. 必须用哈希分片规避内存限制
  2. 分片数需使单分片可载入内存
  3. 同模分片配对处理保证交集不遗漏
  4. 输出去重且不重复写入
完整解析（含追问与踩坑）→
7.假设有万人级别的学生选课，在开课前需要发送上课提醒，粒度是分钟级别的，如何实现？

我会用 Redis ZSet 做时间索引，score 存 Unix 时间戳，value 存学生ID和课程ID；后台用多个 worker 每秒轮询当前时间点及之前的任务，拉取后批量投递到 Kafka；每分钟建一个 ZSet 分桶防热点；所有任务落库持久化，消费端幂等+失败重试三次，超时未确认则补偿。

回答要点
  1. 使用有序数据结构（如ZSet）支持按时间范围高效扫描
  2. 通过分桶（如每分钟一个key）避免单ZSet过大和竞争
  3. 任务持久化+消息队列解耦+消费幂等+重试机制保障可靠性
完整解析（含追问与踩坑）→

9.你们登录系统这一块是怎么做的？

我们用 JWT 方案：用户输账号密码，服务端校验后签发含 userId 和过期时间的 token；前端存 localStorage，每次请求带在 Authorization 头；服务端用公钥验签并解析。密码用 BCrypt 加盐哈希存储，登录失败 5 次锁定账户。

回答要点
  1. 明确 token 签发、传输、校验全流程
  2. 密码必须加盐哈希存储（非明文/简单 hash）
  3. 有防暴力破解措施（如限流、锁定）
  4. token 包含合理有效期且支持主动失效（如黑名单）
完整解析（含追问与踩坑）→
10.发奖这一块是怎么做的？

我们走最终一致性：下单成功发 MQ 消息到发奖服务，它用本地事务表记录发奖状态，成功后更新 DB 并调第三方接口；失败则重试，超过阈值进死信队列人工介入。所有发奖操作带唯一业务 ID 防重。

回答要点
  1. 必须有本地事务表或消息表保障可靠投递
  2. 调第三方接口必须带幂等 key
  3. 失败有分级重试策略（立即/延迟/人工）
  4. 发奖结果需回写主订单表供查询
