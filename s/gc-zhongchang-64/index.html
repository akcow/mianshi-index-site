1.如何设计 Agent/LLM 聊天的断点续传？大模型流式传输如何借鉴 TCP 机制保证可靠性与有序性？

我会用会话 ID + 消息序号 + 服务端快照存储实现断点续传；流式传输借鉴 TCP 的序列号、ACK 确认和重传机制，在客户端缓存未确认 chunk，服务端按序生成并标记 offset，配合超时重发和去重逻辑保障有序可靠。

回答要点
  1. 明确会话状态需持久化（ID+last_offset+context_snapshot）
  2. 流式 chunk 需带唯一序号和校验码
  3. 客户端实现滑动窗口缓存与重传，服务端支持按序重发与幂等响应

2.TCP 为什么要四次挥手？如果省略第四次挥手，会有什么问题？

四次挥手因 TCP 全双工，双方需独立关闭发送方向。第一次 FIN 关 A→B 发送，第二次 ACK 确认，第三次 FIN 关 B→A 发送，第四次 ACK 确认。若省略第四次，B 不知 A 是否收到 FIN，可能重发 FIN，导致 A 无法进入 CLOSED，B 卡在 LAST_ACK，连接异常残留。

回答要点
  1. 说明全双工导致需双方独立关闭发送通道
  2. 准确描述四次交互中每次的发起方和含义
  3. 指出省略第四次会导致 B 卡在 LAST_ACK、A 无法释放资源
完整解析（含追问与踩坑）→
3.拥塞控制讲一下？

拥塞控制核心是通过cwnd动态调节发送速率。慢启动阶段cwnd指数增长，直到达到ssthresh；之后进入拥塞避免，cwnd线性增长；一旦收到3个重复ACK，触发快速重传并进入快速恢复，将ssthresh设为当前cwnd一半，cwnd设为ssthresh+3个MSS，再逐步恢复。关键是它始终在试探网络承载上限，和流量控制互不替代。

回答要点
  1. 准确描述慢启动、拥塞避免、快速重传/恢复三阶段行为
  2. 说明ssthresh的更新规则
  3. 强调cwnd与ssthresh的数值关系
  4. 点明与流量控制的本质区别
完整解析（含追问与踩坑）→
4.HTTPS 与 HTTP 有什么区别？TLS 加密流程是怎样的？

HTTPS = HTTP + TLS，核心区别是加密和身份认证；TLS 握手分四步：ClientHello（支持的密码套件）、ServerHello（选定套件+证书）、ClientKeyExchange（用公钥加密预主密钥）、Finished（用会话密钥验证完整性），之后所有 HTTP 报文都用对称密钥加密。

回答要点
  1. 明确证书由 CA 签发，用于验证 server 身份
  2. 指出 pre-master secret 由 client 生成并用 server 公钥加密传输
  3. 强调 Finished 消息是第一个用协商密钥加密的报文，用于双向认证
完整解析（含追问与踩坑）→
5.协程与线程的区别是什么？适用的场景分别是什么？

协程是用户态轻量级线程，由 runtime 调度，切换开销微秒级，适合高并发 I/O 密集场景；线程是内核调度实体，切换需陷入内核，开销毫秒级，适合 CPU 密集或需系统资源直访的场景。Go 的 goroutine 和 Python asyncio 都是典型协程实现。

回答要点
  1. 明确协程无内核态切换、无锁竞争、内存占用小（KB 级）
  2. 指出线程有独立栈和寄存器上下文，可并行执行 CPU 任务
  3. 举例说明：Web 服务用协程处理万级连接，音视频转码用线程池跑 FFmpeg
完整解析（含追问与踩坑）→
6.协程可以无限制创建吗？如何控制？

不能无限制创建，协程虽轻量但仍消耗栈内存和调度器元数据；实践中用协程池控制上限，比如 Go 的 worker pool 模式或 Python 的 asyncio.Semaphore 限流，同时结合背压机制，当队列积压时拒绝新任务或降级响应。

回答要点
  1. 指出单协程默认栈大小（如 Go 2KB）乘以百万级数量仍会 OOM
  2. 说明协程池需支持动态伸缩（如基于队列水位）而非固定大小
  3. 强调背压策略：拒绝、降级、熔断三选一，不能只靠等待
完整解析（含追问与踩坑）→
7.在一个协程中调用一个同步阻塞的接口会发生什么？

会阻塞当前协程所在的 OS 线程，导致该线程上所有其他协程暂停调度，严重降低并发吞吐；正确做法是用线程池异步执行阻塞调用，再通过 channel 或 Future 将结果交还协程，比如 Go 的 go func() + channel，或 Python 的 loop.run_in_executor。

回答要点
  1. 明确阻塞系统调用会让 M（OS 线程）卡住，P 无法调度其他 G
  2. 指出必须将阻塞操作移出协程调度路径，交由专用线程处理
  3. 给出具体迁移方式：如 Java 的 CompletableFuture.supplyAsync 或 Rust 的 spawn_blocking
完整解析（含追问与踩坑）→
8.操作系统的进程有哪些状态？具体的英文词

五种基本状态：New（新建）、Ready（就绪）、Running（运行）、Blocked/Waiting（阻塞/等待）、Terminated（终止）；其中 Ready 和 Running 是可执行态，Blocked 指因 I/O 或信号量等待而无法继续执行。

回答要点
  1. 准确列出全部五个状态英文名（含 Blocked/Waiting 两种常用写法）
  2. 说明 Ready 表示已就绪待 CPU，Running 表示正在占用 CPU 执行
  3. 指出 Blocked 状态下进程不参与 CPU 竞争，直到事件完成被唤醒
完整解析（含追问与踩坑）→
9.算法题：最长有效括号

我用栈存左括号索引，遍历字符串：遇 ‘(’ 入栈；遇 ‘)’ 时若栈空则更新 left bound，否则弹栈并算当前长度；最后取最大值。关键点是栈底始终存上一个未匹配 ‘)’ 的位置，保证每次计算都基于有效起点。

回答要点
  1. 栈初始化 push -1 作为基准左边界
  2. 遇到 ')' 且栈非空时，pop 后用 i - stack.peek() 更新最大长度
  3. 遇到 ')' 且栈空时，push i 作为新的左边界

10.Redis持久化机制有哪些？RDB和AOF如何选择？

RDB是快照，适合备份和灾难恢复，但会丢最后一次快照后的数据；AOF是命令日志，通过append-only和重写保证数据安全，但文件大、恢复慢。线上一般两者共存：RDB做冷备，AOF开everysec策略保数据；若追求强一致，可AOF+fsync always，但影响性能。

回答要点
  1. 准确说出RDB触发条件（save/bgsave/主从全量同步）
  2. 指出AOF重写机制（fork子进程生成新日志，不阻塞主进程）
  3. 能根据业务场景推荐组合策略（如秒杀用RDB+AOF everysec）
完整解析（含追问与踩坑）→
11.分布式系统有哪些了解？了解 Raft 共识算法及数据一致性算法。

Raft 将共识拆解为领导选举、日志复制、安全性三部分：节点分 Follower/Candidate/Leader，心跳超时触发选举，Leader 接收客户端请求并同步日志给多数节点后提交；它保证强一致性，通过任期号和日志匹配规则防止脑裂和日志回滚。

回答要点
  1. 准确说出 Leader 必须获得集群多数节点投票才能当选
  2. 指出日志提交需满足‘已复制到多数节点’且‘自身已提交’两个条件
  3. 强调安全性约束：Leader 完整性（Leader 一定包含所有已提交日志）和状态机安全性（同一任期同一 index 只能提交一条日志）

12.大模型如何实现结构化输出？

我分三层：模型层用 JSON mode 微调或内置结构化能力；提示层强制 schema 描述 + 示例 + ‘只输出 JSON 不加解释’指令；代码层用 Pydantic 解析 + 异常捕获 + fallback 重试，比如解析失败时补全字段或调用函数校验，确保下游能稳定消费。

回答要点
  1. 必须包含模型能力、提示约束、后置校验三个层次
  2. 指出 JSON mode 并非所有模型原生支持，需确认 provider 文档
  3. fallback 策略需明确：是重试、降级为文本、还是调用确定性函数兜底
