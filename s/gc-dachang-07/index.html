1.搜索旋转排序数组

先判断哪半边有序，再根据target是否落在有序区间决定搜索方向；关键点是每次都能排除一半，时间复杂度O(log n)，要特别注意mid和左右边界相等时的收缩逻辑。

回答要点
  1. 能准确划分有序/无序区间
  2. target在有序侧时直接二分，否则进无序侧递归
  3. 正确处理重复元素或边界重合情况

2.设计数据库表时，给定简单业务场景和几个字段，如何选择数据结构？

比如用户年龄用TINYINT而非INT，避免空间浪费；手机号用VARCHAR(11)加校验，不用BIGINT；状态字段优先用TINYINT枚举，不用VARCHAR存字符串；关键要看是否参与索引、排序、范围查询。

回答要点
  1. 区分固定长/变长场景选CHAR/VARCHAR
  2. 数值类按范围选TINYINT/SMALLINT/INT
  3. 明确是否为空、有无默认值、是否建索引
完整解析（含追问与踩坑）→
3.varchar和char的区别

CHAR是定长，不足补空格，检索快但浪费空间；VARCHAR是变长，存实际长度+1或2字节长度头，节省空间但可能触发行溢出；CHAR适合短且等长字段如性别、国家码，VARCHAR适合长度差异大的如用户名、地址。

回答要点
  1. 存储方式差异（定长vs变长）
  2. 空间开销对比（含长度头）
  3. 适用场景举例（等长/不等长）
完整解析（含追问与踩坑）→
4.联合索引怎么判断是否命中？`(A, B, C)` 跳过 `B` 用 `A` 和 `C` 会怎样？

联合索引(A,B,C)遵循最左前缀：A或A,B或A,B,C能高效命中；但A,C只能用A做索引查找，C无法走B+树。不过MySQL 5.6+有索引下推（ICP），引擎层会在索引扫描时提前用C过滤，大幅减少回表次数。

回答要点
  1. 准确描述最左前缀原则失效场景（跳过中间列）
  2. 指出`A,C`仍能利用`A`进行范围查找
  3. 必须提及ICP对`C`条件的优化作用（非‘完全不用’）
完整解析（含追问与踩坑）→
5.MySQL 索引的底层原理是什么，它解决了什么问题？

先开slow_query_log，设long_query_time阈值；用mysqldumpslow或pt-query-digest分析日志找TOP SQL；再explain看执行计划，重点看type、rows、key、Extra；最后结合索引、SQL写法、数据量做针对性优化，比如加索引、改JOIN顺序、拆分大事务。

回答要点
  1. InnoDB 用 B+ 树：非叶子节点只存键，叶子节点存数据且用链表相连
  2. B+ 树矮胖，三层能存千万级数据，把随机 IO 压到 2-3 次
  3. 相比全表扫描 O(n)，索引把查找降到 O(log n)
  4. 叶子链表支持范围查询和排序，这是 B+ 树相对 B 树的关键优势
完整解析（含追问与踩坑）→
6.GMP 模型。

G 是 goroutine，M 是 OS 线程，P 是调度器上下文。M 必须绑定 P 才能执行 G；P 维护本地运行队列，也会从全局队列或其它 P 偷任务；网络 I/O 由 netpoller 异步唤醒，系统调用阻塞时 P 会转交给空闲 M，避免线程闲置。

回答要点
  1. 清晰定义 G/M/P 三者角色及关系
  2. 说明 P 如何协调本地队列、全局队列和 work-stealing
  3. 指出 netpoller 和系统调用阻塞对 M/P 绑定的影响
完整解析（含追问与踩坑）→
7.遇到并发情况怎么加锁？

读多写少用RWMutex，避免写饥饿；简单计数用sync/atomic；需等待条件用Cond；跨goroutine通知用channel更Go风格；避免锁粒度过大，优先用局部变量或不可变对象；记得defer unlock防panic死锁。

回答要点
  1. 区分Mutex/RWMutex/atomic/channel适用场景
  2. 锁的生命周期管理（尤其panic时）
  3. 避免死锁的典型模式（如按序加锁）
完整解析（含追问与踩坑）→
8.分布式场景下怎么加锁？加锁命令是什么？

Redis用SET key value EX seconds NX实现，必须原子性；要加唯一client_id防误删；超时时间得大于业务执行时间；ZooKeeper靠临时有序节点；Etcd用CompareAndSwap；关键不是命令本身，而是如何保证锁的互斥、防死锁、可重入和容错恢复。

回答要点
  1. Redis SETNX+EX原子性保障
  2. 锁释放时校验value防误删
  3. 设置合理超时并配合续约机制

9.为什么延迟队列可以用zset来做？

zset按score排序，把任务执行时间戳作为score，成员存job内容；用ZRANGEBYSCORE取score≤当前时间的任务，再用ZREM原子删除已消费任务；天然支持按时间排序、去重、范围查询，比list+定时轮询更精准高效。

回答要点
  1. score代表到期时间戳
  2. ZRANGEBYSCORE + ZREM组合保证原子消费
  3. 支持多消费者通过WATCH或Lua脚本防重复取
完整解析（含追问与踩坑）→
10.zset的底层数据结构是什么样的？

zset同时用跳表（skiplist）和哈希表（dict）实现：跳表提供O(logN)范围查询和排序，哈希表提供O(1)按member查score；两者数据冗余但各司其职；小集合（≤128个元素且每个member≤64字节）用压缩列表ziplist优化内存。

回答要点
  1. 双结构共存目的（查score快 vs 查member快）
  2. 跳表层级随机生成与查询路径
  3. ziplist何时升级为skiplist/dict

11.输入一个URL到网页加载之间发生了什么？

先DNS解析域名得IP；再TCP三次握手建连；然后TLS握手加密；接着HTTP发GET请求；服务器返回HTML，浏览器解析构建DOM树，下载CSS/JS，执行渲染流水线：样式计算、布局、绘制、合成；过程中可能触发重定向、缓存协商、预加载等优化。

回答要点
  1. DNS→TCP→TLS→HTTP四层递进
  2. 浏览器解析HTML时的阻塞与异步行为
  3. 关键渲染路径中layout/paint/composite分工

12.TCP为什么要三次握手，而不是两次？

两次握手无法防止旧SYN报文在网络中滞留后突然到达服务端，导致服务端误建连接并浪费资源；三次握手让客户端确认服务端收到了自己的SYN，也确认了服务端的SYN，双方都确保对方收发能力正常，且能同步初始序列号。

回答要点
  1. 解决‘已失效的连接请求’问题
  2. 双向确认收发能力
  3. 同步ISN（初始序列号）防数据混淆
