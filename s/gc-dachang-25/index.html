这一场问了什么

1.请介绍 MySQL、ClickHouse、StarRocks 等数据库。

MySQL是面向事务的OLTP数据库，强一致性、支持ACID；ClickHouse是列式OLAP引擎，高压缩、快聚合但不支持事务；StarRocks也是MPP架构OLAP系统，兼容MySQL协议、支持实时更新和物化视图，比ClickHouse更易用且支持部分更新。

回答要点
  1. 明确区分OLTP与OLAP根本目标
  2. 指出MySQL的事务/行存特性
  3. 说明ClickHouse的列存/无事务/高吞吐特点
  4. 点出StarRocks的实时更新和MySQL协议兼容性
完整解析（含追问与踩坑）→
2.MySQL、PostgreSQL 以及上述 OLAP 数据库如何设计主从一致性？发生故障后如何恢复？

MySQL主从靠binlog异步/半同步复制，一致性靠GTID+延迟监控；PostgreSQL用WAL流复制，可配同步备库；ClickHouse无原生主从，靠ReplicatedMergeTree+ZooKeeper协调；StarRocks用FE/BEBE架构，元数据强一致，BE数据最终一致。故障时MySQL切主+重放binlog，StarRocks自动Failover。

回答要点
  1. MySQL需说明binlog类型与同步模式选择影响
  2. PostgreSQL要提WAL和synchronous_commit配置
  3. ClickHouse必须强调Replicated表引擎依赖ZK
  4. StarRocks需区分FE元数据强一致与BE数据最终一致
完整解析（含追问与踩坑）→
3.当前业务主要采用 MySQL 集群部署，谈谈你的设计思路。

我会分层设计：读写分离用ProxySQL或ShardingSphere做路由；分库分表按用户ID或订单时间哈希，避免热点；用MHA或Orchestrator做高可用；冷热分离，历史订单归档到ClickHouse；所有变更走灰度发布+全链路压测，重点防慢SQL打垮主库。

回答要点
  1. 明确读写分离中间件选型依据
  2. 给出分片键选择逻辑（非随意ID）
  3. 提及高可用切换工具而非仅'主从'二字
  4. 包含冷热分离与发布防护等生产级细节
完整解析（含追问与踩坑）→
4.是否有慢查询分析经验？通常如何定位和优化？

先看slow_log阈值和long_query_time设置；用pt-query-digest聚合分析TOP SQL；对单条查，explain看type/rows/key_len，确认是否走了索引；优化优先加复合索引，其次改写SQL避免函数操作字段，必要时加缓存或异步化。上线前必须explain验证执行计划。

回答要点
  1. 提到pt-query-digest等实际工具
  2. explain必须检查type和rows而非只看key
  3. 索引优化强调'复合索引最左匹配'原则
  4. 明确'上线前explain验证'这一落地动作
完整解析（含追问与踩坑）→
5.GMP 模型。

G 是 goroutine，M 是 OS 线程，P 是调度器上下文。M 必须绑定 P 才能执行 G；P 维护本地运行队列，也会从全局队列或其它 P 偷任务；网络 I/O 由 netpoller 异步唤醒，系统调用阻塞时 P 会转交给空闲 M，避免线程闲置。

回答要点
  1. 清晰定义 G/M/P 三者角色及关系
  2. 说明 P 如何协调本地队列、全局队列和 work-stealing
  3. 指出 netpoller 和系统调用阻塞对 M/P 绑定的影响
完整解析（含追问与踩坑）→
6.介绍一个最熟悉的项目。项目中遇到的最困难问题是什么，如何解决？如果问题进一步升级，会如何处理？

我做过一个订单导出服务，难点是大数据量导出OOM。先用游标分页+流式写文件解决内存溢出；升级后发现DB压力大，就加Redis缓存分页结果；再升级为Flink实时导出+Kafka分流，彻底解耦。每次升级都基于监控指标（内存、QPS、延迟）决策，不是盲目重构。

回答要点
  1. 问题描述具象（如'OOM'而非'性能差'）
  2. 每阶段解决方案对应具体技术手段
  3. 升级动因来自可观测指标而非主观判断
  4. 体现解耦、缓存、流式等分层治理思想
完整解析（含追问与踩坑）→
