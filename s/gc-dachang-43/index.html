1.errgroup 和 waitgroup 的区别是什么？

WaitGroup 只负责协程生命周期同步，不处理错误；errgroup 是 WaitGroup 的增强版，能自动收集首个 panic 或 error 并取消其余协程，底层用 errChan + context.WithCancel 实现错误传播。

回答要点
  1. 明确指出 WaitGroup 无错误传递能力
  2. 说明 errgroup 自动 cancel 其他 goroutine 的行为
  3. 点出 errgroup 基于 context 实现错误广播

2.GMP 模型。

G 是 goroutine，M 是 OS 线程，P 是调度器上下文。M 必须绑定 P 才能执行 G；P 维护本地运行队列，也会从全局队列或其它 P 偷任务；网络 I/O 由 netpoller 异步唤醒，系统调用阻塞时 P 会转交给空闲 M，避免线程闲置。

回答要点
  1. 清晰定义 G/M/P 三者角色及关系
  2. 说明 P 如何协调本地队列、全局队列和 work-stealing
  3. 指出 netpoller 和系统调用阻塞对 M/P 绑定的影响
完整解析（含追问与踩坑）→
3.什么是策略模式？

策略模式定义了一组算法，把每个算法封装成类，让它们可以互相替换；核心是用接口统一行为，运行时动态切换具体实现，比如支付方式选微信还是支付宝，都实现 PayStrategy 接口。

回答要点
  1. 点明‘封装算法族’和‘可互相替换’
  2. 强调接口/抽象类统一行为契约
  3. 举出符合定义的业务例子（如支付、排序）
完整解析（含追问与踩坑）→
4.你的服务瓶颈应该在哪里，怎么判断和扩容？

先看监控：CPU 高查计算热点，内存高看泄漏或缓存膨胀，RT 长查 DB 慢查或锁竞争，QPS 瓶颈看网关限流或连接池耗尽；然后用 pprof、慢日志、链路追踪下钻；扩容分层做——DB 加只读从库或分库分表，缓存加节点，服务本身水平扩实例+调优连接池。

回答要点
  1. 按 CPU/内存/RT/QPS 四类指标对应典型瓶颈
  2. 列出至少两个诊断工具（pprof、慢日志、trace）
  3. 给出分层扩容方案（DB/缓存/服务）
完整解析（含追问与踩坑）→
5.LLM 自己死循环了怎么解决？

三道防线：第一层加最大 step 限制，比如最多调用 10 次工具；第二层用 state tracking 记录历史 action，检测重复调用同一工具三次就强制终止；第三层引入 human-in-the-loop，关键路径超时未返回时弹窗确认。不能只依赖 prompt 约束。

回答要点
  1. 提出 step 数硬限制
  2. 给出基于历史动作的重复检测机制
  3. 说明人工介入的触发条件和位置
完整解析（含追问与踩坑）→
6.有的时候 LLM 可能做了一些危险的操作，要怎么去做一个人工介入/确认的功能呢？

建立危险操作白名单，比如 delete、exec、send_money；agent 执行前检查 action 是否命中，命中则暂停流程，生成结构化确认卡片（含操作对象、影响范围、风险等级），推送给审批人；审批通过才继续，超时自动拒绝。不能只靠 LLM 自判。

回答要点
  1. 定义危险操作的判定依据（白名单+语义）
  2. 说明确认卡片需包含对象/影响/风险三级信息
  3. 明确超时自动拒绝的兜底策略
完整解析（含追问与踩坑）→
7.Function call 的能力和 MCP 这两个有什么区别？

Function call 是 OpenAI 提出的 JSON Schema 描述工具能力，由模型直接输出结构化调用；MCP 是新标准，支持双向通信、流式响应、工具发现和会话上下文共享，本质是协议层升级，让工具能主动推送事件，不止被动响应。

回答要点
  1. 指出 function call 是单向、模型驱动、静态 schema
  2. 说明 MCP 支持双向、流式、动态发现
  3. 强调 MCP 解决了长周期工具交互的断连问题
完整解析（含追问与踩坑）→
8.RAG 文档切分的方式有哪些？

常用三种：按固定长度切（如 512 token），简单但易断句；按语义切，用 NLP 模型识别段落边界；按结构切，比如 markdown 的 #、## 标题层级，保留上下文完整。生产环境推荐标题切分+重叠 10%，兼顾召回和精度。

回答要点
  1. 列举固定长度、语义、结构三种方式
  2. 指出每种的优缺点（如断句/计算开销/结构依赖）
  3. 给出生产推荐方案及理由（标题+重叠）
完整解析（含追问与踩坑）→
9.假如向量数据库现在用户量比较大，用户会频繁地更新这个知识库里面的文档。那你要怎么去做这个数据库的索引？

避免全量重建：用支持增量更新的索引类型，比如 HNSW 的动态版本或 DiskANN；冷热分离——热数据走内存索引，冷数据落盘；再加一层变更日志，异步批量 merge 到主索引，保证查询不卡顿。还要配 TTL 清理过期向量。

  1. 选择支持增量更新的索引结构（如动态 HNSW）
  2. 提出冷热分离架构降低主索引压力
  3. 说明异步 merge + TTL 的稳定性保障

11.MySQL 有哪些锁？事务隔离级别有哪些？不同隔离级别下这些锁如何工作？

锁类型：行锁（记录锁、间隙锁、临键锁）、表锁、意向锁。隔离级别：读未提交、读已提交、可重复读、串行化。RR 下默认用临键锁（记录锁+间隙锁）防止幻读；RC 下只用记录锁，不加间隙锁，所以可能幻读。

回答要点
  1. 准确说出四种隔离级别名称
  2. 区分记录锁、间隙锁、临键锁三者关系
  3. 明确 RR 用临键锁防幻读，RC 不加间隙锁
完整解析（含追问与踩坑）→
12.SSE 的原理是什么？如果不用 SSE 还有什么方法能立即推送？

SSE 是服务器通过持久 HTTP 连接单向推送文本事件，基于 text/event-stream MIME 类型，客户端用 EventSource API 接收；替代方案有 WebSocket（双向、低延迟）、长轮询（兼容老浏览器但开销大）、WebRTC DataChannel（P2P 场景），选型要看是否需要双向、兼容性和运维成本。

回答要点
  1. 说明 SSE 单向、HTTP 持久连接、text/event-stream 核心机制
  2. 列出 WebSocket / 长轮询 / WebRTC 三个替代方案
  3. 点出各方案关键差异（双向性、兼容性、复杂度）
完整解析（含追问与踩坑）→
13.实现 HTTP 206 Partial Content 响应。

接收 Range 请求头，解析 start-end 字节范围；校验范围合法性（不越界、end>=start）；读取文件对应片段；返回 206 状态码，Content-Range 头填 ‘bytes start-end/total’，Content-Length 设为片段大小，最后写入二进制数据流。注意处理单字节范围和多范围请求。

回答要点
  1. 正确解析 Range 头并提取字节区间
  2. 校验范围有效性（含 end==start 和越界）
  3. 设置正确的 Content-Range 和 Content-Length 响应头
完整解析（含追问与踩坑）→
