二面 未标注 GoClub 互联网 8 道题 2026-11-09

这一场问了什么

1.请介绍你们的鉴权方案，包括验证闭环、平台集成和工具动态更新机制。

我设计的是四层鉴权：用户侧用OAuth2.0+SSO，平台侧用AppKey+签名验身份，工具侧按scope控制调用权限，资源侧基于租户/数据域做行级过滤。验证闭环包含单测覆盖鉴权逻辑、集成测试走通主链路、灰度期审计日志+异常告警，工具动态更新靠配置中心实时下发tool schema、版本和路由规则。

回答要点
  1. 分层鉴权（用户/平台/工具/资源）
  2. 验证闭环含单测、集成测试、灰度审计、告警
  3. 工具动态更新依赖配置中心管理schema/版本/路由
完整解析（含追问与踩坑）→
2.你通常如何阅读大型开源框架的源码？

我先跑最小demo，抓准核心概念和入口类；然后顺主链路读关键接口和数据结构，重点看模块边界、生命周期、扩展点和错误处理；复杂部分用断点+调用图+测试用例交叉验证；最终落到三个问题：它解决什么问题？核心抽象是什么？扩展点在哪？

回答要点
  1. 从最小demo和核心概念切入
  2. 关注模块边界、生命周期、扩展点、错误处理
  3. 用调试/日志/调用图/测试辅助理解
  4. 总结出问题域、抽象模型、可扩展性
完整解析（含追问与踩坑）→
3.请介绍你做的Agent或Demo项目的核心模块，包括总线、Session、记忆设计和失败恢复机制。

我拆成七个模块：任务入口、规划器、工具层、事件总线、Session管理、记忆系统、执行器。事件总线串起模型推理、工具调用和用户输入；Session存对话上下文；记忆沉淀用户偏好和历史决策；失败恢复靠重试+断点续跑+执行轨迹记录+人工接管入口。

回答要点
  1. 明确列出核心模块（至少5个）
  2. 事件总线承担解耦和状态同步职责
  3. Session管理单次任务上下文
  4. 记忆系统支持长期知识沉淀
  5. 失败恢复含自动重试、断点续跑、轨迹记录、人工入口
完整解析（含追问与踩坑）→
4.你有没有做过端到端闭环项目？请举例说明。

我做过一个AI客服工单分类项目：需求来自客服团队痛点，我设计prompt+few-shot+规则校验方案，开发时对接内部LLM平台和工单系统，上线后建评测集、收badcase、分析日志，迭代了3版prompt和2次tool schema，最终准确率从72%提到89%，并接入CI回归。

回答要点
  1. 覆盖需求来源→方案→开发→测试→上线→监控→迭代全链路
  2. AI项目需体现prompt/tool schema/评测集/日志分析等特有环节
  3. 有量化结果和具体优化动作
完整解析（含追问与踩坑）→
5.当需求不清晰但Deadline很紧时，你如何推进？

我先拉干系人15分钟对齐目标、核心用户、关键场景和验收标准；再把需求拆成‘必须交付’‘可延后’‘待确认’三类；立刻启动最小闭环开发，比如只做核心流程+mock工具；每个半天同步进展和卡点，把模糊项转成可验证的小里程碑。

回答要点
  1. 15分钟内快速对齐目标/用户/场景/验收标准
  2. 需求三分法（必须/可延/待确认）
  3. 优先实现最小可用闭环而非完整功能
  4. 用短周期同步将模糊需求转化为可验收里程碑
完整解析（含追问与踩坑）→
6.设计一个RAG服务的在线问答链路，要求支持大模型故障时的降级策略。

我把链路拆成query rewrite→embedding→召回→rerank→prompt构造→LLM调用。LLM故障时，我会降级：首token超3秒就熔断，改用缓存答案或摘要；全局并发限流到100QPS；热门问题预缓存结果；最后兜底返回检索到的文档列表，保证用户始终有信息可看，而不是空白页。

回答要点
  1. 必须分层定义各环节超时（如embedding 1s、LLM首token 3s）
  2. 必须有熔断+重试+jitter组合策略
  3. 必须提供非LLM兜底方案（摘要/文档列表/缓存答案）
  4. 必须隔离LLM连接池和熔断器，避免拖垮检索链路
完整解析（含追问与踩坑）→
7.你日常使用 AI 辅助编码的工作流是怎样的？

我把它分成三阶段：理解阶段让AI梳理陌生模块调用链、生成注释和边界图；编码阶段让它写样板代码、单元测试和文档更新，但我严格控制输入prompt和输出校验；验证阶段用AI基于diff分析潜在风险点，再人工跑单测+lint+本地联调确认。AI永远不碰主干逻辑决策。

回答要点
  1. 分阶段定义AI角色（理解/生成/验证）
  2. 明确人机分工边界（如‘AI不碰主干逻辑’）
  3. 有具体校验手段（prompt约束、diff分析、人工复核）
  4. 体现对AI输出缺陷的防范意识
  5. 给出至少一个真实使用场景（如写测试/注释）
完整解析（含追问与踩坑）→
8.当模型输出不稳定时，工程上有哪些处理手段？

我分三层处理：输入层用few-shot+低temperature+结构化prompt约束；输出层强制JSON Schema校验+规则后处理+rerank；关键链路加兜底策略——校验失败自动重试、触发人工确认、记录完整trace供回放。工具调用还额外加幂等ID和失败原因标记。

回答要点
  1. 输入层：few-shot/temperature/prompt结构化
  2. 输出层：Schema校验+规则后处理+rerank
  3. 兜底层：重试+人工确认+完整trace记录
  4. 工具调用需幂等ID和失败归因标记
完整解析（含追问与踩坑）→
