这一场问了什么

1.对 Harness / AI Coding Harness 怎么理解？

Harness 是 AI Coding 的工程外骨骼——它把需求、上下文、代码库、工具调用、测试、CI、权限、日志和回放串成闭环，核心目标是让 AI 产出可约束、可验证、可复现、可持续改进。

回答要点
  1. 明确 Harness 是工程闭环而非单点工具
  2. 点出至少4个关键组件（如测试、CI、权限、日志）
  3. 强调‘可约束/可验证/可复现’三大目标
完整解析（含追问与踩坑）→
2.文档、代码、记忆/事实层，这三层应该如何分层设计？

我按稳定性与可信度分层：文档层放长期稳定的设计契约、业务规则和接口规范；代码层是唯一可信的事实源，含逻辑、测试和配置；记忆层存动态状态——比如线上报错模式、用户偏好、本周重点OKR。用AI时，文档提供背景，代码做事实校验，记忆给个性化上下文，且每次注入都带来源、时间戳和置信度标签。

回答要点
  1. 清晰定义每层内容范围与核心属性（如‘代码层是唯一可信事实源’）
  2. 说明各层对AI的作用（背景/校验/上下文）
  3. 提出关键治理机制（如来源标注、时效性标识）
  4. 体现层间隔离与协作关系
  5. 避免将‘记忆层’等同于聊天记录或日志堆砌
完整解析（含追问与踩坑）→
3.你日常使用 AI 辅助编码的工作流是怎样的？

我把它分成三阶段：理解阶段让AI梳理陌生模块调用链、生成注释和边界图；编码阶段让它写样板代码、单元测试和文档更新，但我严格控制输入prompt和输出校验；验证阶段用AI基于diff分析潜在风险点，再人工跑单测+lint+本地联调确认。AI永远不碰主干逻辑决策。

回答要点
  1. 分阶段定义AI角色（理解/生成/验证）
  2. 明确人机分工边界（如‘AI不碰主干逻辑’）
  3. 有具体校验手段（prompt约束、diff分析、人工复核）
  4. 体现对AI输出缺陷的防范意识
  5. 给出至少一个真实使用场景（如写测试/注释）
完整解析（含追问与踩坑）→
4.现在主要使用哪些 AI Coding 工具？

主力是 GitHub Copilot 和 Cursor，用于日常补全和对话编程；配合自建的本地 LLM + CodeGraph 索引做 repo 级理解；还用 CodeWhisperer 做安全敏感场景的二次校验。所有工具都绑定到我们的 CI 流水线里做自动 PR review。

回答要点
  1. 列出至少2个具体工具名
  2. 说明每个工具的差异化用途（如 Copilot 日常补全/Cursor 对话编程）
  3. 体现工具已融入工程流程（如绑定 CI/PR review）
完整解析（含追问与踩坑）→
5.为什么觉得汇报和表达产出很重要？

研发工作需要让团队理解‘做了什么、为什么做、结果如何、风险在哪、下一步是什么’。表达产出能降低协作成本，也能把个人技术价值转化成团队可复用资产。对 AI 研发尤其重要——它关系到需求澄清、评测解释、效果复盘和跨团队推动。

回答要点
  1. 点明表达的4个核心信息维度（做了什么/为什么/结果/风险）
  2. 说明表达对协作和资产沉淀的双重价值
  3. 结合 AI 研发特殊性给出1个具体场景（如评测解释）
完整解析（含追问与踩坑）→
6.在开源社区做 PR，具体做什么？

我会先读 issue 背景和相关模块，设计最小可合并方案，写清晰 commit message 和 PR 描述，加对应测试，响应 reviewer 修改意见，迭代后合入。重点是读懂项目规范、和 maintainer 协作、把问题拆小、给出可维护实现——技术之外，文档、测试和兼容性同样重要。

回答要点
  1. 完整覆盖 PR 全流程（issue→设计→实现→测试→review→合入）
  2. 强调2个非代码要素（如文档/测试/兼容性/沟通）
  3. 点明‘最小可合并’和‘可维护实现’两个工程原则
完整解析（含追问与踩坑）→
