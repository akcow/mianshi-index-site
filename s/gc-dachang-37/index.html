1.手写LRU缓存

用哈希表O(1)查节点，双向链表O(1)移位和删尾。头结点最新访问，尾结点最久未用。Get命中就移到头；Put时若存在则更新值并移到头，若不存在且超容，先删尾节点再插入新节点到头。关键细节：哨兵头尾节点避免空指针判断，删除节点要同时解哈希表映射。

回答要点
  1. 哈希表+双向链表结构选型合理
  2. Get/Put操作时间复杂度均为O(1)
  3. 正确处理容量超限时的尾部淘汰
  4. 哨兵节点或空指针防护到位
完整解析（含追问与踩坑）→
2.GMP 模型。

G 是 goroutine，M 是 OS 线程，P 是调度器上下文。M 必须绑定 P 才能执行 G；P 维护本地运行队列，也会从全局队列或其它 P 偷任务；网络 I/O 由 netpoller 异步唤醒，系统调用阻塞时 P 会转交给空闲 M，避免线程闲置。

回答要点
  1. 清晰定义 G/M/P 三者角色及关系
  2. 说明 P 如何协调本地队列、全局队列和 work-stealing
  3. 指出 netpoller 和系统调用阻塞对 M/P 绑定的影响
完整解析（含追问与踩坑）→
3.Channel 无缓存和有缓存有什么区别？分别在什么情况下使用？

无缓存 channel 是同步的，发送方必须等到接收方就绪才返回，适合任务交接、信号通知、强背压控制；有缓存 channel 是异步的，发送方写入缓冲区就返回，适合解耦生产消费、削峰填谷、worker pool 任务分发。

回答要点
  1. 明确区分同步 vs 异步行为本质
  2. 各举一个典型使用场景（非教科书式）
  3. 能说明缓冲区大小设置不当的风险（如过大导致内存积压）
完整解析（含追问与踩坑）→
4.defer 的实现和返回值修改

defer 会把函数调用记录到当前 goroutine 的 defer 链表，函数 return 前按后进先出执行。关键点是：先给返回值赋值，再执行 defer，最后返回。所以命名返回值（如 func() (x int)）能被 defer 修改；但普通变量不行，因为返回值已在 defer 前确定。

回答要点
  1. 明确 defer 执行时机在 return 语句赋值之后、真正返回之前
  2. 区分命名返回值（可被 defer 修改）和匿名返回值（不可）
  3. 能正确分析示例代码返回 2 的原因
  4. 知道现代 Go 对简单 defer 做开放编码优化（减少 runtime 开销）
完整解析（含追问与踩坑）→
5.某网关项目里，如何把存量 API 适配成 MCP 调用形式？

我在网关层解析OpenAPI或内部IDL，自动生成MCP tool的name、description、input schema；请求来时把模型传入的JSON参数反序列化，转成HTTP/gRPC调用下游，再把响应按MCP result格式封装返回。

回答要点
  1. 明确适配发生在网关层而非业务服务
  2. 说明输入schema生成与参数转换逻辑
  3. 输出符合MCP规范的result结构
完整解析（含追问与踩坑）→
6.OAuth 相关鉴权流程怎么设计？

用户跳转授权服务登录并授权，回调带code；网关用code换access_token和refresh_token；后续请求校验token签名、scope、audience和过期时间，并把用户ID、权限列表透传给下游服务。

回答要点
  1. 完整描述Authorization Code Flow关键步骤
  2. 强调网关承担token校验与上下文透传
  3. 指出scope/audience等关键校验项
完整解析（含追问与踩坑）→
7.高并发下网关怎么考虑扩展和治理？

网关本身无状态，靠水平扩容；入口用负载均衡，内部做连接池、限流熔断、超时重试；可观测性要记录QPS、错误率、P95延迟、下游耗时、重试次数，失败时能按租户/接口/模型快速下钻。

回答要点
  1. 明确无状态+水平扩展前提
  2. 列出至少三项核心治理能力（限流/熔断/超时）
  3. 强调可观测性维度（租户/接口/模型等）
完整解析（含追问与踩坑）→
8.你的上下文压缩怎么做的？

分三步：先用AST解析提取代码关键节点（函数签名、调用链）；再用语义聚类合并相似日志片段；最后用轻量RAG索引，只保留触发条件和错误码，原始文件走按需加载。不是全文摘要，而是结构化裁剪。

回答要点
  1. AST解析用于代码结构压缩
  2. 语义聚类用于日志去重
  3. RAG索引+按需加载应对超长文件
完整解析（含追问与踩坑）→
9.agent loop 为什么会死循环，怎么防护？

死循环常因目标模糊、工具返回信息不足、模型反复选同一工具或缺少停止条件。我加最大轮数、工具调用次数限制、重复动作检测、token预算控制，还设失败阈值和人工确认开关。

回答要点
  1. 准确归因三类典型死循环原因
  2. 防护手段覆盖硬限制（轮数/次数）、软检测（重复/预算）、人工兜底
  3. 强调stop condition显式定义
完整解析（含追问与踩坑）→

长期记忆沉淀用户偏好、项目事实等结构化知识；RAG从外部知识库召回相关内容增强回答。关键环节包括文档清洗切分、embedding生成、向量检索、rerank、权限过滤、上下文拼装和引用溯源。

  2. 列出不少于5个关键环节
  3. 强调权限过滤与引用溯源的工程必要性

11.平时 AI coding 怎么用？AI 生成代码和人工 review 的关系。

我用AI写样板代码、补单元测试、解释报错、做重构草案和写文档。但它不替代人工review——人工要卡架构边界、业务语义、安全漏洞、异常路径和可维护性，AI只是提效助手。

回答要点
  1. 列举3种以上具体使用场景
  2. 明确AI与人工的分工边界（AI提效，人工把关）
  3. 指出人工必须守住的关键质量红线
完整解析（含追问与踩坑）→
12.AI review AI 是否有效？

对明显bug、遗漏分支、风格问题、测试缺口和安全线索，AI review有一定效果；但关键业务逻辑、性能瓶颈、异常传播路径，仍需人工结合静态扫描、自动化测试和线上观测共同把关。

回答要点
  1. 分场景说明有效性（强项/弱项）
  2. 指出必须人工介入的典型场景
  3. 强调多手段（扫描/测试/观测）闭环验证
完整解析（含追问与踩坑）→
