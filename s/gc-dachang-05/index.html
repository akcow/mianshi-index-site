1.视频 Feed 流最核心的设计是什么

我觉得最核心的是复合游标分页。因为 Feed 数据持续新增、删除、热度变化，用 offset 深分页会越来越慢，还容易跳过或重复。我用 (score, id) 或 (created_at, id) 做游标，查的时候 where (score < ? or (score = ? and id < ?))，再配 (score,id) 联合索引，既保证翻页稳定，又支持高性能深分页。

回答要点
  1. 指出 offset 分页在动态 Feed 中的缺陷（性能退化+数据错乱）
  2. 明确复合游标结构（排序字段+唯一主键）及 SQL 写法
  3. 说明索引需匹配游标字段（如 (score DESC, id DESC)）
  4. 能区分通用游标与个性化场景（如 ZSet 预排序后游标）
完整解析（含追问与踩坑）→
2.消息队列异常时怎么降级

我会按业务强弱依赖分级降级：强依赖结果的走同步直写或本地消息表兜底；弱依赖的落库记状态，后台补偿；非核心通知类延迟处理。比如 MQ 异常时，worker 投递失败就更新 retry_count 和 next_retry_at 指数重试；长时间异常就熔断投递，核心链路直写 MySQL，同时保留 outbox 记录，等恢复后补偿。

回答要点
  1. 明确三级降级策略（同步直写/本地任务/延迟处理）并对应业务场景
  2. 说出具体技术手段（outbox 表、retry_count+指数退避、熔断开关）
  3. 强调幂等保障（如幂等键）和恢复补偿机制
  4. 区分 Redis 异常（降级读 DB+singleflight）与 MQ 异常的不同应对
完整解析（含追问与踩坑）→
3.消息队列怎么做高可用和持久化

RabbitMQ 高可用和持久化要三端协同：生产端开 confirm 确认，Broker 端设 exchange 和 queue 为 durable、消息 delivery_mode=2，消费端用 manual ack。优先选 quorum queue，它用 Raft 多副本，主挂了能自动切主。还要配死信队列和 TTL，异常消息进 DLX 人工排查，不能全靠重试。

回答要点
  1. 生产端：confirm 机制 + 消息持久化（delivery_mode=2）
  2. Broker 端：exchange/queue durable + quorum queue 选型依据
  3. 消费端：manual ack + nack/requeue/死信路由
  4. 监控项：积压量、ack 速率、磁盘水位、死信数量
完整解析（含追问与踩坑）→
4.切片和数组的区别

数组是固定长度的值类型，长度属于类型的一部分，比如 [3]int 和 [4]int 是不同类型，赋值会复制整个数组。切片是引用类型，底层是包含指针、长度、容量的 header 结构，传参只复制 header，底层数组共享，扩容可能分配新内存。

回答要点
  1. 数组长度是类型组成部分，不同长度数组类型不兼容
  2. 数组赋值/传参是值拷贝，切片是 header 拷贝
  3. 切片扩容可能改变底层数组指针，原 slice 与新 slice 不再共享数据
  4. 能举例说明切片修改影响原底层数组，而数组不会

5.缓存击穿和缓存雪崩

缓存击穿是单个热点 key 失效瞬间，大量请求穿透到 DB；缓存雪崩是大量 key 同时过期或缓存集群宕机，导致 DB 承压面广。击穿用互斥锁或 singleflight 拦住并发请求；雪崩要加随机 TTL、做缓存预热、部署多级缓存，甚至限流降级。

回答要点
  1. 准确定义：击穿=单 key 热点失效，雪崩=批量 key 失效或集群故障
  2. 击穿解法必须含并发控制（锁/sf）+ 后台刷新
  3. 雪崩解法必须含时间分散（随机 TTL）+ 容灾（多级缓存/限流）
  4. 能指出两者监控指标差异（击穿看单 key QPS 突增，雪崩看整体缓存命中率骤降）
完整解析（含追问与踩坑）→
6.Go map 底层如何实现

Go map 底层是哈希表，核心是 hmap 结构和桶 bmap。每个桶最多存 8 个键值对，存 top hash 加速比较；冲突时挂溢出桶。扩容不是一次性搬完，而是渐进式：每次读写都搬一个旧桶，避免卡顿。hash 值先定位 bucket，再比 top hash，最后比 key。

回答要点
  1. 说出 bucket 最大容量（8）及 top hash 作用（快速过滤）
  2. 说明溢出桶机制和渐进式扩容原理
  3. 能描述查找路径：hash → bucket → top hash → key 比较
  4. 知道扩容触发条件（装载因子 > 6.5 或 overflow 太多）
完整解析（含追问与踩坑）→
7.defer 的实现和返回值修改

defer 会把函数调用记录到当前 goroutine 的 defer 链表，函数 return 前按后进先出执行。关键点是：先给返回值赋值，再执行 defer，最后返回。所以命名返回值（如 func() (x int)）能被 defer 修改；但普通变量不行，因为返回值已在 defer 前确定。

回答要点
  1. 明确 defer 执行时机在 return 语句赋值之后、真正返回之前
  2. 区分命名返回值（可被 defer 修改）和匿名返回值（不可）
  3. 能正确分析示例代码返回 2 的原因
  4. 知道现代 Go 对简单 defer 做开放编码优化（减少 runtime 开销）
完整解析（含追问与踩坑）→
8.Channel 无缓存和有缓存有什么区别？分别在什么情况下使用？

无缓存 channel 是同步的，发送方必须等到接收方就绪才返回，适合任务交接、信号通知、强背压控制；有缓存 channel 是异步的，发送方写入缓冲区就返回，适合解耦生产消费、削峰填谷、worker pool 任务分发。

回答要点
  1. 明确区分同步 vs 异步行为本质
  2. 各举一个典型使用场景（非教科书式）
  3. 能说明缓冲区大小设置不当的风险（如过大导致内存积压）
完整解析（含追问与踩坑）→
9.两个有序数组的中位数

最优解是二分较短数组的切分点。设切分后左半部分共 (m+n+1)/2 个元素，通过 i+j=(m+n+1)/2 算出另一数组切分点 j。检查 leftA <= rightB 且 leftB <= rightA，满足则中位数是左半最大值（奇数）或左右半极值平均（偶数）。注意边界处理：i=0/j=0 或 i=m/j=n 时用 INT_MIN/INT_MAX 替代。

回答要点
  1. 能写出二分框架：在较短数组上二分 i，j 由公式导出
  2. 正确处理四个边界值（leftA/rightA/leftB/rightB）的越界情况
  3. 准确计算中位数：奇数取 max(leftA,leftB)，偶数取 (max(leftA,leftB)+min(rightA,rightB))/2
  4. 时间复杂度明确为 O(log(min(m,n)))
完整解析（含追问与踩坑）→
10.根据字符串中的数字重新排序

遍历每个字符串，逐字符扫描，遇到数字就拼成整数，没数字就设为 0。然后按这个数字升序排序，数字相同时保持原顺序（用 stable sort）。关键点是：数字提取要连续拼接，比如 ‘a2b3’ 提取 23，不是 2 和 3；空字符串或纯字母返回 0。

回答要点
  1. 正确提取连续数字字符并转为整数（如 'ab2cd3' → 23）
  2. 无数字字符串返回 0
  3. 使用稳定排序保证相同数字的原始顺序
  4. 能处理边界：空字符串、纯字母、前导零（如 'a01b' → 1）
