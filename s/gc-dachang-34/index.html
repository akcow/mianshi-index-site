1.UDP 会不会发生黏包？如果不会，为什么常被误认为会？应用层如何设计协议来可靠传输多个逻辑消息？

UDP 本身不会黏包，因为它是面向报文的，每次 recvfrom 一定返回一个完整 datagram。所谓‘黏包’其实是应用层把多个业务消息塞进同一个 UDP 包，或没按协议解析导致的。正确做法是加应用层帧头，比如前 4 字节存 payload 长度，接收时先读头、再按长度截取，还要校验长度合法性，避免缓冲区溢出。

回答要点
  1. 明确指出 UDP 按报文交付、无黏包概念
  2. 说明常见误解根源（应用层打包/解析不当）
  3. 给出可落地的帧格式（如 length+payload）和安全解析逻辑（校验长度、防截断）
完整解析（含追问与踩坑）→
2.手写一个基于开放寻址法的 HashMap，要求支持 Put、Get、Delete，并处理扩容和删除标记。

我用线性探测，每个槽位存 key/val/state 三元组，state 分 empty/used/deleted。Put 时先找空位或 deleted 位，优先复用 deleted；Get 要跳过 deleted 继续探；Delete 只打标不真删。扩容触发条件是负载因子超 0.7，新数组重建时只 rehash used 状态项。关键点是探测循环要模数组长，且 delete 后必须留 tombstone 保链路。

回答要点
  1. 正确实现线性探测的查找/插入/删除循环逻辑
  2. delete 使用 deleted 标记而非清空，且 Get/Put 能正确处理
  3. 扩容时仅迁移 state==used 的项，且重新哈希
完整解析（含追问与踩坑）→
3.前缀表达式如何求值？请从右向左扫描并用栈实现。

从右往左扫：遇到数字就压栈；遇到运算符就弹两个数——注意顺序，先弹的是左操作数，后弹的是右操作数，比如‘-’要算 a-b；算完结果再压栈。最后栈里只剩一个数就是答案。要检查栈大小，避免弹空或剩多个，还要判除零。

回答要点
  1. 明确扫描方向为从右向左
  2. 弹出两个操作数时顺序正确（先弹左，后弹右）
  3. 有基础错误处理（栈空、除零、最终栈元素数≠1）
完整解析（含追问与踩坑）→

5.项目中如何发现并解决 UDP 相关的问题？当时用了什么工具抓包或调试？

我们在压测时发现部分请求超时，但服务端日志显示没收到。用 tcpdump 抓包发现客户端发出了 UDP 包，但服务端网卡没收到。进一步用 ss -u 查接收队列溢出，确认是 recv buffer 太小。我们调大 net.core.rmem_default，同时在应用层加了 SO_RCVBUF 设置，并监控 socket 接收队列长度告警。

6.前缀表达式求值时，如果遇到非法 token（比如字母），你的程序怎么处理？

我会在解析 token 时做类型校验：非运算符且不能转整数，就立即返回 error，带明确定位信息，比如‘token at index 5 “abc” is invalid’。不静默跳过，也不用 panic，因为这是输入错误，不是程序 bug。上层可以据此拒绝整个表达式，避免后续计算污染。

回答要点
  1. 对非法 token 主动校验并提前失败
  2. error 信息包含位置和具体内容
  3. 不 panic、不忽略、不继续执行

8.UDP 传输中，如果 IP 层发生了分片，你的应用层帧解析逻辑会受影响吗？为什么？

会！虽然 UDP 本身不关心分片，但你的帧头（比如前 4 字节 length）如果被 IP 分片切在中间，接收端第一次 recvfrom 只拿到第一个分片，里面没有完整 length 字段，就会解析失败或越界读。必须确保单个 UDP 包不超过 MTU（通常 1500），或者在应用层加重传和重组逻辑。

回答要点
  1. 明确指出分片可能割裂帧头，导致解析失败
  2. 给出规避方案（控制包大小 ≤ MTU）
  3. 说明若必须大包，需额外设计分片重组机制
完整解析（含追问与踩坑）→
9.前缀表达式求值栈实现中，为什么弹出的两个数，第一个是左操作数、第二个是右操作数？

因为前缀是 operator operand1 operand2，从右往左扫时，operand2 先入栈，operand1 后入栈。弹出时 operand1 先出（栈顶），operand2 后出（次栈顶）。比如 ‘- 5 3’，右扫得 [3,5]，弹 5 再弹 3，算 5-3，顺序才对。

回答要点
  1. 明确前缀语法结构 operator op1 op2
  2. 说明从右向左扫描导致 op2 先入、op1 后入
  3. 弹出顺序与运算顺序严格对应（先弹左，后弹右）
完整解析（含追问与踩坑）→
10.你设计的 UDP 应用层协议，如何防止恶意客户端发送超大 length 字段导致服务端内存耗尽？

我在解析 length 字段后立刻校验：必须 ≤ 预设最大消息体（如 64KB），且 ≤ 当前 recv buffer 剩余长度。校验失败直接 close 连接并记录攻击 IP。另外，服务端分配内存前先检查系统剩余内存，低于阈值则拒绝新连接。这样既防 OOM，又阻断暴力试探。

回答要点
  1. length 校验双维度（协议上限 + 缓冲区剩余）
  2. 失败后主动断连并审计（IP 记录）
  3. 增加系统级防护（内存水位检查）
完整解析（含追问与踩坑）→
