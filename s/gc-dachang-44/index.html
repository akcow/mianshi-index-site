1.数据从 MySQL 同步到 ES 的方法有哪些？

常用三种：一是用 Logstash 或 DataX 做定时全量+增量抽取；二是监听 MySQL binlog（如 Canal）实时捕获变更，推送到 Kafka 再消费写入 ES；三是业务层双写，但需处理一致性问题。我们项目用的是 Canal + Kafka 方案，保障实时性和可靠性。

回答要点
  1. 说出至少两种主流同步方式
  2. 能区分实时性/一致性/运维成本差异
  3. 提到 binlog 监听或中间件（如 Canal/Kafka）

2.MySQL 有哪些日志？各自作用是什么？

主要有三种：redo log（InnoDB 引擎层，保证崩溃恢复，循环写，物理日志）；undo log（引擎层，支持回滚和 MVCC，逻辑日志）；binlog（Server 层，用于主从复制和恢复，逻辑日志，追加写）。三者协同保障 ACID。

回答要点
  1. 分别说明 redo、undo、binlog 的层级（引擎/Server）
  2. 指出 redo 保崩溃恢复、binlog 保复制与归档、undo 保回滚与 MVCC
  3. 强调 redo 是物理日志、binlog/undo 是逻辑日志
完整解析（含追问与踩坑）→
3.Cache Aside 模式存在哪些问题？如何解决延迟双删？

主要问题是并发写导致脏数据：先删缓存再更新 DB 时，若另一请求在删缓存后、DB 更新前读到旧值并回写缓存，就出错了。延迟双删是在更新 DB 后 sleep 一段时间再删一次缓存，靠时间差覆盖可能的脏写，但 sleep 时间难定，我们改用订阅 binlog 异步删缓存。

回答要点
  1. 准确描述‘先删缓存后更新DB’下的并发脏读场景
  2. 说明延迟双删的原理和固有缺陷（如 sleep 不确定性）
  3. 提出更优解如 binlog 监听或消息队列
完整解析（含追问与踩坑）→
4.项目中遇到的分布式事务问题是什么？如何解决的？

我们在订单创建时要扣库存、发优惠券、写订单表，跨三个微服务。没用 Seata 全局事务，因为性能压不住。最后用 TCC 模式：Try 阶段预占资源（冻结库存、生成待发券），Confirm 真实扣减，Cancel 回滚预占。关键点是 Confirm/Cancel 必须幂等，且要有超时自动补偿。

回答要点
  1. 明确具体业务场景（如订单+库存+券）
  2. 说明选型理由（如放弃XA/Seata，选择TCC/Saga）
  3. 强调幂等、补偿、超时等生产级细节
完整解析（含追问与踩坑）→
5.Go map 底层如何实现

Go map 底层是哈希表，核心是 hmap 结构和桶 bmap。每个桶最多存 8 个键值对，存 top hash 加速比较；冲突时挂溢出桶。扩容不是一次性搬完，而是渐进式：每次读写都搬一个旧桶，避免卡顿。hash 值先定位 bucket，再比 top hash，最后比 key。

回答要点
  1. 说出 bucket 最大容量（8）及 top hash 作用（快速过滤）
  2. 说明溢出桶机制和渐进式扩容原理
  3. 能描述查找路径：hash → bucket → top hash → key 比较
  4. 知道扩容触发条件（装载因子 > 6.5 或 overflow 太多）
完整解析（含追问与踩坑）→
6.对比 Go 和 Java 的 GC 机制

Java G1 是分代+增量回收，停顿可控但仍有 STW；Go 1.22 用的是三色标记+混合写屏障的并发 GC，STW 仅在标记开始和结束各一次，毫秒级。Go GC 更激进地减少暂停，代价是 CPU 占用略高；Java 则提供更细粒度调优参数。我们服务切 Go 后 P99 延迟降了 40%。

回答要点
  1. 指出 Go GC 目标是超低延迟（sub-ms STW）
  2. 说明 Java G1 的混合回收与分区概念
  3. 提到写屏障在并发标记中的作用
完整解析（含追问与踩坑）→
7.Go GC的STW（Stop-The-World）发生在哪些具体阶段？每个阶段的主要任务是什么？

Go GC有三次极短STW：第一次在sweep termination，确保上一轮清扫干净；第二次在mark setup，开启写屏障前做标记准备；第三次在mark termination，完成最终标记后关闭写屏障、切换到清扫。每次都在毫秒级，目标是让并发标记更安全。

回答要点
  1. 必须准确列出三个阶段名称：sweep termination / mark setup / mark termination
  2. 每个阶段需对应一句话任务（如‘mark setup：启用混合写屏障’）
  3. 必须强调STW时长目标（毫秒级）和设计意图（保障并发标记正确性）
  4. 需指出写屏障是STW的核心关联点
完整解析（含追问与踩坑）→
8.协程原理是什么？

协程是用户态的轻量级线程，由运行时自主调度；核心是保存和恢复寄存器上下文（如栈指针、指令指针），通过函数跳转或汇编指令实现无系统调用的切换，避免线程切换开销。Go 的 GMP 模型、Python 的 async/await 都基于此。

回答要点
  1. 明确协程是用户态调度而非内核态
  2. 指出关键动作：上下文保存/恢复（栈+寄存器）
  3. 说明优势：低开销、高并发、无锁协作
完整解析（含追问与踩坑）→
9.MySQL 聚簇索引和非聚簇索引的区别？为什么非聚簇索引的叶子节点中会包含全部记录？

聚簇索引叶子存完整行数据，主键即索引；非聚簇索引（二级索引）叶子存的是主键值，不是整行。题干说法有误——非聚簇索引叶子不存全部记录，只存索引列+主键，查数据要回表。可能面试官口误，或指覆盖索引场景下联合索引恰好包含所有 SELECT 字段。

回答要点
  1. 清晰定义聚簇索引叶子存数据行
  2. 指出非聚簇索引叶子只存索引列+主键
  3. 纠正原文错误并给出合理解释（如覆盖索引）
完整解析（含追问与踩坑）→
10.B+ 树结构中，如果是联合索引 (a,b,c)，每个非叶子节点的结构是什么样的？

非叶子节点只存索引键的最左前缀，比如 (a,b,c) 联合索引，非叶子节点里每个键是 a 的值，不带 b、c；只有叶子节点才按 a→b→c 排序存储完整索引项，并用链表连起来。所以非叶子节点本质是‘a 的目录’，靠它快速定位到对应 a 值的叶子块。

回答要点
  1. 明确非叶子节点仅含最左列 a 的值
  2. 说明叶子节点才包含完整联合键 (a,b,c)
  3. 指出叶子节点间有双向链表支持范围查询
完整解析（含追问与踩坑）→
11.怎么看一条 SQL 的执行计划？需要重点关注哪些字段？

用EXPLAIN FORMAT=TREE或EXPLAIN ANALYZE执行SQL。重点看type（最好到range或ref）、rows（预估扫描行数）、key（实际使用的索引）、Extra（警惕Using filesort/Using temporary）。如果type是ALL或rows远超实际结果数，说明索引没用好。

回答要点
  1. 写出标准命令EXPLAIN [FORMAT=TREE] SELECT...
  2. 指出type、rows、key、Extra四个必看字段
  3. 说明各字段的健康阈值（如type≠ALL，rows接近实际）
完整解析（含追问与踩坑）→
12.ES 有三个数据节点，某个索引有三个分片，分别在不同节点上。查询纯数字 ID 的 Top100 倒序结果，请求发给 ES 后的简单实现原理是什么？

客户端请求任意节点（协调节点），它把查询广播到三个分片，每个分片本地查自己的 Top100，返回各自 top100 给协调节点；协调节点合并 300 条结果，再取全局 Top100 返回。注意：ID 是数字且倒序，ES 会用 doc values 加速排序，不走 text 分词。

回答要点
  1. 明确协调节点的路由与合并角色
  2. 指出各分片独立计算局部 top-k，再全局归并
  3. 说明数字 ID 排序走 doc values 而非 inverted index

13.Spring 是怎么解决循环依赖的？

Spring 用三级缓存：一级存成品 Bean，二级存早期暴露的 Bean（未初始化完），三级存 ObjectFactory 工厂。A 依赖 B 时，A 创建中就把 A 的工厂放入三级缓存；B 创建时发现依赖 A，就从三级缓存拿工厂，提前暴露 A 的半成品实例放进二级缓存，B 完成后 A 再注入 B 并完成初始化。

回答要点
  1. 准确说出三级缓存各自作用（尤其三级存 ObjectFactory）
  2. 描述 A→B→A 循环中三级缓存的流转过程
  3. 指出只能解决 setter 注入的循环依赖
完整解析（含追问与踩坑）→
14.Kafka 什么情况下会触发 rebalance？

四种情况：消费者主动加入或退出组（如启停）、消费者心跳超时（session.timeout.ms）、订阅主题分区数变化、消费者组元数据版本不一致。其中心跳超时最常见，比如 GC 停顿太久或网络抖动，Coordinator 会认为消费者失联，强制 rebalance。

回答要点
  1. 列出至少三种明确触发条件
  2. 指出 session.timeout.ms 是心跳超时判定依据
  3. 说明 rebalance 会导致消费暂停和分区重分配
完整解析（含追问与踩坑）→
