1.JWT 认证在你的视频 Feed 流系统中具体是如何实现的？

我们用 Go 的 jwt-go 库生成 token，登录成功后签发含 user_id 和 role 的 HS256 token；API 网关统一校验签名和过期时间，解析后注入 context；敏感接口还校验 role 字段，且每次刷新 token 都更新 Redis 黑名单防止重放。

  2. 说明签名算法与关键载荷（user_id/role）
  3. 描述校验位置（网关层）与上下文传递方式
  4. 提到防重放机制（如 Redis 黑名单或 jti 校验）

2.讲一下推拉结合。你的Inbox和Outbox如何实现？大V如何判定？

普通用户用推模式：关注关系变更时，把大V新视频推到其Inbox（Redis Sorted Set）；大V用拉模式：粉丝查Feed时实时聚合其Outbox（MySQL分表）；大V判定标准是粉丝>10万或单条视频曝光>50万。

  1. 明确推/拉适用对象及触发时机
  2. Inbox用Redis ZSet、Outbox用MySQL分表
  3. 大V判定有可量化阈值（非主观）

3.RabbitMQ 在项目中具体起什么作用？

主要解耦 feed 生成与通知：用户发布视频后，生产者发消息到 fanout exchange，消费端分别做三件事——写入 Redis 热榜、触发 ES 索引更新、异步发站内信；所有耗时操作不阻塞主链路，且通过 ack + 死信队列保障至少一次投递。

回答要点
  1. 明确解耦的具体环节（如发布视频 → 多下游）
  2. 指出 exchange 类型（fanout）及对应业务意图
  3. 列出至少两个独立消费动作（如写 Redis、更新 ES）
  4. 说明可靠性机制（ack + 死信）
完整解析（含追问与踩坑）→
4.Redis 内存淘汰策略有哪些？

共 8 种，常用的是 volatile-lru、allkeys-lru、volatile-ttl、noeviction。重点区别在于：volatil-* 只淘汰带过期时间的 key，allkeys-* 淘汰所有 key；lru 是最近最少使用，ttl 是剩余时间最短，noeviction 则直接报错不淘汰。

回答要点
  1. 至少列出 4 种策略名称
  2. 区分 volatile- 和 allkeys- 前缀含义
  3. 说明 noeviction 的行为
完整解析（含追问与踩坑）→
5.热榜是如何实现的？

用 Redis ZSet 存 hourly_score，score = log(1+pv) * 0.7 + log(1+like_cnt) * 0.3；每小时用 Lua 脚本聚合日志表统计 PV/Like，更新 ZSet；前端查 zrevrangebyscore 获取 Top100；降级时直接读 MySQL 副本兜底。

回答要点
  1. 明确 score 公式含多维度加权（PV+互动）及衰减设计
  2. 说明更新时机与原子性保障（Lua 脚本聚合）
  3. 指出存储结构（ZSet）及查询命令（zrevrangebyscore）
  4. 有降级方案（MySQL 副本）
完整解析（含追问与踩坑）→
6.Raft 共识算法的原理是什么？

Raft 把节点分为 Leader/Follower/Candidate 三种状态；Leader 通过心跳维持权威；选举时 Candidate 发起 RequestVote RPC，获多数票即胜出；日志复制要求 Leader 将命令追加到本地 log 后，异步同步给 Follower，等多数节点 commit 才应用到状态机。

回答要点
  1. 准确说出三种角色及其转换条件
  2. 强调心跳是 Leader 维持权威的核心机制
  3. 说明日志复制的两阶段：追加本地 log → 等多数响应后 commit
  4. 点明安全性约束（如 Leader 必须包含所有已提交日志）
完整解析（含追问与踩坑）→
7.项目中如何防止分布式账本被篡改？

每个区块头存前块哈希、Merkle Root 和 nonce；交易按 Merkle Tree 组织，根哈希写入区块头；全节点校验时，重新计算 Merkle Root 并比对；篡改任一交易会导致路径上所有哈希变更，最终使当前区块头哈希不匹配，从而被网络拒绝。

回答要点
  1. 指出哈希指针链（前块哈希）与 Merkle Tree 双重保障
  2. 说明 Merkle Root 存储位置（区块头）及校验方式（重算比对）
  3. 解释篡改传播路径（单交易→路径哈希→Root→区块头）
  4. 强调全节点独立验证机制
完整解析（含追问与踩坑）→
8.ECDSA 加密的原理是什么？

ECDSA 不是加密算法，而是基于椭圆曲线的数字签名算法；它用私钥对消息哈希值生成签名（r,s），用公钥验证签名有效性；安全性依赖椭圆曲线离散对数难题，相比 RSA 在同等安全强度下密钥更短、计算更快。

回答要点
  1. 立即纠正‘ECDSA 加密’说法，明确其为签名算法
  2. 说明输入输出（私钥+hash→签名；公钥+签名+消息→验证结果）
  3. 指出核心数学难题（ECDLP）
  4. 对比 RSA 突出优势（密钥短、性能好）
完整解析（含追问与踩坑）→
9.每笔交易的签名和验签流程是怎样的？

签名：取交易原文（含 from/to/amount/timestamp）做 SHA256 哈希，用发送方私钥对哈希值执行 ECDSA_sign 得到 (r,s)；验签：接收方用发送方公钥、原始交易、(r,s) 调用 ECDSA_verify，返回 true 表示签名有效且交易未被篡改。

回答要点
  1. 明确签名对象是交易原文哈希（非明文）
  2. 写出签名输入三要素（私钥+哈希+曲线参数）
  3. 写出验签输入四要素（公钥+原文+ r + s）
  4. 强调验签结果是布尔值，用于后续共识过滤
完整解析（含追问与踩坑）→
10.GMP 模型。

G 是 goroutine，M 是 OS 线程，P 是调度器上下文。M 必须绑定 P 才能执行 G；P 维护本地运行队列，也会从全局队列或其它 P 偷任务；网络 I/O 由 netpoller 异步唤醒，系统调用阻塞时 P 会转交给空闲 M，避免线程闲置。

回答要点
  1. 清晰定义 G/M/P 三者角色及关系
  2. 说明 P 如何协调本地队列、全局队列和 work-stealing
  3. 指出 netpoller 和系统调用阻塞对 M/P 绑定的影响
完整解析（含追问与踩坑）→
11.进程、线程、协程有什么区别？
回答要点
  1. 进程是资源分配单位，有独立地址空间；线程是调度单位，共享进程资源
  2. 进程切换要换页表，开销最大；线程切换只换栈和寄存器，属内核态
  3. 协程是用户态调度，切换不陷入内核，成本最低
  4. 协程适合 IO 密集，线程适合 CPU 密集并行
完整解析（含追问与踩坑）→
12.输入一个URL到网页加载之间发生了什么？

  2. 浏览器解析HTML时的阻塞与异步行为
  3. 关键渲染路径中layout/paint/composite分工

13.TCP 为什么要四次挥手？如果省略第四次挥手，会有什么问题？

四次挥手因 TCP 全双工，双方需独立关闭发送方向。第一次 FIN 关 A→B 发送，第二次 ACK 确认，第三次 FIN 关 B→A 发送，第四次 ACK 确认。若省略第四次，B 不知 A 是否收到 FIN，可能重发 FIN，导致 A 无法进入 CLOSED，B 卡在 LAST_ACK，连接异常残留。

回答要点
  1. 说明全双工导致需双方独立关闭发送通道
  2. 准确描述四次交互中每次的发起方和含义
  3. 指出省略第四次会导致 B 卡在 LAST_ACK、A 无法释放资源
完整解析（含追问与踩坑）→
14.B+ 树相比 B 树的优势是什么？

B+ 树所有数据都在叶子节点，且叶子节点用链表相连；这带来两大优势：一是范围查询快，只需遍历链表；二是树更矮胖，IO 次数更少，因为非叶节点只存 key 不存 data，同样大小磁盘块能存更多分支。

回答要点
  1. 指出数据全在叶子节点（B 树数据可在内部节点）
  2. 强调叶子节点有序链表对范围查询的加速
  3. 说明非叶节点纯索引（无 data）带来的扇出提升
  4. 归结到 IO 效率（更少磁盘读）
完整解析（含追问与踩坑）→
15.MySQL的事务隔离级别有哪些？各自解决什么并发问题？

读未提交：啥都能读，脏读、不可重复读、幻读全有；读已提交：只能读已提交数据，解决脏读；可重复读：InnoDB默认，MVCC保证同一事务多次读同数据结果一致，解决脏读和不可重复读，但当前读仍可能幻读；串行化：强制排队执行，彻底解决所有问题但性能最差。

回答要点
  1. 四级名称与顺序正确
  2. 每级明确解决哪些问题（用‘解决/仍有’表述）
  3. 指出可重复读下‘当前读’仍幻读这一关键细节
