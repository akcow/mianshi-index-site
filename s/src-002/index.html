这一场问了什么

1.讲清楚 Agent 项目从用户输入到最终输出的全链路，每一环的输入输出分别是什么？
回答要点
  1. 用户输入 → 拼装上下文（system、历史、工具定义、记忆）→ 调模型
  2. 模型返回纯文本或 tool_call；tool_call 进参数校验 → 权限校验 → 执行（沙箱）→ 结果回灌
  3. 循环直到模型输出终止信号或触发 max_steps；最后一次输出做后处理返回用户
  4. 每一环能明确说出输入是什么、输出是什么、失败怎么处理
完整解析（含追问与踩坑）→
2.Agent 陷入死循环或反复调用同一工具，怎么检测和处理？
回答要点
  1. 检测：对（工具名 + 参数）做指纹，连续重复 N 次即判定；也可用状态哈希比对
  2. 原因：工具返回值没有提供有效信号、错误信息太模糊、任务本身无解、prompt 缺少退出指引
  3. 处理：注入反思提示、切换策略、熔断并人工介入、回退到上一个成功状态
  4. 根治：让工具返回结构化错误码，prompt 里明确「同一工具失败两次就换方案」
完整解析（含追问与踩坑）→
3.如何避免上下文压缩之后，模型忘记用户之前提出的重要需求？
回答要点
  1. 把用户约束单独抽成结构化字段（requirements），每次请求都带上，不参与压缩
  2. 压缩时用固定模板强制包含约束段
  3. 在系统提示里重申当前目标清单
  4. 加校验：输出前检查是否违反已知约束
完整解析（含追问与踩坑）→
4.Multi-Agent 系统中，不同 Agent 之间应该怎么划分职责，任务怎么拆分？
回答要点
  1. 按能力边界拆（检索、编码、审核）而非按步骤流水拆
  2. 拆分的判据：子任务是否可独立验证、是否需要不同工具集或不同模型
  3. 要有明确的输入输出契约，否则接口处会大量信息丢失
  4. 别为了多 Agent 而多 Agent，单 Agent 能解决就别拆
完整解析（含追问与踩坑）→
5.多个 Agent 并发修改同一个文件或资源，怎么防冲突，锁粒度怎么定？
回答要点
  1. 乐观锁：文件版本号 / 内容哈希，提交时版本不符则拒绝并重试
  2. 悲观锁：按文件路径加锁，但要处理死锁和锁超时
  3. 锁粒度：单文件 > 目录 > 仓库。粒度越细并发越高，但锁管理越复杂
  4. 更好的思路是序列化写：让所有写入经过单一写入队列，Agent 只提变更意图
完整解析（含追问与踩坑）→
6.Agent 执行到一半服务重启，checkpoint 存什么、放哪、怎么恢复现场？
回答要点
  1. 存什么：任务目标、已完成步骤、当前状态、工具调用历史摘要、待执行队列
  2. 放哪：外部持久化（DB 或对象存储），不能放进程内存
  3. 怎么恢复：幂等化每一步，重放时跳过已完成；不确定是否完成的步骤要能查询外部副作用
  4. 关键是工具的副作用必须幂等或可探测，否则重试会重复下单/重复发送
完整解析（含追问与踩坑）→
7.human-in-the-loop 场景下，用户驳回或超时，任务怎么续跑和兜底？
回答要点
  1. 任务挂起时持久化完整状态，等待外部事件（批准/驳回/超时）
  2. 驳回要带上理由，作为新约束回灌给模型重新规划，而不是从头再来
  3. 超时按预设策略处理：自动驳回、降级执行、或转人工
  4. 要有幂等的续跑入口，避免重复审批
完整解析（含追问与踩坑）→
8.工具调用失败时怎么做重试、熔断，怎么保证幂等？
回答要点
  1. 区分可重试错误（超时、5xx）与不可重试错误（4xx、参数非法）
  2. 退避重试 + 上限次数，失败信息要结构化回灌让模型换策略
  3. 熔断：连续失败达阈值直接短路，避免拖垮整个 loop
  4. 幂等：写操作带幂等键，让重复执行不产生重复副作用
完整解析（含追问与踩坑）→
9.Agent 拥有大量工具时，怎么避免工具描述导致 Prompt 过长？
回答要点
  1. 工具检索：按 query 语义召回 top-k 工具，只注入相关的
  2. 分层：先给工具分类目录，模型选定类目再加载该类目下的工具
  3. 按需加载（MCP 的 tools/list 分页或按 server 粒度挂载）
  4. 精简描述：每个工具描述控制在必要信息内，长文档移到工具返回里
完整解析（含追问与踩坑）→
10.RAG 在 Agent 里什么时机触发检索，query 改写和 rerank 怎么接？
回答要点
  1. 触发时机：模型主动决定（把检索做成工具）、规则触发（命中知识域关键词）、或每轮前置
  2. query 改写：结合对话历史把省略指代补全，拆成多个子查询并行检索
  3. rerank：粗排向量召回 top-50，再用交叉编码器精排 top-5
  4. 检索结果要带来源，便于引用和后续校验
完整解析（含追问与踩坑）→
11.Prompt 注入怎么防，危险工具调用怎么拦截，敏感数据怎么脱敏？
回答要点
  1. 注入面：用户输入、工具返回内容（间接注入）、检索到的文档
  2. 防注入：把外部内容标记为不可信数据、指令与数据分离、输出侧校验
  3. 危险工具：分级授权 + 白名单 + 人工确认 + 参数合法性校验
  4. 脱敏：入口正则/模型识别敏感字段，出口再做一次过滤
完整解析（含追问与踩坑）→
12.Agent 线上怎么评测？任务成功率、工具选择率、参数错误率、成本和耗时怎么埋点？
回答要点
  1. 分层指标：端到端（任务成功率、平均轮数、P95 耗时、单任务成本）与组件级（工具选择准确率、参数合法率、检索召回率）
  2. 要有可判定的成功标准，否则成功率无从算起——先定义任务完成的判定条件
  3. 埋点在每一步工具调用上，记录入参、出参、耗时、token 数、是否重试
  4. 离线用固定回归集，线上用采样加人工标注，两者对不上就说明分布漂移
完整解析（含追问与踩坑）→
13.badcase 怎么归因到模型、prompt、检索还是工具，怎么回流成回归集？
回答要点
  1. 归因方法：逐步回放轨迹，定位第一个错误步骤，看是决策错还是执行错
  2. 决策错 → 看 prompt 和上下文是否缺信息；执行错 → 看工具参数和返回
  3. 建立错误分类标签，统计分布才知道该修哪
  4. 回流：把复现输入固化成回归用例，修完后跑全量回归防退化
完整解析（含追问与踩坑）→
14.给一个带 parent_id 的扁平 JSON 列表，还原成树形结构并返回根节点列表。
回答要点
  1. 先遍历一遍建 id → node 的哈希表
  2. 再遍历一遍挂接父子关系，parent_id 不存在或为空的作为根
  3. O(n) 时间复杂度，注意节点乱序和孤儿节点
