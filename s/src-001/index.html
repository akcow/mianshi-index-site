这一场问了什么

1.平时自己做小项目吗？
回答要点
  1. 哪怕很小也要有，说明动机和解决的真实问题
  2. 能说出用了什么技术、踩了什么坑
完整解析（含追问与踩坑）→
2.在你的 Agent 项目里，模型负责哪些功能？除了模型之外还有哪些部分？
回答要点
  1. 模型只负责决策：下一步做什么、调哪个工具、传什么参数
  2. 模型之外：编排循环、工具注册与执行、上下文管理、记忆存储、权限与沙箱、日志与评测
  3. 能说清各模块边界和交互方式
完整解析（含追问与踩坑）→
3.相比直接在 ChatGPT 里聊，你的 Agent 多了哪些步骤和特有能力？
回答要点
  1. 多了工具调用、状态持久化、多轮规划、可观测与回放
  2. ChatGPT 也有工具，差异在你对工具链、记忆、评测有控制权
  3. 能说出自己项目的具体增量，而不是泛泛而谈
完整解析（含追问与踩坑）→
4.讲清楚 Agent 项目从用户输入到最终输出的全链路，每一环的输入输出分别是什么？
回答要点
  1. 用户输入 → 拼装上下文（system、历史、工具定义、记忆）→ 调模型
  2. 模型返回纯文本或 tool_call；tool_call 进参数校验 → 权限校验 → 执行（沙箱）→ 结果回灌
  3. 循环直到模型输出终止信号或触发 max_steps；最后一次输出做后处理返回用户
  4. 每一环能明确说出输入是什么、输出是什么、失败怎么处理
完整解析（含追问与踩坑）→
5.Agent 执行到一半服务重启，checkpoint 存什么、放哪、怎么恢复现场？
回答要点
  1. 存什么：任务目标、已完成步骤、当前状态、工具调用历史摘要、待执行队列
  2. 放哪：外部持久化（DB 或对象存储），不能放进程内存
  3. 怎么恢复：幂等化每一步，重放时跳过已完成；不确定是否完成的步骤要能查询外部副作用
  4. 关键是工具的副作用必须幂等或可探测，否则重试会重复下单/重复发送
完整解析（含追问与踩坑）→
6.MySQL 索引的底层原理是什么，它解决了什么问题？

先开slow_query_log，设long_query_time阈值；用mysqldumpslow或pt-query-digest分析日志找TOP SQL；再explain看执行计划，重点看type、rows、key、Extra；最后结合索引、SQL写法、数据量做针对性优化，比如加索引、改JOIN顺序、拆分大事务。

回答要点
  1. InnoDB 用 B+ 树：非叶子节点只存键，叶子节点存数据且用链表相连
  2. B+ 树矮胖，三层能存千万级数据，把随机 IO 压到 2-3 次
  3. 相比全表扫描 O(n)，索引把查找降到 O(log n)
  4. 叶子链表支持范围查询和排序，这是 B+ 树相对 B 树的关键优势
完整解析（含追问与踩坑）→
7.Agent 线上怎么评测？任务成功率、工具选择率、参数错误率、成本和耗时怎么埋点？
回答要点
  1. 分层指标：端到端（任务成功率、平均轮数、P95 耗时、单任务成本）与组件级（工具选择准确率、参数合法率、检索召回率）
  2. 要有可判定的成功标准，否则成功率无从算起——先定义任务完成的判定条件
  3. 埋点在每一步工具调用上，记录入参、出参、耗时、token 数、是否重试
  4. 离线用固定回归集，线上用采样加人工标注，两者对不上就说明分布漂移
完整解析（含追问与踩坑）→
8.AI 生成的代码不是你想要的，你怎么办？有什么提效方式？
回答要点
  1. 先定位是「需求没说清」还是「AI 理解偏了」，前者补上下文，后者给反例
  2. 把任务拆小，一次只改一个点
  3. 用具体产物约束：给接口签名、给已有代码片段、给测试用例
  4. 不满意就回退重来，不要在错误输出上反复修补
完整解析（含追问与踩坑）→
9.三数之和（先说思路再写代码）
回答要点

  2. O(n²) 复杂度，去重要在三个位置都处理
  3. 先说思路再落笔，这是面试官明确要求的
