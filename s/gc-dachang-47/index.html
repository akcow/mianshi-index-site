一面 未标注 GoClub 互联网 8 道题 2026-11-09

这一场问了什么

1.你的 Agent 有统计过 token 的消耗量吗？

我确实在 Agent 中加了 token 统计，用的是 OpenAI 的 tiktoken 库预估输入输出长度，再结合 API 返回的 usage 字段做双校验；关键是在每个工具调用和 LLM 调用节点埋点，聚合到 trace ID 下，方便按会话、用户、场景维度分析超支原因。

回答要点
  1. 明确使用了预估+返回双校验机制
  2. 说明埋点粒度（工具/LLM 调用级）
  3. 指出聚合维度（trace ID/会话/用户）
完整解析（含追问与踩坑）→
2.MCP、Skills 概念

MCP 是 Model Control Protocol，是 Agent 与外部工具交互的标准协议，定义了请求格式、认证和错误码；Skills 指可插拔的原子能力单元，比如查天气、发邮件，每个 Skill 封装了具体实现和 MCP 接口适配器，让 Agent 不用关心底层细节。

回答要点
  1. MCP 是标准化通信协议（非框架或库）
  2. Skills 是封装了实现+适配器的原子能力单元
  3. 强调 Skills 的可插拔性和解耦价值
完整解析（含追问与踩坑）→
3.分布式系统 CAP 的概念

CAP 指一致性（C）、可用性（A）、分区容错性（P）三者不可兼得，最多满足其中两个；注意它说的是在网络分区发生时的权衡，不是日常状态下的取舍；比如 ZooKeeper 选 CP，Eureka 选 AP。

回答要点
  1. 明确定义 C/A/P 各自含义
  2. 强调前提条件是‘网络分区发生时’
  3. 举出一个 CP 和一个 AP 的典型系统例子
完整解析（含追问与踩坑）→
4.数据库，为什么选 PostgreSQL，PostgreSQL 和 MySQL 的区别

我选 PostgreSQL 主要是它原生支持 JSONB 和全文检索，我们业务有大量半结构化日志查询；另外它的 MVCC 实现更彻底，长事务不会阻塞读；和 MySQL 比，PG 的外键约束更严格，但主从同步延迟略高，且生态工具链不如 MySQL 丰富。

回答要点
  1. 给出至少一个具体业务场景驱动选型（如 JSONB/全文检索）
  2. 指出 PG 在 MVCC 或事务隔离上的实质优势
  3. 对比时包含至少一项 MySQL 的优势（如生态）
完整解析（含追问与踩坑）→
5.介绍一下 PostgreSQL 事务方面 ACID 是怎么保证的

A（原子性）靠 WAL 日志保证崩溃恢复；C（一致性）由约束、触发器和应用逻辑共同保障；I（隔离性）通过 MVCC + 行级锁实现，快照隔离避免脏读幻读；D（持久性）依赖 WAL 写入磁盘并 fsync。重点是 WAL 和 MVCC 如何配合：写操作先记日志再改数据页，读操作基于事务快照访问历史版本。

回答要点
  1. WAL 对应原子性和持久性
  2. MVCC + 快照机制对应隔离性
  3. 明确一致性需约束+应用协同
完整解析（含追问与踩坑）→
6.为什么考虑只用 Redis 做消息队列，为什么不用 Kafka

我们内部小规模任务调度用 Redis List+BRPOP，因为开发快、延迟低、运维简单；但明确不用于订单、支付等核心链路——Kafka 的磁盘持久化、副本机制、精确一次语义才是刚需。选 Redis 是接受‘可能丢少量非关键任务’换迭代速度，不是技术上更优。

回答要点
  1. 区分场景（小任务 vs 核心链路）
  2. 指出 Kafka 的不可替代性（持久化/副本/精确一次）
  3. 承认 Redis MQ 的本质妥协（非关键任务容忍丢失）
完整解析（含追问与踩坑）→
7.Redis 了解热点 key 的方法，一般用什么方式缓解 Redis 的热度压力

先用 redis-cli –hotkeys 或 monitor + slowlog 定位，再用 client list 查连接分布；缓解分三层：客户端本地缓存（如 Guava Cache）挡第一波，服务端加二级缓存（如 Caffeine），最后对 key 做散列（user:123 → user:123:shard0）打散压力。

回答要点
  1. 至少两种定位手段（hotkeys/monitor/slowlog）
  2. 分层缓解策略（客户端缓存→二级缓存→key 散列）
  3. 明确每层作用（如本地缓存挡穿透）
完整解析（含追问与踩坑）→
8.介绍 Redis 主从同步的机制

主从同步分两步：首次全量用 RDB 快照，主库 bgsave 生成 rdb 文件传给从库，从库清空内存加载；增量靠 repl_backlog 缓冲区，主库把写命令写入缓冲区，从库通过 offset 断点续传。关键点是 repl_backlog 是环形缓冲区，大小决定从库断连多久能追上。

回答要点
  1. 全量同步含 bgsave + rdb 传输 + 从库加载
  2. 增量同步依赖 repl_backlog 环形缓冲区
  3. 说明 repl_backlog size 决定断连恢复窗口
完整解析（含追问与踩坑）→
