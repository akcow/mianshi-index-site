这一场问了什么

1.消息队列如何保证消息不丢失？如何保证消息至少被消费一次？

发端要确认 broker 接收成功，比如 Kafka 要 ack=all；broker 端要持久化到磁盘+副本同步；消费端要手动提交 offset，且必须在业务逻辑执行成功后才提交，避免重复消费或丢消息。

回答要点
  1. 生产者端 ack 机制与重试策略
  2. Broker 端持久化与多副本同步
  3. 消费者端手动 commit offset 的时机控制
完整解析（含追问与踩坑）→
2.点击短信短链后跳转成长链，这个短链服务如何设计？

短链用哈希+自增ID生成，存 Redis 做缓存，DB 做持久化；跳转时先查 Redis，命中直接 302；未命中查 DB 并回填 Redis；加布隆过滤器防缓存穿透；短链带签名防恶意构造。

回答要点
  1. 短链生成策略（不可预测+唯一性）
  2. 跳转链路的缓存-数据库双写一致性
  3. 防穿透/防刷/防滥用措施
完整解析（含追问与踩坑）→
3.定时任务和延迟任务发布后，如何保证其正确执行？

用时间轮+Redis ZSet 或 XXL-JOB 这类调度中心；任务注册时存 DB + 设置状态为 pending；执行前先 CAS 更新为 running；成功后更新为 done；失败走重试+死信队列；所有状态变更打日志并告警。

回答要点
  1. 任务状态机设计与数据库事务/乐观锁保障
  2. 执行过程中的幂等控制（如唯一业务 ID + 去重表）
  3. 失败后的重试策略、死信处理与人工介入通道
完整解析（含追问与踩坑）→
4.用栈模拟队列

用两个栈：push 时全进 inStack；pop 或 peek 时，若 outStack 为空，就把 inStack 全部倒出到 outStack，再操作 outStack；这样均摊时间复杂度是 O(1)。

回答要点
  1. 明确区分 inStack 和 outStack 的职责
  2. outStack 为空时才触发倒数据，避免重复搬运
  3. 正确实现 push/pop/peek 三个接口并处理空队列异常
完整解析（含追问与踩坑）→
