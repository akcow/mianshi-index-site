1.第一个 PR 修复了什么问题？

我第一个 PR 是修复登录态校验的并发空指针异常：用户高频刷新时，session 对象被提前释放但校验逻辑未判空。我加了 nil 检查和单元测试覆盖，并用压测验证了 500 QPS 下不再 panic。

回答要点
  1. 明确说出具体问题现象（如空指针/数据不一致）
  2. 说明根因（非表面描述，如‘没判空’而非‘代码有 bug’）
  3. 交代验证方式（压测/日志/监控等）
完整解析（含追问与踩坑）→
2.SQLite 数据库有了解吗？

SQLite 是单文件嵌入式数据库，不依赖服务进程，适合移动端或配置管理这类低并发场景。但它不支持多写并发，也没用户权限体系，所以绝不能用在高流量 Web 后端主库。

回答要点
  1. 点明‘无服务进程、单文件’本质
  2. 说出典型适用场景（如移动端、本地工具）
  3. 指出关键限制（无并发写、无用户权限、无网络访问）
完整解析（含追问与踩坑）→
3.用的什么数据库比较多？

我们核心交易链路用 MySQL，因为强一致性+成熟运维；用户行为日志用 ClickHouse，靠列存压缩和向量化加速分析；实时推荐缓存用 Redis ZSet 做热度排序——选型全看读写模式、一致性要求和查询特征，不是凭喜好。

回答要点
  1. 至少给出两个数据库并匹配不同业务场景
  2. 每个选择都关联明确技术动因（如‘ClickHouse 列存适合聚合分析’）
  3. 体现取舍意识（如‘放弃强事务换性能’）
完整解析（含追问与踩坑）→
4.MySQL 性能调优

先看慢查询日志定位瓶颈 SQL，用 EXPLAIN 看执行计划——重点查是否走索引、有没有回表；再检查索引设计，比如联合索引是否满足最左前缀；然后看 buffer pool 大小和刷脏策略；最后才是分库分表，那已经是架构级方案了，不能一上来就提。

回答要点
  1. 按优先级分层：SQL → 索引 → 配置 → 架构
  2. EXPLAIN 必须能解读 key、rows、Extra 字段含义
  3. 强调索引失效场景（如 like '%abc'、函数包裹字段）
完整解析（含追问与踩坑）→
5.数据库事务四大特性。

ACID：A 是原子性，事务要么全成功要么全回滚；C 是一致性，事务前后数据满足约束规则；I 是隔离性，多个事务并发执行互不干扰，靠 MVCC 或锁实现；D 是持久性，提交后数据落盘，崩溃也不丢。

回答要点
  1. 逐字准确说出 ACID 四词及对应中文
  2. 对每个特性能用一句话解释本质（非定义复读）
  3. 能指出隔离性是通过 MVCC 或锁机制实现
完整解析（含追问与踩坑）→
6.Redis 里面有哪些数据类型，分别适合什么场景？

String 适合做缓存、计数器、分布式锁；Hash 存对象字段比如用户信息；List 当简单队列或消息广播；Set 做去重、标签系统、共同关注；ZSet 搞排行榜、延时队列、按分数排序查询。还用过 Bitmap 做日活统计，HyperLogLog 估 UV。

回答要点
  1. 准确说出 5 种基础类型（String/Hash/List/Set/ZSet）及其典型场景
  2. 至少补充 1 种扩展结构（Bitmap/HyperLogLog/Stream）及用途
  3. 能区分 List 和 ZSet 在排序需求上的本质差异
完整解析（含追问与踩坑）→
7.zset的底层数据结构是什么样的？

zset同时用跳表（skiplist）和哈希表（dict）实现：跳表提供O(logN)范围查询和排序，哈希表提供O(1)按member查score；两者数据冗余但各司其职；小集合（≤128个元素且每个member≤64字节）用压缩列表ziplist优化内存。

回答要点
  1. 双结构共存目的（查score快 vs 查member快）
  2. 跳表层级随机生成与查询路径
  3. ziplist何时升级为skiplist/dict
完整解析（含追问与踩坑）→
8.单线程 IO 模型是怎么样的？

Redis 主线程用 epoll 监听所有 socket，事件就绪后放入队列，再顺序执行命令。单线程避免了锁竞争和上下文切换，所有命令天然串行，所以不需要考虑并发安全——这才是它快的关键，不是单纯‘没线程’。

回答要点
  1. 点明 I/O 多路复用（epoll/kqueue）是核心
  2. 说明事件循环流程（监听→就绪→入队→执行）
  3. 强调单线程带来命令原子性和零锁开销
完整解析（含追问与踩坑）→
9.Redis 怎么保证原子性？通过什么操作保证原子性？

单条命令天然原子，因为单线程串行执行；多命令要用 Lua 脚本或 MULTI/EXEC 事务包起来。注意 Pipeline 只是批量发包，每条仍独立执行，不保证原子性——这点面试常踩坑。

回答要点
  1. 明确单命令原子性源于单线程模型
  2. 指出 Lua 脚本和事务是两种多命令原子方案
  3. 强调 Pipeline 不提供原子性
完整解析（含追问与踩坑）→
10.GMP 模型。

G 是 goroutine，M 是 OS 线程，P 是调度器上下文。M 必须绑定 P 才能执行 G；P 维护本地运行队列，也会从全局队列或其它 P 偷任务；网络 I/O 由 netpoller 异步唤醒，系统调用阻塞时 P 会转交给空闲 M，避免线程闲置。

回答要点
  1. 清晰定义 G/M/P 三者角色及关系
  2. 说明 P 如何协调本地队列、全局队列和 work-stealing
  3. 指出 netpoller 和系统调用阻塞对 M/P 绑定的影响
完整解析（含追问与踩坑）→
11.Channel 无缓存和有缓存有什么区别？分别在什么情况下使用？

无缓存 channel 是同步的，发送方必须等到接收方就绪才返回，适合任务交接、信号通知、强背压控制；有缓存 channel 是异步的，发送方写入缓冲区就返回，适合解耦生产消费、削峰填谷、worker pool 任务分发。

回答要点
  1. 明确区分同步 vs 异步行为本质
  2. 各举一个典型使用场景（非教科书式）
  3. 能说明缓冲区大小设置不当的风险（如过大导致内存积压）
完整解析（含追问与踩坑）→
12.B 分支 merge A 分支的代码出现了问题怎么做？回滚命令

如果还没 push，直接 git reset –hard HEAD~1 回退；如果已推送到远端，必须用 git revert -m 1 生成反向提交，避免污染他人历史。遇到冲突先 git merge –abort，别硬 commit。

回答要点
  1. 区分未 push（reset）与已 push（revert）两种策略
  2. 写出正确 revert 命令含 -m 1 参数
  3. 说明冲突时 abort 的必要性
完整解析（含追问与踩坑）→
13.Git 查看提交记录

用 git log –oneline –graph –all 看分支拓扑；加 –author=‘xxx’ 查某人提交；–since=‘2 weeks ago’ 筛时间范围；如果想查某文件修改历史，加 -p path/to/file ——这些组合能快速定位引入 bug 的那次提交。

回答要点
  1. 至少写出三个实用参数组合（如 --oneline + --graph）
  2. 说明 --author 和 --since 的实际调试价值
  3. 提到 -p 查看某文件变更内容
完整解析（含追问与踩坑）→
14.Git 暂存

用 git stash save ‘wip: 登录接口重构’ 暂存当前修改；切分支修 bug 后，用 git stash pop 恢复；如果 pop 冲突，用 git stash apply 先应用再手动解冲突。stash list 能看到所有暂存，drop 清理不用的。

回答要点
  1. 写出完整 stash/save/pop 流程
  2. 说明 save 加描述信息的必要性
  3. 指出 apply 与 pop 在冲突处理上的差异
