这一场问了什么

1.进程的调度方法有哪些？不同调度方法分别适合什么场景？

常见调度算法有先来先服务FCFS、短作业优先SJF、时间片轮转RR、优先级调度、多级反馈队列。FCFS适合批处理，RR适合分时系统，多级反馈队列兼顾响应与吞吐，能动态调整优先级。

回答要点
  1. 准确列出5种以上主流调度算法
  2. 明确区分抢占式与非抢占式（如RR抢占、FCFS非抢占）
  3. 为至少3种算法匹配典型适用场景（如RR用于交互式系统）
完整解析（含追问与踩坑）→
2.线程调度的开销主要由哪几部分组成？

主要是三块：CPU寄存器保存与恢复、内核栈切换、TLB缓存刷新。其中TLB刷新在跨地址空间时最重，但同进程线程切换不涉及页表切换，所以比进程切换轻得多。

回答要点
  1. 明确指出寄存器保存/恢复是基础开销
  2. 识别出内核栈切换的必要性
  3. 强调TLB失效对性能的影响，尤其对比进程切换
完整解析（含追问与踩坑）→
3.操作系统的 I/O 模型有哪些？

五种：阻塞I/O、非阻塞I/O、I/O复用（select/poll/epoll）、信号驱动I/O、异步I/O。Linux下前四种是同步I/O，只有POSIX AIO或io_uring才算真正异步。

回答要点
  1. 完整说出5种模型名称
  2. 明确区分同步I/O与异步I/O的本质差异（是否内核完成数据拷贝）
  3. 指出epoll属于I/O复用而非异步
完整解析（含追问与踩坑）→
4.讲一下阻塞 I/O 和非阻塞 I/O。

阻塞I/O调用后线程挂起，直到数据就绪并拷贝完成才返回；非阻塞I/O立即返回，若数据未就绪则返回EAGAIN/EWOULDBLOCK错误，需轮询重试。本质区别在于用户线程是否被内核挂起。

回答要点
  1. 清晰定义两者返回时机和线程状态
  2. 准确写出非阻塞失败时的典型错误码
  3. 点明非阻塞必须配合轮询或事件通知使用
完整解析（含追问与踩坑）→
5.为什么不能一下开上万个线程？

每线程默认占1MB栈空间，万线程就是10GB内存；还有内核TCB开销、上下文切换雪崩、锁竞争加剧。Linux默认ulimit -u限制进程线程数，且调度器在超千级线程时性能断崖下降。

回答要点
  1. 量化栈内存消耗（如x86-64默认1MB）
  2. 指出内核线程控制块TCB的额外开销
  3. 说明调度器在大量线程下的O(n)扫描瓶颈
完整解析（含追问与踩坑）→
6.TCP是怎么保证可靠传输的？

TCP靠八种机制协同保障可靠：序列号确保字节流有序；ACK确认应答反馈接收状态；超时重传应对丢包；快速重传加速丢包恢复；滑动窗口提升吞吐；流量控制防接收方溢出；拥塞控制适配网络状况；校验和检测传输错误。其中前四条解决‘传得准’，后四条解决‘传得稳’和‘传得快’。

回答要点
  1. 覆盖序列号、ACK、重传（含超时+快速）、滑动窗口
  2. 区分流量控制（接收方能力）和拥塞控制（网络状态）
  3. 强调校验和防错
  4. 指出机制间的协作关系
完整解析（含追问与踩坑）→
7.流量控制和拥塞控制的区别是什么？

流量控制是点对点的，接收方通过窗口字段告诉发送方‘我还能收多少’，防接收方缓冲区溢出；拥塞控制是全局的，发送方通过慢启动、拥塞避免等算法感知网络状况，防路由器队列过载。前者看接收方能力，后者看网络链路状态。

回答要点
  1. 明确流量控制主体是接收方，拥塞控制主体是发送方
  2. 指出流量控制依赖rwnd字段，拥塞控制依赖cwnd计算
  3. 区分二者目标：防接收方溢出 vs 防网络中间节点拥塞
完整解析（含追问与踩坑）→
8.为什么 MySQL 使用 B+ 树？

B+树所有数据在叶子节点且有序链表连接，范围查询快；非叶子节点只存键，扇出更高，树更矮，IO次数少；叶子节点顺序存储利于磁盘预读。相比B树，B+树更适合MySQL这种以范围查询和磁盘IO为主的场景。

回答要点
  1. 指出B+树叶子节点有序链表对范围查询的加速
  2. 说明非叶子节点无数据带来的更高扇出和更矮树高
  3. 强调顺序存储对磁盘预读的友好性
完整解析（含追问与踩坑）→
9.索引有哪些类型？覆盖索引是什么？

类型有主键、唯一、普通、全文、空间索引。覆盖索引指查询所需所有字段都包含在索引中，无需回表。比如联合索引(a,b,c)，查SELECT a,b WHERE a=1，就能直接从索引获取全部数据。

回答要点
  1. 准确列举5种索引类型
  2. 明确定义覆盖索引为‘索引包含查询所有列’
  3. 给出符合覆盖索引定义的具体SQL示例
完整解析（含追问与踩坑）→
10.联合索引 abc 查询 bc 能不能走索引？

不能。联合索引abc遵循最左前缀原则，查询条件必须从a开始。bc没有a，无法利用索引的有序性，会全表扫描。除非改写为SELECT * FROM t WHERE a>0 AND b=1 AND c=2，才能用上。

回答要点
  1. 明确回答‘不能’并引用最左前缀原则
  2. 指出缺失最左列a导致无法定位索引范围
  3. 给出能走索引的等价改写方式（如加a条件）
完整解析（含追问与踩坑）→
11.索引失效的常见情况有哪些？

六种典型失效：对索引列做函数操作（如WHERE YEAR(create_time)=2023）；使用!=或NOT IN；LIKE以%开头；OR连接非索引列；隐式类型转换；联合索引跳过最左列。本质都是破坏了索引的有序性或范围扫描能力。

回答要点
  1. 准确列出至少4种失效场景
  2. 为每种场景配一个典型SQL反例
  3. 统一归因到‘破坏有序性/范围扫描’这一本质
完整解析（含追问与踩坑）→
12.怎么看一条 SQL 的执行计划？需要重点关注哪些字段？

用EXPLAIN FORMAT=TREE或EXPLAIN ANALYZE执行SQL。重点看type（最好到range或ref）、rows（预估扫描行数）、key（实际使用的索引）、Extra（警惕Using filesort/Using temporary）。如果type是ALL或rows远超实际结果数，说明索引没用好。

回答要点
  1. 写出标准命令EXPLAIN [FORMAT=TREE] SELECT...
  2. 指出type、rows、key、Extra四个必看字段
  3. 说明各字段的健康阈值（如type≠ALL，rows接近实际）
完整解析（含追问与踩坑）→
13.LLM 的幻觉是什么？

幻觉是指模型生成看似合理但事实错误、逻辑矛盾或毫无依据的内容，比如编造不存在的论文、虚构API参数、捏造历史事件。它源于统计模式匹配而非真实知识存储，训练数据噪声和解码策略会加剧该问题。

回答要点
  1. 明确定义为‘虚假但自信的输出’
  2. 给出技术层面原因（统计建模+缺乏事实核查）
  3. 举出1个具体、可验证的错误示例（如虚构作者名）
完整解析（含追问与踩坑）→
14.怎么解决或者缓解幻觉？

三层策略：输入层用RAG引入可信源；模型层用Self-Check prompting让模型质疑自身输出；输出层加事实核查模块，比如调用维基API验证实体。没有银弹，必须组合使用，且RAG效果高度依赖检索质量。

回答要点
  1. 提出至少2个不同层级的缓解手段（输入/模型/输出）
  2. 指出RAG不是万能，其效果受限于检索召回率
  3. 强调需验证环节而非仅依赖模型自省
完整解析（含追问与踩坑）→
15.AI Coding 场景题：给了一段几行代码，内容是对所有 user_ids 执行一条 update。这个实现的风险点是什么？

三大风险：一是单条SQL拼接百万ID导致SQL超长报错；二是事务锁住全表或大量行，阻塞其他业务；三是OOM——JDBC加载全部结果到内存。正确做法是分批（如1000条/批）、加事务粒度控制、用PreparedStatement防注入。

回答要点
  1. 指出SQL长度超限（max_allowed_packet）
  2. 说明行锁升级为表锁或长事务阻塞风险
  3. 识别内存溢出隐患（ResultSet全量加载）
完整解析（含追问与踩坑）→
16.AI Coding 场景题：如果 user_ids 是百万级，并且更新的值是负数，会怎么样？

负数本身无问题，但若字段有CHECK约束（如balance >= 0），会批量报错中断；更危险的是，若业务逻辑要求负数触发补偿流程，单次百万更新会让补偿服务瞬间过载甚至雪崩。必须前置校验+分批+异步化补偿。

回答要点
  1. 意识到CHECK约束导致批量失败
  2. 指出负数可能激活下游强耦合业务逻辑
  3. 强调需隔离补偿流程，避免同步阻塞主更新
完整解析（含追问与踩坑）→
17.AI Coding 场景题：怎么把它做成一个更工程化的版本？

四步改造：1. 分片：按user_id哈希分100批；2. 异步：用消息队列投递批次任务；3. 监控：记录每批成功数/失败ID/耗时；4. 回滚：保留原始ID快照，失败时可重试或人工介入。核心是‘可观察、可中断、可补偿’。

回答要点
  1. 提出分片+异步+监控+回滚四要素
  2. 说明分片依据（如哈希而非顺序，防热点）
  3. 强调失败ID需落库便于人工排查
完整解析（含追问与踩坑）→
