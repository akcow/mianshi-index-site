数据结构 4 题

Redis 里面有哪些数据类型，分别适合什么场景？

String 适合做缓存、计数器、分布式锁；Hash 存对象字段比如用户信息；List 当简单队列或消息广播；Set 做去重、标签系统、共同关注；ZSet 搞排行榜、延时队列、按分数排序查询。还用过 Bitmap 做日活统计，HyperLogLog 估 UV。

回答要点
  1. 准确说出 5 种基础类型（String/Hash/List/Set/ZSet）及其典型场景
  2. 至少补充 1 种扩展结构（Bitmap/HyperLogLog/Stream）及用途
  3. 能区分 List 和 ZSet 在排序需求上的本质差异

zset的底层数据结构是什么样的？

zset同时用跳表（skiplist）和哈希表（dict）实现：跳表提供O(logN)范围查询和排序，哈希表提供O(1)按member查score；两者数据冗余但各司其职；小集合（≤128个元素且每个member≤64字节）用压缩列表ziplist优化内存。

回答要点
  1. 双结构共存目的（查score快 vs 查member快）
  2. 跳表层级随机生成与查询路径
  3. ziplist何时升级为skiplist/dict

Redis 存储一个商品的各项信息，应该使用什么数据结构？

商品各项信息是键值对形式的结构化数据，比如 name、price、stock，推荐用 Hash：单 key 存多字段，内存紧凑，支持原子性增删改查单个字段，也方便整体读取。String 虽然能存 JSON，但没法局部更新；其他结构更不匹配。

回答要点
  1. 明确选择 Hash
  2. 说明 Hash 支持字段级操作
  3. 指出 String 存 JSON 的缺陷（无法局部更新）

Redis 里面的自增命令是哪个。

String 类型用 INCR key 或 INCRBY key step；Hash 字段用 HINCRBY key field step；浮点数用 INCRBYFLOAT 或 HINCRBYFLOAT。注意 INCR 只支持整数，且 key 不存在时自动初始化为 0。

  2. 说明 key 不存在时的默认行为
  3. 指出 INCR 仅支持整数

线程模型与内存 2 题

Redis 内存淘汰策略有哪些？

共 8 种，常用的是 volatile-lru、allkeys-lru、volatile-ttl、noeviction。重点区别在于：volatil-* 只淘汰带过期时间的 key，allkeys-* 淘汰所有 key；lru 是最近最少使用，ttl 是剩余时间最短，noeviction 则直接报错不淘汰。

回答要点
  1. 至少列出 4 种策略名称
  2. 区分 volatile- 和 allkeys- 前缀含义
  3. 说明 noeviction 的行为
完整解析（含追问与踩坑）→
Redis 是单线程的，为什么还这么快？
回答要点
  1. 纯内存操作，没有磁盘 IO 瓶颈
  2. 单线程避免了锁竞争和线程切换开销
  3. IO 多路复用（epoll）让单线程处理大量连接
  4. 高效数据结构（SDS、跳表、ziplist/listpack、渐进式 rehash）
  5. 注意：Redis 6.0 起网络 IO 是多线程的，命令执行仍是单线程

事务、原子性与锁 3 题

在 Redis 里面有没有应用过分布式锁？怎么使用 Redis 实现分布式锁？

我用 SET key token NX PX 过期时间实现加锁，保证原子写入和自动过期；解锁时用 Lua 脚本先校验 token 再删 key，避免误删别人锁；还加了超时重试和看门狗续期机制，防止业务卡住导致锁失效。

回答要点
  1. 加锁必须原子：SET + NX + PX
  2. 解锁必须原子且防误删：Lua 校验 token 后删除
  3. 必须设合理过期时间，且有续期或业务超时兜底
完整解析（含追问与踩坑）→
Redis 事务和 MySQL 事务有什么区别？

Redis 事务只是命令打包+顺序执行，不支持回滚、无隔离级别、无 ACID 中的 A 和 I；MySQL 事务基于 WAL 和 MVCC，支持原子性、一致性、隔离性、持久性，能回滚、有锁机制和隔离级别控制。根本区别是：Redis 事务是伪事务，MySQL 才是真事务。

回答要点
  1. 指出 Redis 无回滚能力
  2. 强调 MySQL 具备完整 ACID
  3. 点明隔离性实现机制差异（MVCC vs 无）
完整解析（含追问与踩坑）→
Redis 怎么保证原子性？通过什么操作保证原子性？

单条命令天然原子，因为单线程串行执行；多命令要用 Lua 脚本或 MULTI/EXEC 事务包起来。注意 Pipeline 只是批量发包，每条仍独立执行，不保证原子性——这点面试常踩坑。

回答要点
  1. 明确单命令原子性源于单线程模型
  2. 指出 Lua 脚本和事务是两种多命令原子方案
  3. 强调 Pipeline 不提供原子性

持久化与高可用 2 题

Redis持久化机制有哪些？RDB和AOF如何选择？

RDB是快照，适合备份和灾难恢复，但会丢最后一次快照后的数据；AOF是命令日志，通过append-only和重写保证数据安全，但文件大、恢复慢。线上一般两者共存：RDB做冷备，AOF开everysec策略保数据；若追求强一致，可AOF+fsync always，但影响性能。

回答要点
  1. 准确说出RDB触发条件（save/bgsave/主从全量同步）
  2. 指出AOF重写机制（fork子进程生成新日志，不阻塞主进程）
  3. 能根据业务场景推荐组合策略（如秒杀用RDB+AOF everysec）
完整解析（含追问与踩坑）→
介绍 Redis 主从同步的机制

主从同步分两步：首次全量用 RDB 快照，主库 bgsave 生成 rdb 文件传给从库，从库清空内存加载；增量靠 repl_backlog 缓冲区，主库把写命令写入缓冲区，从库通过 offset 断点续传。关键点是 repl_backlog 是环形缓冲区，大小决定从库断连多久能追上。

回答要点
  1. 全量同步含 bgsave + rdb 传输 + 从库加载
  2. 增量同步依赖 repl_backlog 环形缓冲区
  3. 说明 repl_backlog size 决定断连恢复窗口

缓存问题 2 题

缓存穿透、缓存击穿、缓存雪崩分别是什么，如何应对？
回答要点
  1. 穿透：查不存在的数据，请求绕过缓存直打 DB。解法：布隆过滤器、空值缓存
  2. 击穿：单个热点 key 过期瞬间大量请求打到 DB。解法：互斥锁重建、逻辑过期不失效
  3. 雪崩：大批 key 同时过期或缓存服务整体挂掉。解法：过期时间加随机、多级缓存、熔断降级
  4. 能说出三者的触发条件差异，而不是只背解法
展开讲讲

缓存穿透中使用布隆过滤器，本质是用空间换确定性：它通过 k 个哈希函数将 key 映射到位数组，查询时只要任一位置为 0 就可确定该 key 不存在（无假阴性），但所有位置为 1 时仅表示‘可能已存在’（有假阳性）——这是概率型数据结构的固有设计，无法消除误判，只能控制误判率。误判率公式为 $ (1 - e^{-kn/m})^k $，其中 m 是位数组长度，n 是插入元素数，k 是哈希函数数；实践中通过调整 m/n 比值（如 10–20）和 k（通常 3–7）可将误判率压至 1% 以下（《Network Applications of Bloom Filters: A Survey》, IEEE Communications Surveys & Tutorials, 2003, §III-A）。若用空值缓存替代布隆过滤器，则需承担存储膨胀与一致性维护成本：Redis 中大量空值会显著增加内存占用，且需设置较短 TTL（如 2–5 分钟），否则可能长期阻塞真实数据写入（Redis 官方文档：SET key value [EX seconds] 行为说明）。逻辑过期方案中，value 内嵌 expireTime 字段而非依赖 Redis TTL，是因为 Redis 的 EXPIRE 命令在 key 被驱逐或主从切换时可能丢失过期语义，而应用层控制能确保‘逻辑过期’状态始终与业务数据共存于同一序列化体中（Redis Design Docs: ‘Expiration’ section, redis.io）。

雪崩防护中‘过期时间加随机’必须作用于初始设值阶段，而非每次读取时重算；若在 SET key value EX 3600 中动态加随机，会导致同一 key 多次写入不同 TTL，破坏预期内存释放节奏（Redis 8.0 手册：EX 参数语义明确为‘设置绝对过期时长’）。

多级缓存（如本地 Caffeine + Redis）并非简单叠加，而是利用 L1 缓存的纳秒级响应规避网络往返，但需解决双写不一致：Caffeine 的 refreshAfterWrite 仅触发异步加载，不阻塞读请求，因此旧值可能被持续返回直至刷新完成（Caffeine GitHub Wiki: Refresh）。

熔断降级在缓存层失效时启用，其阈值（如 50% 请求超时）需基于服务 SLO 设定，而非固定值；Hystrix 等库的默认半开窗口可能引发雪崩式重试，应改用滑动窗口计数（Netflix Hystrix Documentation: ‘Circuit Breaker’）。

完整解析（含追问与踩坑）→
Redis 了解热点 key 的方法，一般用什么方式缓解 Redis 的热度压力

先用 redis-cli –hotkeys 或 monitor + slowlog 定位，再用 client list 查连接分布；缓解分三层：客户端本地缓存（如 Guava Cache）挡第一波，服务端加二级缓存（如 Caffeine），最后对 key 做散列（user:123 → user:123:shard0）打散压力。

  2. 分层缓解策略（客户端缓存→二级缓存→key 散列）
  3. 明确每层作用（如本地缓存挡穿透）

消息队列 3 题

为什么延迟队列可以用zset来做？

zset按score排序，把任务执行时间戳作为score，成员存job内容；用ZRANGEBYSCORE取score≤当前时间的任务，再用ZREM原子删除已消费任务；天然支持按时间排序、去重、范围查询，比list+定时轮询更精准高效。

回答要点
  1. score代表到期时间戳
  2. ZRANGEBYSCORE + ZREM组合保证原子消费
  3. 支持多消费者通过WATCH或Lua脚本防重复取

为什么考虑只用 Redis 做消息队列，为什么不用 Kafka

我们内部小规模任务调度用 Redis List+BRPOP，因为开发快、延迟低、运维简单；但明确不用于订单、支付等核心链路——Kafka 的磁盘持久化、副本机制、精确一次语义才是刚需。选 Redis 是接受‘可能丢少量非关键任务’换迭代速度，不是技术上更优。

回答要点
  1. 区分场景（小任务 vs 核心链路）
  2. 指出 Kafka 的不可替代性（持久化/副本/精确一次）
  3. 承认 Redis MQ 的本质妥协（非关键任务容忍丢失）

Redis 如何实现消息队列？

Redis 主要用 List 和 Stream 两种方式实现消息队列。List 靠 LPUSH/RPOP 简单实现，但无 ACK 机制；Stream 支持消费者组、PEL 和 XACK，能保证 at-least-once 语义，还支持 XCLAIM 故障接管。中小规模用 Stream 更稳妥，大规模高可靠场景建议 Kafka。

回答要点
  1. 能区分 List 与 Stream 队列的核心能力差异
  2. 说出 Stream 的 PEL、XACK、XCLAIM 三者协作流程
  3. 指出 Redis 队列在持久化和扩展性上的本质局限
