MySQL 索引的底层原理是什么，它解决了什么问题？

先开slow_query_log，设long_query_time阈值；用mysqldumpslow或pt-query-digest分析日志找TOP SQL；再explain看执行计划，重点看type、rows、key、Extra；最后结合索引、SQL写法、数据量做针对性优化，比如加索引、改JOIN顺序、拆分大事务。

回答要点
  1. InnoDB 用 B+ 树：非叶子节点只存键，叶子节点存数据且用链表相连
  2. B+ 树矮胖，三层能存千万级数据，把随机 IO 压到 2-3 次
  3. 相比全表扫描 O(n)，索引把查找降到 O(log n)
  4. 叶子链表支持范围查询和排序，这是 B+ 树相对 B 树的关键优势
展开讲讲
B+ 树被选为 InnoDB 默认索引结构，核心在于其对磁盘 I/O 和范围查询的协同优化。B 树的每个节点既存键又存数据（或行指针），导致非叶子节点能容纳的键更少，树高更高——例如 16KB 页、int 键 + 8B 指针下，B 树非叶子节点约存 400 键，而 B+ 树可存约 1200 键（因仅存键），三层 B+ 树即可覆盖千万级记录（MySQL 8.0 手册 15.3.12）。若用 B 树，同等数据量下树高增加，随机 I/O 次数上升，违背‘减少磁盘寻道’的设计目标（Goetz Graefe, SIGMOD Record 2011, ‘Modern B-Tree Techniques’）。更重要的是，B+ 树叶子节点用双向链表连接，使 SELECT ... WHERE id BETWEEN 100 AND 200 ORDER BY id 这类查询只需定位起始叶节点后顺序遍历，避免反复回溯父节点；而 B 树无此链表，范围扫描需多次树搜索，性能退化为 O(k log n)（k 为范围长度）（MySQL 8.0 手册 15.3.12）。聚簇索引中叶子节点直接存完整行数据（主键值即物理位置），二级索引叶子则只存主键值——这正是 B+ 树‘数据只在叶子’特性的强制体现，确保所有索引路径最终收敛于聚簇索引，避免数据冗余和更新异常（MySQL 8.0 手册 15.3.1）。

联合索引怎么判断是否命中？`(A, B, C)` 跳过 `B` 用 `A` 和 `C` 会怎样？

联合索引(A,B,C)遵循最左前缀：A或A,B或A,B,C能高效命中；但A,C只能用A做索引查找，C无法走B+树。不过MySQL 5.6+有索引下推（ICP），引擎层会在索引扫描时提前用C过滤，大幅减少回表次数。

回答要点
  1. 准确描述最左前缀原则失效场景（跳过中间列）
  2. 指出`A,C`仍能利用`A`进行范围查找
  3. 必须提及ICP对`C`条件的优化作用（非‘完全不用’）

MySQL 有哪些索引类型？

逻辑上分主键、唯一、普通、联合索引；物理上InnoDB只有聚簇索引（叶子存整行）和二级索引（叶子存主键）。特别注意：二级索引查非主键列要回表，但自适应哈希索引（AHI）能加速热点查询。

回答要点
  1. 区分逻辑分类（功能）和物理分类（存储结构）
  2. 明确聚簇索引=主键索引，二级索引叶子节点存主键值
  3. 提到AHI是InnoDB自动维护的优化机制
展开讲讲

InnoDB 的聚簇索引将数据行与主键 B+ 树物理绑定，因此主键选择直接影响页分裂频率和磁盘碎片。若主键非自增（如 UUID），新记录会随机插入到 B+ 树中间页，频繁触发页分裂：当页满时需拆分为两个页，并复制约 50% 的键值对，同时更新父节点指针——这不仅增加 I/O 和锁竞争，还导致逻辑上相邻的主键在物理上分散（MySQL 8.0 手册 15.6.2.1）。而自增主键保证插入始终追加到最右叶页，仅在页满时分裂一次且新页承接后续插入，显著降低分裂次数（MySQL 8.0 手册 15.6.2.1）。AHI（Adaptive Hash Index）依赖访问模式自动为热点二级索引前缀构建哈希索引，但仅加速等值查询；其维护开销由后台线程异步承担，且仅在缓冲池中存在足够空闲帧时启用（MySQL 8.0 手册 15.6.3.4）。若关闭 AHI（innodb_adaptive_hash_index=OFF），高频等值查询性能可能下降 10–30%，但可减少争用，适用于写密集或哈希冲突高的场景（MySQL 8.0 手册 15.6.3.4）。

SHOW ENGINE INNODB STATUS\G -- 搜索 'adaptive hash index'

varchar和char的区别

CHAR是定长，不足补空格，检索快但浪费空间；VARCHAR是变长，存实际长度+1或2字节长度头，节省空间但可能触发行溢出；CHAR适合短且等长字段如性别、国家码，VARCHAR适合长度差异大的如用户名、地址。

回答要点
  1. 存储方式差异（定长vs变长）
  2. 空间开销对比（含长度头）
  3. 适用场景举例（等长/不等长）

MySQL 有哪些锁？事务隔离级别有哪些？不同隔离级别下这些锁如何工作？

锁类型：行锁（记录锁、间隙锁、临键锁）、表锁、意向锁。隔离级别：读未提交、读已提交、可重复读、串行化。RR 下默认用临键锁（记录锁+间隙锁）防止幻读；RC 下只用记录锁，不加间隙锁，所以可能幻读。

回答要点
  1. 准确说出四种隔离级别名称
  2. 区分记录锁、间隙锁、临键锁三者关系
  3. 明确 RR 用临键锁防幻读，RC 不加间隙锁

MySQL 有哪些日志？各自作用是什么？

主要有三种：redo log（InnoDB 引擎层，保证崩溃恢复，循环写，物理日志）；undo log（引擎层，支持回滚和 MVCC，逻辑日志）；binlog（Server 层，用于主从复制和恢复，逻辑日志，追加写）。三者协同保障 ACID。

回答要点
  1. 分别说明 redo、undo、binlog 的层级（引擎/Server）
  2. 指出 redo 保崩溃恢复、binlog 保复制与归档、undo 保回滚与 MVCC
  3. 强调 redo 是物理日志、binlog/undo 是逻辑日志

MySQL 聚簇索引和非聚簇索引的区别？为什么非聚簇索引的叶子节点中会包含全部记录？

聚簇索引叶子存完整行数据，主键即索引；非聚簇索引（二级索引）叶子存的是主键值，不是整行。题干说法有误——非聚簇索引叶子不存全部记录，只存索引列+主键，查数据要回表。可能面试官口误，或指覆盖索引场景下联合索引恰好包含所有 SELECT 字段。

回答要点
  1. 清晰定义聚簇索引叶子存数据行
  2. 指出非聚簇索引叶子只存索引列+主键
  3. 纠正原文错误并给出合理解释（如覆盖索引）

设计数据库表时，给定简单业务场景和几个字段，如何选择数据结构？

比如用户年龄用TINYINT而非INT，避免空间浪费；手机号用VARCHAR(11)加校验，不用BIGINT；状态字段优先用TINYINT枚举，不用VARCHAR存字符串；关键要看是否参与索引、排序、范围查询。

回答要点
  1. 区分固定长/变长场景选CHAR/VARCHAR
  2. 数值类按范围选TINYINT/SMALLINT/INT
  3. 明确是否为空、有无默认值、是否建索引

一个查询语句里条件比较全，比如 `where`、`group by`、`order by`、`limit`，MySQL 执行这个查询语句时的执行顺序是什么？

逻辑执行顺序是：FROM→ON→WHERE→GROUP BY→聚合函数→HAVING→SELECT→DISTINCT→ORDER BY→LIMIT；注意WHERE在GROUP BY前过滤，所以不能用聚合结果，而HAVING在分组后过滤，能用COUNT(*)>10这种条件。

回答要点
  1. 准确列出WHERE在GROUP BY前
  2. 指出HAVING可用聚合函数
  3. 强调这是逻辑顺序非物理执行
