其他题目 14 题

请讲讲 redo log 和 undo log。

redo log是重做日志，保障持久性：事务提交时先写redo log，再异步刷数据页，宕机后靠它恢复已提交修改；undo log是回滚日志，保障原子性：记录修改前旧值，回滚时用它复原，还支撑MVCC快照读。两者配合，才让ACID落地。

回答要点
  1. redo log→持久性→WAL→崩溃恢复
  2. undo log→原子性→回滚→MVCC
  3. 点明二者协同实现ACID
展开讲讲
redo log 设计为循环写（ring buffer）而非无限追加，核心原因是避免日志文件无界增长导致磁盘耗尽和I/O性能退化。InnoDB 通过 innodb_log_file_size 和 innodb_log_files_in_group 配置固定大小的日志组，由 log_sys->lsn 和 log_sys->write_lsn 等指针控制覆盖边界；只有当对应脏页已刷入数据文件（即 checkpoint 已推进至该 LSN），该段日志才可被安全覆盖。若不循环而无限追加，不仅需持续分配磁盘空间，更会因日志文件过大导致崩溃恢复时扫描时间线性增长——MySQL 8.0 手册 15.6.2 明确指出：‘Recovery time is proportional to the amount of log to scan’。undo log 的存储结构也非简单追加：在 innodb_undo_tablespaces 启用时，每个 undo 表空间独立管理段（segment），且 innodb_undo_log_truncate 启用后，后台线程会将已提交事务的 undo log 段标记为可截断，但仅当其 LSN 小于最老活跃读视图（trx_sys->view_list 头部）时才真正清理，否则破坏 MVCC 一致性（MySQL 8.0 手册 15.7.2、15.7.3）。例如：SET GLOBAL innodb_undo_log_truncate=ON; 触发周期性 truncate，但前提是 innodb_undo_log_age 超过阈值且无长事务阻塞。

update这个语句会加什么锁？

在RC和RR隔离级别下，update会先对id=10这行加X（排他）记录锁；如果id是二级索引且不是唯一索引，还会加gap锁防止幻读；如果是唯一索引等值查询，则只加记录锁。注意：即使where条件没走索引，也会对所有扫描行加锁，可能升级为表锁。

回答要点
  1. 明确X记录锁是基础
  2. 说明gap锁在非唯一二级索引下的存在
  3. 指出唯一索引等值查询不加gap锁
展开讲讲

InnoDB 的 UPDATE 加锁行为本质是为保证 ACID 中的隔离性（Isolation）与持久性（Durability）协同实现。X 记录锁是原子性修改的必要前提：若不加 X 锁，多个事务可能同时读取旧值并基于此计算新值（如 UPDATE t SET c = c + 1），导致丢失更新——这违反了可重复读隔离级别下对同一行的写冲突控制要求（MySQL 8.0 手册 15.7.3）。Gap 锁仅在非唯一二级索引上存在，是因为唯一索引的等值查询能精确定位单一行（或确认不存在），无需防止幻读插入；而非唯一索引可能对应多行，若不加 gap 锁，其他事务可在间隙中插入新记录，破坏当前事务的范围语义（例如 WHERE name LIKE 'A%' 下的幻行）（MySQL 8.0 手册 15.7.1）。值得注意的是，gap 锁本身不阻塞 SELECT，但会阻塞 INSERT —— 这正是其设计目的：仅封锁插入点，而非读取点（MySQL 8.0 手册 15.7.1）。配置示例：SELECT * FROM t WHERE non_unique_idx = 1 FOR UPDATE; 在 RR 隔离级别下会加 X 记录锁 + gap 锁；而 WHERE pk = 1 则仅加 X 记录锁（无 gap 锁）（MySQL 8.0 手册 15.7.1）。

两阶段提交（2PC）与 buffer pool 异步刷盘并非锁机制的直接组成部分，但二者共同服务于崩溃恢复一致性：redo log 的 prepare 阶段确保事务状态可持久化，而 buffer pool 修改延迟刷盘则避免每次 UPDATE 都触发随机磁盘 I/O，否则 OLTP 性能将急剧下降（MySQL 8.0 手册 15.4.2）。

注意：gap 锁在 READ COMMITTED 隔离级别下被禁用（MySQL 8.0 手册 15.7.1），这是明确的语义变更，非 bug。

最左前缀原则？

最左前缀原则指联合索引(a,b,c)必须从最左列a开始连续匹配才能有效利用索引。比如where a=? and b>?能用上a,b，但where b=? or where a=? and c=?就只能用a或完全不用。特别注意范围查询后列失效，像a=? and b>? and c=?中c基本无法走索引定位。

B+ 树相比 B 树的优势是什么？

B+ 树所有数据都在叶子节点，且叶子节点用链表相连；这带来两大优势：一是范围查询快，只需遍历链表；二是树更矮胖，IO 次数更少，因为非叶节点只存 key 不存 data，同样大小磁盘块能存更多分支。

  1. 指出数据全在叶子节点（B 树数据可在内部节点）
  2. 强调叶子节点有序链表对范围查询的加速
  3. 说明非叶节点纯索引（无 data）带来的扇出提升
  4. 归结到 IO 效率（更少磁盘读）

当 MySQL 一页存不下一条记录时，会怎么处理？

InnoDB 会把超长字段（如 VARCHAR、TEXT、BLOB）的前 768 字节存在主数据页，剩余部分存到单独的溢出页（overflow page），用 20 字节指针链接。这会导致额外 IO 和锁竞争，也是推荐避免超长字段的原因。

高可用 2 题

MySQL、PostgreSQL 以及上述 OLAP 数据库如何设计主从一致性？发生故障后如何恢复？

MySQL主从靠binlog异步/半同步复制，一致性靠GTID+延迟监控；PostgreSQL用WAL流复制，可配同步备库；ClickHouse无原生主从，靠ReplicatedMergeTree+ZooKeeper协调；StarRocks用FE/BEBE架构，元数据强一致，BE数据最终一致。故障时MySQL切主+重放binlog，StarRocks自动Failover。

回答要点
  1. MySQL需说明binlog类型与同步模式选择影响
  2. PostgreSQL要提WAL和synchronous_commit配置
  3. ClickHouse必须强调Replicated表引擎依赖ZK
  4. StarRocks需区分FE元数据强一致与BE数据最终一致

Redis宕机了怎么办，再启动呢

第一反应切直连DB+本地缓存降级；第二步检查RDB/AOF是否完整，若可用则快速恢复；第三步启动后做双写同步补偿，用binlog比对缺失数据，避免雪崩。

  1. 立即降级策略（如DB直查+本地Caffeine缓存）
  2. 恢复时校验持久化文件完整性
