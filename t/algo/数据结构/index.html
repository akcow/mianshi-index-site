手写LRU缓存

用哈希表O(1)查节点，双向链表O(1)移位和删尾。头结点最新访问，尾结点最久未用。Get命中就移到头；Put时若存在则更新值并移到头，若不存在且超容，先删尾节点再插入新节点到头。关键细节：哨兵头尾节点避免空指针判断，删除节点要同时解哈希表映射。

回答要点
  1. 哈希表+双向链表结构选型合理
  2. Get/Put操作时间复杂度均为O(1)
  3. 正确处理容量超限时的尾部淘汰
  4. 哨兵节点或空指针防护到位
展开讲讲

LRU缓存采用哈希表+双向链表的核心设计，本质是为同时满足O(1)随机访问与O(1)有序淘汰两个正交需求：哈希表提供键到节点的直接映射（避免遍历），而双向链表支持在任意位置O(1)删除和移动节点（单向链表无法在已知节点引用时O(1)删除前驱）。若仅用哈希表+单向链表，淘汰尾部节点时需从头遍历至倒数第二节点，退化为O(n)；若仅用有序数组，则Get/Put均需O(n)移动元素。哨兵节点（dummy head/tail）消除空指针分支判断，使插入/删除逻辑统一，符合Go标准库container/list的设计实践（Go 官方文档：container/list）；其存在使Remove(e *Element)无需检查e.prev/e.next是否为nil，显著降低边界错误概率。过期时间与LRU淘汰属不同维度——LRU管理访问序，TTL管理生存期，二者不可合并为单一排序依据（如按访问时间排序则无法及时清理过期项），必须正交处理（Redis 7.0 设计文档：Eviction and Expiration Separation）。

// 最小示例：哨兵初始化
type LRUCache struct {
    head, tail *Node
}
func Constructor() LRUCache {
    h, t := &Node{}, &Node{}
    h.next = t
    t.prev = h
    return LRUCache{head: h, tail: t}
}

用栈模拟队列

用两个栈：push 时全进 inStack；pop 或 peek 时，若 outStack 为空，就把 inStack 全部倒出到 outStack，再操作 outStack；这样均摊时间复杂度是 O(1)。

回答要点
  1. 明确区分 inStack 和 outStack 的职责
  2. outStack 为空时才触发倒数据，避免重复搬运
  3. 正确实现 push/pop/peek 三个接口并处理空队列异常

手撕：树的层序遍历（BFS）

用队列存节点，初始放根节点；每次取队首，把它的左右子节点依次入队，直到队列为空。关键要判空——根为null直接返回空列表，每层结果用临时list收集再加入总结果。

回答要点
  1. 正确使用Queue实现FIFO遍历
  2. 处理root为null的边界情况
  3. 分层输出（每层一个子列表）

手撕：查找树中值为value的节点，并返回从根到该节点的路径（DFS回溯）

用DFS递归，每层把当前节点加入path列表；找到目标值就立即返回true；没找到就递归左右子树，回溯时removeLast。关键点是：一找到就层层return true中断搜索，避免无效遍历。

回答要点
  1. 正确维护路径列表（add→递归→remove）
  2. 命中目标时立即返回并逐层透传true
  3. 空节点及时return false避免NPE

算法：检验是否二叉搜索树。

用递归传递上下界：每个节点必须大于左子树所有值、小于右子树所有值，所以递归时传low和high指针。空节点返回true；当前值越界就false；否则递归检查左右子树，左子树high更新为当前节点，右子树low更新为当前节点。

回答要点
  1. 使用上下界递归（非中序遍历）
  2. 正确处理nil边界（low/high为nil时跳过比较）
  3. 明确重复值判定（BST通常不允许相等）

数组和链表的区别是什么？优缺点是什么？有什么使用场景？

数组内存连续，随机访问 O(1)，但插入删除 O(n)；链表节点分散，插入删除 O(1)（已知位置），但访问 O(n)。数组缓存友好适合批量读写；链表适合频繁中间增删，比如 LRU 缓存。实际选型看访问模式和修改频率。

回答要点
  1. 对比内存布局、访问/增删时间复杂度
  2. 点出缓存局部性对数组性能的影响
  3. 给出各一个典型场景（如数组→批量统计，链表→LRU）

手写一个基于开放寻址法的 HashMap，要求支持 Put、Get、Delete，并处理扩容和删除标记。

我用线性探测，每个槽位存 key/val/state 三元组，state 分 empty/used/deleted。Put 时先找空位或 deleted 位，优先复用 deleted；Get 要跳过 deleted 继续探；Delete 只打标不真删。扩容触发条件是负载因子超 0.7，新数组重建时只 rehash used 状态项。关键点是探测循环要模数组长，且 delete 后必须留 tombstone 保链路。

回答要点
  1. 正确实现线性探测的查找/插入/删除循环逻辑
  2. delete 使用 deleted 标记而非清空，且 Get/Put 能正确处理
  3. 扩容时仅迁移 state==used 的项，且重新哈希

堆的复杂度是怎么样的？

堆的插入和删除最大（或最小）元素都是O(log n)，建堆是O(n)，查找任意元素是O(n)——因为堆不是为查找设计的，得遍历。空间复杂度是O(1)（原地建堆）或O(n)（显式存储）

回答要点
  1. 插入/删除操作为O(log n)
  2. 建堆时间为O(n)而非O(n log n)
  3. 不支持O(1)或O(log n)查找任意值

Gin路由使用的数据结构是字典树，请介绍一下字典树。

字典树是树形结构，边代表字符，节点代表路径前缀；根到叶的路径构成单词；支持O(m)时间复杂度的插入和查询（m为字符串长度）；常用于自动补全、IP路由、敏感词过滤，优势是节省空间且支持前缀匹配。

回答要点
  1. 节点不存字符，边存字符（或数组索引映射）
  2. 查询时逐字符遍历，中途无边则失败
  3. 相比哈希表，天然支持前缀搜索和词频统计
