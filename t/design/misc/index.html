你理解的RPC是什么？

RPC就是让调用远程服务像调用本地函数一样。它隐藏了网络通信、序列化、连接管理、超时重试这些脏活。一次调用流程是：客户端调代理→框架序列化请求→发到服务端→服务端反序列化并执行→返回结果。工业级RPC框架还得有服务发现、负载均衡、熔断限流、链路追踪这些能力，否则根本没法在线上用。

回答要点
  1. 定义RPC目标是透明化远程调用
  2. 完整描述请求-响应数据流路径
  3. 指出序列化/反序列化、网络传输、超时重试三大必有环节
  4. 提及至少两个生产级扩展能力（如服务发现、熔断）
完整解析（含追问与踩坑）→
分布式场景下怎么加锁？加锁命令是什么？

Redis用SET key value EX seconds NX实现，必须原子性；要加唯一client_id防误删；超时时间得大于业务执行时间；ZooKeeper靠临时有序节点；Etcd用CompareAndSwap；关键不是命令本身，而是如何保证锁的互斥、防死锁、可重入和容错恢复。

回答要点
  1. Redis SETNX+EX原子性保障
  2. 锁释放时校验value防误删
  3. 设置合理超时并配合续约机制

Pod到Service的数据链路是怎样的？

发奖这一块是怎么做的？

我们走最终一致性：下单成功发 MQ 消息到发奖服务，它用本地事务表记录发奖状态，成功后更新 DB 并调第三方接口；失败则重试，超过阈值进死信队列人工介入。所有发奖操作带唯一业务 ID 防重。

回答要点
  1. 必须有本地事务表或消息表保障可靠投递
  2. 调第三方接口必须带幂等 key
  3. 失败有分级重试策略（立即/延迟/人工）
  4. 发奖结果需回写主订单表供查询

这个场景更像 workflow 还是 agent？为什么？

你们登录系统这一块是怎么做的？

我们用 JWT 方案：用户输账号密码，服务端校验后签发含 userId 和过期时间的 token；前端存 localStorage，每次请求带在 Authorization 头；服务端用公钥验签并解析。密码用 BCrypt 加盐哈希存储，登录失败 5 次锁定账户。

算法 2 题

如何把 CPU 计算前置来优化抢红包？

把‘抢时算金额’变成‘发时存金额’：发红包阶段就用伪随机算法生成 10 个严格加总为 100 的整数，序列化后存 Redis List；抢的过程只是消费队列，完全剥离计算，让高并发压力从 CPU 转移到内存带宽。

回答要点
  1. 发红包阶段完成全部金额生成与校验
  2. 存储结构必须支持无锁快速消费（如 List/LPUSH+RPOP）
  3. 金额序列需满足数学约束（总和精确、最小单位、非负）

为什么红包金额写死在 Redis 里会导致不公平？

写死金额意味着每个红包的分配序列完全相同，比如都是 [1,2,3,4,5,10,15,20,20,20]，那抢到第 10 个的人永远拿 20 元，而第 1 个永远拿 1 元——这违背了‘先到先得但金额随机’的用户预期，造成确定性歧视。

回答要点
  1. 指出写死导致分配序列固定可预测
  2. 关联用户体验：先抢者未必多拿，破坏心理公平
  3. 点明与微信实际‘随机但总和可控’机制的本质差异

缓存 2 题

为什么要使用 Singleflight？Singleflight 只在进程内有效，真实环境中还有什么手段优化？

Singleflight 解决的是单机内重复请求穿透缓存的问题，比如多个 goroutine 同时查同一个 key。但在集群中，得靠分布式锁——比如 Redis SETNX 加随机 value 防误删，或者用 etcd 的 Lease 机制。更优方案是加二级缓存，本地缓存兜底+短 TTL，降低打到中心缓存的概率。

回答要点
  1. 准确说出 Singleflight 的作用边界（单机、请求去重）
  2. 提出至少一种跨进程防重方案（如 Redis 分布式锁）
  3. 给出二级缓存等降级思路
