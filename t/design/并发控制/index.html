Raft 共识算法的原理是什么？

Raft 把节点分为 Leader/Follower/Candidate 三种状态；Leader 通过心跳维持权威；选举时 Candidate 发起 RequestVote RPC，获多数票即胜出；日志复制要求 Leader 将命令追加到本地 log 后，异步同步给 Follower，等多数节点 commit 才应用到状态机。

回答要点
  1. 准确说出三种角色及其转换条件
  2. 强调心跳是 Leader 维持权威的核心机制
  3. 说明日志复制的两阶段：追加本地 log → 等多数响应后 commit
  4. 点明安全性约束（如 Leader 必须包含所有已提交日志）
展开讲讲
Raft 的 Leader 必须包含所有已提交日志（Log Matching Property），这一约束由选举限制（Election Restriction）强制保障：Candidate 在 RequestVote RPC 中必须携带自身 last log index 和 term，Follower 拒绝投票给 last log term 更小、或 term 相同但 index 更短的 Candidate（Raft 论文 §5.2, Figure 7）；若 term 更大但 log 不完整，则其日志可能缺失已提交条目，故拒绝。不满足此限制将导致新 Leader 缺失已提交日志，破坏安全性——例如旧 Leader 在提交 index=5 后宕机，新 Leader 若无该条目却获选并覆盖日志，将造成已提交日志丢失（违反 Raft 安全性定理）。心跳机制不仅是权威维持手段，更是时间同步信号：Follower 收到任一 Leader 的有效 AppendEntries（含 term ≥ 自身 currentTerm）即重置选举超时器（Raft 论文 §5.2）；若无此设计，网络延迟波动易触发频繁无效选举。日志复制的‘两阶段’本质是分离写入与提交：AppendEntries 请求仅要求 Follower 将条目追加至本地 log（不执行），而 commitIndex 推进需 Leader 自身 log 包含该条目且多数节点已复制（Raft 论文 §5.3）；若合并为单阶段（如追加即提交），则网络分区时可能在少数节点上错误提交未被多数确认的日志。

项目中如何防止分布式账本被篡改？

每个区块头存前块哈希、Merkle Root 和 nonce；交易按 Merkle Tree 组织，根哈希写入区块头；全节点校验时，重新计算 Merkle Root 并比对；篡改任一交易会导致路径上所有哈希变更，最终使当前区块头哈希不匹配，从而被网络拒绝。

回答要点
  1. 指出哈希指针链（前块哈希）与 Merkle Tree 双重保障
  2. 说明 Merkle Root 存储位置（区块头）及校验方式（重算比对）
  3. 解释篡改传播路径（单交易→路径哈希→Root→区块头）
  4. 强调全节点独立验证机制

为什么做请求与响应的顺序控制，不做会有什么问题？
回答要点
  1. 说清场景：同一客户端的请求必须串行，否则响应乱序导致状态错乱
  2. 并发下的正确性：顺序控制在哪个线程做的、是否阻塞、QPS 100 时会不会打爆
  3. 能主动指出设计的代价（耗时任务阻塞快速任务），而不是等面试官点破
  4. 区分「同客户端串行」与「跨客户端并行」，这是设计的关键边界
