如何提升 LRU 缓存的并发性能？

最直接的是分片——把缓存拆成多个独立shard，每个有自己map、链表和锁，大幅降低锁粒度；其次可放宽语义，比如用异步方式批量更新访问序，牺牲一点精确性换吞吐；再往上，可以结合多级缓存隔离冷热，或引入热点自动保护机制，甚至换用更工程友好的策略如TinyLFU或W-TinyLFU。

回答要点
  1. 提出分片降低锁竞争
  2. 提出近似LRU（如异步/批量更新）换取性能
  3. 提到多级缓存或替代策略（如TinyLFU）作为演进方向

定时任务和延迟任务发布后，如何保证其正确执行？

用时间轮+Redis ZSet 或 XXL-JOB 这类调度中心；任务注册时存 DB + 设置状态为 pending；执行前先 CAS 更新为 running；成功后更新为 done；失败走重试+死信队列；所有状态变更打日志并告警。

回答要点
  1. 任务状态机设计与数据库事务/乐观锁保障
  2. 执行过程中的幂等控制（如唯一业务 ID + 去重表）
  3. 失败后的重试策略、死信处理与人工介入通道

简历写有2000 QPS，这个QPS是指创建任务的QPS吗？

是创建任务接口的QPS，即每秒成功写入数据库的新任务数。压测时用wrk模拟100并发，持续5分钟，取稳定期平均值。排除了DB连接池耗尽和网络超时的case，只统计HTTP 200响应。

回答要点
  1. 明确定义QPS统计对象（创建接口）
  2. 说明压测工具（wrk）和关键参数（并发数/时长）
  3. 指出有效响应范围（HTTP 200）

多级缓存如何实现？请描述完整的请求路径。

请求先查本地缓存（如Caffeine），未命中则查Redis集群，再未命中才查DB；写操作用Cache-Aside模式，更新DB后删除Redis和本地缓存，本地缓存加主动刷新+过期双机制防雪崩。

回答要点
  1. 明确三级：本地缓存→Redis→DB
  2. 读路径：逐级回源，写路径：先DB后删缓存
  3. 本地缓存需设过期时间+主动刷新避免脏数据

高并发下网关怎么考虑扩展和治理？

网关本身无状态，靠水平扩容；入口用负载均衡，内部做连接池、限流熔断、超时重试；可观测性要记录QPS、错误率、P95延迟、下游耗时、重试次数，失败时能按租户/接口/模型快速下钻。

回答要点
  1. 明确无状态+水平扩展前提
  2. 列出至少三项核心治理能力（限流/熔断/超时）
  3. 强调可观测性维度（租户/接口/模型等）

多用户高并发发布视频，后端只有一个数据库，如何缓解入库压力？

核心是用消息队列做缓冲层：发布接口校验完就投递消息到MQ，立刻返回‘处理中’，不等DB写入。消费者按可控并发数批量写库，防止连接池打满或磁盘IO饱和。消息必须持久化，消费者成功写库再ACK，失败则重试；为防重复消费，DB仍需request_id唯一约束。如果强一致性要求高，就用事务Outbox模式——同一事务写业务表和outbox_event表，后台再可靠投递。

回答要点
  1. 明确接口层与DB解耦，返回时机前移
  2. 消费者配置需考虑DB承受力（并发数/批量大小）
  3. 指出消息重复的必然性及DB层幂等兜底

整体架构如何拆分？

我拆成五块：API网关统一入口；元数据服务管MySQL里的目录和文件；存储适配器层屏蔽云盘/HDFS/本地盘差异；搜索服务消费消息队列事件，维护ES索引；下载服务负责权限校验、任务调度和流式ZIP生成。所有跨存储操作都走适配器，变更都发事件，不直接调用。

回答要点
  1. 明确划分元数据、存储、搜索、下载四大核心服务
  2. 指出消息队列作为元数据变更与索引更新的解耦媒介
  3. 说明适配器层对不同存储SDK的封装职责
  4. 下载服务需支持同步小文件流式响应和异步大任务
  5. 强调各模块间无直接依赖，靠接口和事件通信

异步下载场景还有哪些优化？

四点优化：一是按存储endpoint分组，复用连接并调批量接口；二是Worker Pool限流+超时+有界队列，防打挂下游；三是读取和ZIP写入间加有界缓冲，用背压控内存；四是缓存高频ZIP，任务用幂等键，失败只重试分片并记录进度。对已压缩文件跳过ZIP压缩，减少CPU。

回答要点
  1. 分组复用连接并利用存储方批量API
  2. Worker Pool需配置并发数、超时、队列长度三要素
  3. 有界缓冲实现读写速率解耦与内存保护
  4. 幂等键设计+分片重试+进度记录构成可靠任务框架
  5. 缓存策略针对常用目录或重复下载文件
