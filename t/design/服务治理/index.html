展开讲讲

为什么需要分布式锁而非本地锁

本地锁（如 Java 的 synchronized 或 ReentrantLock）仅在单 JVM 进程内有效，多实例部署时各进程拥有独立内存空间和锁对象，无法感知彼此状态，导致并发控制完全失效——这直接违反 CAP 中的 Consistency 要求（当系统选择 AP 时，仍需在业务层保障关键操作的逻辑一致性）（Go 官方文档：Memory Model；Java Language Specification §17.4）。例如 synchronized (this) { updateDB(); } 在两个实例中会各自执行 updateDB()，造成重复扣款。必须升级为分布式协调机制，如基于 Redis 的 Redlock（Redis 官方文档：Distributed locks）或 ZooKeeper 的临时顺序节点（ZooKeeper Programmer’s Guide §7.2），其核心是通过共享存储实现跨进程的互斥原语。

为什么定时任务需中心化调度

多实例下若每个节点独立执行 @Scheduled(fixedRate=60000)，将触发 N 倍重复执行。根本原因在于 Cron 表达式在各节点本地解析并触发，缺乏全局执行视图。解决方案必须引入外部协调者：Quartz 集群模式依赖 JDBC JobStore 实现 TRIGGER_STATE 表行锁（Quartz Scheduler 2.3.x 手册：Configuring Clustering）；或使用 XXL-JOB 等调度平台，由中心服务分配执行权（XXL-JOB v2.4.0 文档：Executor Design）。

一致性哈希为何能缓解缓存雪崩

普通轮询使节点增减导致全部 key 重映射，引发缓存集体失效（RFC 1952 §2.3 类比思想）。一致性哈希将 key 和节点映射至同一环，增删节点仅影响邻近区间，降低缓存击穿概率（Karger et al., Consistent Hashing and Random Trees, STOC 1997）。

Reactor 网络模型的工作原理是什么？
回答要点
  1. 事件循环 + IO 多路复用（epoll）监听就绪事件，分发到对应 handler
  2. 单 Reactor 单线程 / 单 Reactor 多线程 / 主从 Reactor 三种形态的差异
  3. 主从 Reactor：mainReactor 只处理 accept，subReactor 处理读写，避免 accept 阻塞影响 IO
  4. 与 Proactor 的区别：Reactor 是就绪通知，Proactor 是完成通知
