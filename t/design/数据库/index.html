讲一下推拉结合。你的Inbox和Outbox如何实现？大V如何判定？

普通用户用推模式：关注关系变更时，把大V新视频推到其Inbox（Redis Sorted Set）；大V用拉模式：粉丝查Feed时实时聚合其Outbox（MySQL分表）；大V判定标准是粉丝>10万或单条视频曝光>50万。

回答要点
  1. 明确推/拉适用对象及触发时机
  2. Inbox用Redis ZSet、Outbox用MySQL分表
  3. 大V判定有可量化阈值（非主观）

热榜是如何实现的？

用 Redis ZSet 存 hourly_score，score = log(1+pv) * 0.7 + log(1+like_cnt) * 0.3；每小时用 Lua 脚本聚合日志表统计 PV/Like，更新 ZSet；前端查 zrevrangebyscore 获取 Top100；降级时直接读 MySQL 副本兜底。

回答要点
  1. 明确 score 公式含多维度加权（PV+互动）及衰减设计
  2. 说明更新时机与原子性保障（Lua 脚本聚合）
  3. 指出存储结构（ZSet）及查询命令（zrevrangebyscore）
  4. 有降级方案（MySQL 副本）
展开讲讲

热榜的衰减设计本质是为了解决时间敏感性与数据新鲜度的权衡。若不衰减（如仅用原始 PV 或互动数），旧内容会因历史累积优势长期霸榜，违背‘热’的实时语义；而线性衰减无法匹配用户兴趣衰减的非线性特征，因此工业界普遍采用指数衰减（如 score = (base_score) * e^(-λ * t)），其数学基础源于泊松过程对事件流的建模假设（《Mining of Massive Datasets》第10.2节）。Redis ZSet 的 score 是 64 位双精度浮点数，当时间戳参与计算时，若直接使用秒级 Unix 时间戳（如 time.Now().Unix()），在 t 较大时会导致浮点精度丢失，使相近时间的条目 score 相同，破坏排序稳定性——正确做法是使用相对时间（如 t = now - publish_time）并控制量纲（例如以小时为单位，保留小数点后两位）。Lua 脚本保障原子性并非仅因 Redis 单线程，而是避免多命令间被其他客户端插入导致中间状态不一致，这是 Redis 官方文档明确强调的「atomicity guarantee for multi-step operations」（Redis 官方文档：Scripting#atomicity）。ZSet 底层虽为跳表，但 zrevrangebyscore 在范围查询时仍需遍历 O(log N + M) 节点，当 M（返回数量）远小于总成员数时性能尚可，但若 M 接近总规模（如取 top 100000），则实际耗时趋近 O(N)（Redis 源码 t_zset.c#zslGetRank 注释说明）。

-- 示例：安全的时间衰减 Lua 脚本（避免大整数精度问题）
local now_h = math.floor(tonumber(ARGV[1]) / 3600)
local pub_h = math.floor(tonumber(ARGV[2]) / 3600)
local delta_h = math.max(0, now_h - pub_h)
local score = tonumber(ARGV[3]) * math.exp(-0.1 * delta_h)
redis.call('zadd', KEYS[1], score, ARGV[4])

当Redis故障时，JWT鉴权如何降级到MySQL？请说明降级触发条件、MySQL压力控制措施和兜底时效性保障。

我们用命令超时+错误率双指标触发降级：连续3次Redis调用超50ms或10秒内错误率超30%就熔断。降级后走MySQL查session状态，但会加本地LRU缓存（TTL 60秒）、singleflight合并并发请求，并用独立连接池限流到50QPS，避免打爆DB。

回答要点
  1. 降级触发必须基于实时可观测指标（非心跳探测）
  2. MySQL回源必须带本地短TTL缓存+请求合并
  3. 必须隔离连接池和并发信号量，防止拖垮主链路
  4. 需说明降级是临时兜底，恢复后需异步回填热点数据

用户表数据量太大，怎么分表？有没有后续动态扩容且分布均匀的分表方法？

推荐一致性哈希或虚拟槽位法：预设 1024 个 slot，每个 user_id hash 后映射到 slot，再由 slot 映射到物理库表。扩容时只需迁移部分 slot，不影响其他数据，且分布天然均匀。比简单取模更抗抖动，比 range 分片更均衡。

回答要点
  1. 提出一致性哈希或虚拟槽位方案
  2. 说明扩容只需迁移部分数据
  3. 强调分布均匀性保障机制

数据库表结构怎么设计？

我按三层解耦设计：storage_systems存云盘/HDFS等接入信息；directories用parent_id实现目录树，支持路径查询；files表存文件核心元数据，并通过directory_id关联目录。不把文件列表放目录表里，避免字段膨胀和更新困难。如果一个逻辑文件跨多个物理存储，再加file_sources表做多对多映射。

回答要点
  1. 区分存储系统、目录、文件三层实体
  2. 目录树用邻接表（parent_id）而非嵌套集
  3. files表通过foreign key关联directory_id而非反向存储列表
  4. 能说明为何不用目录表存文件ID数组
  5. 提出file_sources表应对多源存储场景

如何实现跨存储系统搜索？为什么使用搜索引擎？

我把文件名、路径、大小、更新时间等元数据同步到Elasticsearch，查的时候先搜ES再回查MySQL拿权限和最新状态。不用MySQL是因为它不擅长分词、模糊匹配和高并发全文检索；ES倒排索引快，还能做相关性排序。同步用Outbox+消息队列保证可靠，存量走全量扫描，增量靠事件。

回答要点
  1. 明确ES存检索字段，MySQL存强一致元数据
  2. 指出MySQL不适合分词/前缀/模糊等复杂查询
  3. 同步机制含Outbox事务保障+幂等upsert+版本控制
  4. 说明全量+增量双阶段同步策略
  5. 提及短暂延迟下回查MySQL兜底

实现微信抢红包功能，你会怎么设计？

我会分三层：预热层用 Redis List 存拆好的随机金额（保证公平），抢领层用 Lua 原子 pop + 记录用户ID，异步层用 MQ 落库并校验总金额。绝不在线程里做金额计算或 DB 写入，所有耗时操作后置。

回答要点
  1. 预拆金额到 Redis List（非运行时计算）
  2. 抢动作由 Lua 原子 pop 保证幂等和顺序
  3. DB 落库与金额校验异步化，解耦核心链路
