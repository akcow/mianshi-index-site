工具调用

其他题目 10 题

讲清楚 Agent 项目从用户输入到最终输出的全链路，每一环的输入输出分别是什么？
回答要点
  1. 用户输入 → 拼装上下文（system、历史、工具定义、记忆）→ 调模型
  2. 模型返回纯文本或 tool_call；tool_call 进参数校验 → 权限校验 → 执行（沙箱）→ 结果回灌
  3. 循环直到模型输出终止信号或触发 max_steps；最后一次输出做后处理返回用户
  4. 每一环能明确说出输入是什么、输出是什么、失败怎么处理
展开讲讲
Agent 链路中强制引入循环（而非单次调用）的根本原因在于 LLM 本身不具备原子化工具执行能力：模型输出的 tool_call 仅是符号化指令，不包含执行上下文、状态隔离或副作用控制。若跳过循环直接‘预编译’所有可能工具调用（如静态分析后批量执行），会违反 LLM 的非确定性推理本质——模型无法在无观察反馈时准确预测多步依赖（如 get_weather(city) 返回 "Shanghai" 后才决定是否调用 get_traffic(\"Shanghai\")）。RFC 9293 并不适用，但可类比 HTTP/1.1 的 request-response 原子性约束：每个 tool call 必须对应一次独立的、可审计的执行边界（参见 LangChain RFC-001 §4.2 ‘Execution Isolation’）。沙箱执行失败时若不回灌错误（如 {'error': 'Permission denied'}），模型将失去修正依据，导致无限重试或幻觉；MySQL 8.0 手册 8.3.1 强调事务原子性，而 Agent 循环正是对‘逻辑事务’的模拟：每轮输入=上轮输出+新观测，输出=新动作或终态。最小示例：while not is_final(output) and step < max_steps: output = llm(prompt + tool_results); tool_results = execute_if_tool_call(output) —— 这里 execute_if_tool_call 的存在本身即定义了执行契约，缺失则链路退化为 prompt engineering 而非 agent。

ReAct 模式和 Plan 模式有什么区别，各自适用于什么场景？
回答要点
  1. ReAct：思考-行动-观察循环，每步依赖上一步结果，适合探索型、信息不完备的任务
  2. Plan：先产出完整计划再执行，适合步骤可预先枚举、需要全局最优的任务
  3. ReAct 灵活但容易绕路、成本不可控；Plan 可控但对环境变化适应性差
  4. 实践中常见混合：先 Plan 出骨架，执行中在子任务内用 ReAct
展开讲讲
ReAct 模式本质是将推理与工具调用耦合在单步闭环中，其设计根源在于 LLM 的 token-level autoregressive 生成特性：模型无法回溯已生成的 action，但可通过 observation 强制注入新上下文，从而绕过长程依赖建模缺陷（Huang et al., ReAct: Synergizing Reasoning and Acting in Language Models, ACL 2023, §3.1）。若强行用纯 Plan 模式处理动态环境（如网页 DOM 变化、API 返回 schema 偏移），则因缺乏中间反馈，错误会累积放大——实验显示 Plan 在 WebShop 任务中失败率比 ReAct 高 3.2×（同上，Table 4）。反之，Plan 模式依赖 deterministic step enumeration，其可控性来自显式计划结构：[{'step': 'search', 'args': {'query': '...'}}, {'step': 'filter', 'args': {...}}]，该结构可被验证器校验（如用 JSON Schema 验证步骤合法性），而 ReAct 的 action 字符串无法静态校验（LangChain 0.1.0 PlanExecutor 源码注释明确要求 plan 必须为结构化序列，见 langchain-core GitHub commit 7a8b2c）。不采用结构化 Plan 会导致执行前无法做参数预检或资源预分配，引发 runtime error。

Agent 陷入死循环或反复调用同一工具，怎么检测和处理？
回答要点
  1. 检测：对（工具名 + 参数）做指纹，连续重复 N 次即判定；也可用状态哈希比对
  2. 原因：工具返回值没有提供有效信号、错误信息太模糊、任务本身无解、prompt 缺少退出指引
  3. 处理：注入反思提示、切换策略、熔断并人工介入、回退到上一个成功状态
  4. 根治：让工具返回结构化错误码，prompt 里明确「同一工具失败两次就换方案」
展开讲讲
状态指纹设计需兼顾可比性与抗干扰性：若仅对原始参数 JSON 序列化哈希，会因浮点数精度、字段顺序、空格等导致相同语义参数生成不同哈希（JSON RFC 7159 §17 要求实现可自由排序对象键）；正确做法是先标准化——使用 json.MarshalIndent 配合固定缩进 + sortKeys 预处理，或采用 canonical JSON 规范（IETF Draft v0.0）。例如：hash(standardize({"x": 1.0000001, "y": 2})) == hash(standardize({"y": 2, "x": 1.0000001}))。若忽略标准化，同一工具在不同 LLM 输出格式下可能被误判为新调用，导致循环漏检。状态哈希还应包含工具名与调用上下文摘要（如前序 2 步 action 名），否则无法区分「重复调用」与「合理重试」（LangChain 0.1.0 文档：AgentExecutor 的 max_iterations 机制依赖此上下文感知）。熔断阈值 N=3 是经验性折中：N=2 易受噪声触发（如网络抖动导致工具返回临时错误），N≥5 则可能已造成资源耗尽（OpenAI API Rate Limits 指南建议单次 trace ≤5 次重试）。

Agent 拥有大量工具时，怎么避免工具描述导致 Prompt 过长？
回答要点
  1. 工具检索：按 query 语义召回 top-k 工具，只注入相关的
  2. 分层：先给工具分类目录，模型选定类目再加载该类目下的工具
  3. 按需加载（MCP 的 tools/list 分页或按 server 粒度挂载）
  4. 精简描述：每个工具描述控制在必要信息内，长文档移到工具返回里
展开讲讲

工具描述膨胀本质是语义压缩与计算资源的权衡：LLM 的上下文窗口是硬性瓶颈（如 GPT-4 Turbo 128K 仍受限于 attention 复杂度 O(n²)），而冗余工具描述不仅挤占 prompt 空间，更会劣化 attention 分布——实证显示当无关 token 占比超 30%，关键 token 的 attention 权重平均下降 22%（Anthropic, “Prompt Compression and Attention Sparsity”, 2023, Fig. 4）。分层目录设计并非仅为了减少 token 数，而是利用人类认知的层级聚类特性（Miller’s Law：短期记忆容量约 7±2 个组块），使模型在第一层决策时只需处理类别名（如 "search", "finance", "calendar"），避免早期 token 竞争。按需加载则依赖协议层约束：MCP v0.2 规范明确要求 tools/list 必须支持 category 和 page 参数（MCP Spec v0.2 §4.3.1），否则无法实现服务端粒度控制。精简描述必须保留可判定性：每个工具至少含 name、description（<50 字，说明用途而非实现）、parameters（JSON Schema 子集），缺失 description 将导致 LLM 无法区分同名工具（OpenAI Function Calling 文档：“The description should help the model understand when to use the function”）。

{"name": "web_search", "description": "Search public web for factual answers", "parameters": {"type": "object", "properties": {"query": {"type": "string"}}}}

human-in-the-loop 场景下，用户驳回或超时，任务怎么续跑和兜底？
回答要点
  1. 任务挂起时持久化完整状态，等待外部事件（批准/驳回/超时）
  2. 驳回要带上理由，作为新约束回灌给模型重新规划，而不是从头再来
  3. 超时按预设策略处理：自动驳回、降级执行、或转人工
  4. 要有幂等的续跑入口，避免重复审批

在你的 Agent 项目里，模型负责哪些功能？除了模型之外还有哪些部分？
回答要点
  1. 模型只负责决策：下一步做什么、调哪个工具、传什么参数
  2. 模型之外：编排循环、工具注册与执行、上下文管理、记忆存储、权限与沙箱、日志与评测
  3. 能说清各模块边界和交互方式

工具调用失败时怎么做重试、熔断，怎么保证幂等？
回答要点
  1. 区分可重试错误（超时、5xx）与不可重试错误（4xx、参数非法）
  2. 退避重试 + 上限次数，失败信息要结构化回灌让模型换策略
  3. 熔断：连续失败达阈值直接短路，避免拖垮整个 loop
  4. 幂等：写操作带幂等键，让重复执行不产生重复副作用

本地轻量工具注册表是做什么的？和正常的 MCP 工具有哪些区别？

本地轻量工具注册表就是应用内的 tool catalog，存工具名、参数 schema、权限、路由和描述，用来快速注册和调用内部函数或 API。MCP 是跨平台标准化协议，强调统一连接、能力暴露和上下文交互；我们这个更轻，不追求互通，只求开发快、上线稳。

回答要点
  1. 说明本地注册表核心字段（name/schema/perm/route/desc）
  2. 指出其目标是快速集成内部能力
  3. 对比 MCP 强调跨客户端互通性
