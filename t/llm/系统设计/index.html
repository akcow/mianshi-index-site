你的上下文压缩怎么做的？

分三步：先用AST解析提取代码关键节点（函数签名、调用链）；再用语义聚类合并相似日志片段；最后用轻量RAG索引，只保留触发条件和错误码，原始文件走按需加载。不是全文摘要，而是结构化裁剪。

回答要点
  1. AST解析用于代码结构压缩
  2. 语义聚类用于日志去重
  3. RAG索引+按需加载应对超长文件
完整解析（含追问与踩坑）→
设计一个RAG服务的在线问答链路，要求支持大模型故障时的降级策略。

我把链路拆成query rewrite→embedding→召回→rerank→prompt构造→LLM调用。LLM故障时，我会降级：首token超3秒就熔断，改用缓存答案或摘要；全局并发限流到100QPS；热门问题预缓存结果；最后兜底返回检索到的文档列表，保证用户始终有信息可看，而不是空白页。

回答要点
  1. 必须分层定义各环节超时（如embedding 1s、LLM首token 3s）
  2. 必须有熔断+重试+jitter组合策略
  3. 必须提供非LLM兜底方案（摘要/文档列表/缓存答案）
  4. 必须隔离LLM连接池和熔断器，避免拖垮检索链路
完整解析（含追问与踩坑）→
记忆你提到有两块，具体是什么？

一块是用户级记忆，存长期偏好、技术栈习惯、常用工具链配置，跨项目持久化；另一块是项目级记忆，存当前代码库结构、依赖关系、近期修改痕迹，随项目上下文动态加载和淘汰。

回答要点
  1. 明确区分用户级（跨项目）和项目级（单项目）
  2. 各举一个典型存储内容例子
  3. 点出两者生命周期差异（持久化 vs 动态淘汰）

这个项目是做什么的？

这是一个面向开发者提效的 Coding Agent，它能理解用户自然语言指令，自动拆解任务、调用工具链（如代码搜索、执行、调试），最终生成可运行代码。不是端到端生成，而是分层可控的智能协作代理。

回答要点
  1. 明确说出目标用户（开发者）
  2. 点出核心能力（任务拆解+工具调用+代码生成）
  3. 强调与纯LLM生成的本质区别（可控性、可调试、分层）

你写了五层架构，是哪五层？

最上是用户交互层，处理自然语言输入和结果渲染；第二是任务规划层，把指令拆成子任务序列；第三是工具调度层，决定调哪个MCP、传什么参数；第四是记忆管理层，区分用户级和项目级上下文；最下是执行层，对接代码搜索、执行沙箱等具体工具。

回答要点
  1. 准确列出五层名称及顺序
  2. 每层用一句话说明核心职责
  3. 指出层间数据流（如规划层输出→调度层输入）

为什么要分用户级和项目级？

不分层的话，每次都要把所有历史项目细节塞进上下文，很快超限；而且用户A的私有配置不该泄露给项目B；更重要的是，用户习惯（比如偏爱Go而非Python）要全局生效，而项目结构只在当前上下文有用。

回答要点
  1. 指出上下文长度瓶颈
  2. 说明安全/隐私隔离需求
  3. 强调个性化（用户级）vs 场景化（项目级）的不可替代性

你的 MCP 是怎么设计的？

MCP是Model-Centric Plugin，每个工具封装成独立服务，带标准元数据：名称、描述、输入Schema、输出Schema、调用协议。主Agent通过tool_search接口按关键词检索，拿到完整定义后再构造调用请求，支持热插拔和版本管理。

回答要点
  1. 说明MCP是独立服务而非函数
  2. 点出元数据四要素（名/描/入/出）
  3. 强调tool_search作为统一发现入口
完整解析（含追问与踩坑）→
多 Agent 应该怎么拆分？

按MECE原则拆：Plan Agent专责任务分解和优先级排序；Code Agent只管生成和修复；Test Agent负责单元测试生成和执行；Deploy Agent处理环境配置和灰度发布。每个Agent有独立内存、工具集和失败回滚策略，不共享状态。

回答要点
  1. 给出四个以上职责分明的Agent角色
  2. 说明拆分依据（MECE/故障隔离）
  3. 强调各自独立内存和工具集

你收到一条告警'某个接口发生了N次500错误'，你的告警分析 Agent 怎么处理？

第一步查指标：确认500突增是否真实；第二步捞日志：按traceID聚合错误堆栈；第三步查链路：看上游调用是否超时、下游是否拒绝；第四步查CMDB：确认该接口所属服务最近是否有发布。最后用RAG召回历史类似case的解决方案。

回答要点
  1. 指标→日志→链路→CMDB四步递进
  2. 每步说明查什么（如'查traceID聚合堆栈'）
  3. 结尾用RAG复用历史经验

举个例子：我要写个登录系统的注册流程，Coding Agent怎么组织？

第一步用Swagger解析现有API文档提取注册字段；第二步调用代码生成工具产出Gin路由+MySQL建表SQL；第三步启动Postman自动化校验；最后用Diff工具比对生成代码与历史风格。整个过程由框架根据工具元数据自动编排，无需人工写胶水代码。

回答要点
  1. 明确各步骤对应的具体工具及输入输出
  2. 说明框架如何判断执行顺序和依赖关系
  3. 指出异常时的fallback机制（如Swagger解析失败则启用字段手动标注）

agent loop 为什么会死循环，怎么防护？

死循环常因目标模糊、工具返回信息不足、模型反复选同一工具或缺少停止条件。我加最大轮数、工具调用次数限制、重复动作检测、token预算控制，还设失败阈值和人工确认开关。

回答要点
  1. 准确归因三类典型死循环原因
  2. 防护手段覆盖硬限制（轮数/次数）、软检测（重复/预算）、人工兜底
  3. 强调stop condition显式定义
完整解析（含追问与踩坑）→
请介绍你做的Agent或Demo项目的核心模块，包括总线、Session、记忆设计和失败恢复机制。

我拆成七个模块：任务入口、规划器、工具层、事件总线、Session管理、记忆系统、执行器。事件总线串起模型推理、工具调用和用户输入；Session存对话上下文；记忆沉淀用户偏好和历史决策；失败恢复靠重试+断点续跑+执行轨迹记录+人工接管入口。

回答要点
  1. 明确列出核心模块（至少5个）
  2. 事件总线承担解耦和状态同步职责
  3. Session管理单次任务上下文
  4. 记忆系统支持长期知识沉淀
  5. 失败恢复含自动重试、断点续跑、轨迹记录、人工入口

当模型输出不稳定时，工程上有哪些处理手段？

我分三层处理：输入层用few-shot+低temperature+结构化prompt约束；输出层强制JSON Schema校验+规则后处理+rerank；关键链路加兜底策略——校验失败自动重试、触发人工确认、记录完整trace供回放。工具调用还额外加幂等ID和失败原因标记。

回答要点
  1. 输入层：few-shot/temperature/prompt结构化
  2. 输出层：Schema校验+规则后处理+rerank
  3. 兜底层：重试+人工确认+完整trace记录
  4. 工具调用需幂等ID和失败归因标记

你可以讲一下从在聊天框向AI提问、敲下回车到看到回答的整个过程经历了哪些步骤吗？

  1. 覆盖请求入口→网关→业务服务→模型调用→安全→输出的全链路
  2. 指出关键环节（如prompt组装、流式解析、安全审核）
  3. 提及容错机制（重试、降级、兜底）

工作流、单智能体、多智能体系统之间的区别是什么？

工作流是固定步骤的线性编排，比如先搜再总结再推送；单智能体是单一 LLM 实例+记忆+工具，所有决策由它闭环完成；多智能体则是多个角色化 agent 通过 message 通信协作，比如 researcher、writer、reviewer 各司其职，状态不共享，需显式协调。

回答要点
  1. 指出工作流无自主决策，依赖预设流程
  2. 强调单智能体共享全局状态和 memory
  3. 点明多智能体间需通信协议且角色职责分离
完整解析（含追问与踩坑）→
如何设计 Agent/LLM 聊天的断点续传？大模型流式传输如何借鉴 TCP 机制保证可靠性与有序性？

我会用会话 ID + 消息序号 + 服务端快照存储实现断点续传；流式传输借鉴 TCP 的序列号、ACK 确认和重传机制，在客户端缓存未确认 chunk，服务端按序生成并标记 offset，配合超时重发和去重逻辑保障有序可靠。

回答要点
  1. 明确会话状态需持久化（ID+last_offset+context_snapshot）
  2. 流式 chunk 需带唯一序号和校验码
  3. 客户端实现滑动窗口缓存与重传，服务端支持按序重发与幂等响应
完整解析（含追问与踩坑）→
Agent有没有熔断机制？比如基模卡死，后端是否有保底机制？

工具调用层做了三次失败熔断；基模卡死时用LLM集群兜底，单节点故障自动切到备用服务器，同时降级为规则引擎处理简单查询。

回答要点
  1. 明确工具层熔断阈值（三次）
  2. 提出集群化LLM服务方案
  3. 补充降级策略（规则引擎兜底）
