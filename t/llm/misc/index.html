向量数据库在 RAG 中后续还有哪些需求？

向量数据库不会被取代，但角色会更聚焦：它适合企业级多语言语义查询、跨文档关联、海量增量索引和高并发权限过滤。而小规模代码库或 Markdown 知识库，关键词、AST 索引、page index 更高效。未来 RAG 的能力上限，取决于混合检索栈——向量只是其中一层。

回答要点
  1. 明确区分适用场景（企业级 vs 个人/代码库）并给出典型判据
  2. 指出向量库不可替代的 2 项高阶需求（如跨文档关联、权限过滤）
  3. 强调混合检索是趋势，并点出其他必要组件（如 AST 索引、BM25）

如果通过模型判断需要回退的节点，如何控制成本和稳定性？

绝不把全图扔给模型！先用规则和依赖图粗筛候选节点，只把 diff、上下文摘要和关键约束喂给模型。要求模型输出结构化 JSON（affected_nodes, reason, confidence），低置信度走保守回退或人工确认。还要记录每次判断与真实结果，持续回归评测。

RAG 是什么？请讲讲 RAG 的完整流程。

RAG是检索增强生成，用来让大模型结合私有知识回答。流程分两步：离线时把文档切块、向量化、存进向量库；在线时用户提问，先把问题向量化，在向量库检索最相关片段，拼成新prompt喂给大模型，模型结合这些真实资料生成答案，避免胡编。

回答要点
  1. 定义点明‘缓解幻觉/知识截止’
  2. 离线阶段含‘分块-向量化-入库’三步
  3. 在线阶段含‘问题向量化-检索-拼接prompt-生成’四步

模型上下文窗口是什么？

上下文窗口就是模型单次能处理的最大token数，包括你的提问、历史对话、以及它自己的回答。比如4K窗口，你输3.5K token的问题，它最多只能输出500个token。超了就会截断或报错，长文档、多轮对话必须时刻盯着这个限额。

回答要点
  1. 明确定义为‘输入+输出总token上限’
  2. 举例说明超限后果（截断/报错）
  3. 点出典型场景（长对话/长文档）
完整解析（含追问与踩坑）→
假设用户觉得回答不准，有什么排查和优化思路吗？

先分三层归因：输入层（用户query歧义、历史丢失）、Prompt层（system指令模糊、few-shot示例差）、模型层（领域适配弱）。优化优先级：1. 改prompt加约束（如‘只答事实，不确定就说不知道’）；2. 加query改写模块；3. 小样本微调——绝不一上来就重训大模型

  2. 给出prompt优化的具体动作（如加约束指令）
  3. 强调低成本优先（改prompt > 微调 > 重训）

Chunk 切片粒度太大或太小分别会导致什么问题？

粒度太大（如整页 PDF）会让 embedding 混淆无关信息，降低关键词匹配精度，还可能超出 LLM 上下文窗口；粒度太小（如单句）会割裂语义连贯性，导致关键实体分散，向量无法表征完整意图，召回时容易漏掉上下文依赖的答案。

回答要点
  1. 粒度大→语义混杂+超长截断
  2. 粒度小→语义碎片化+实体丢失
  3. 各举一个影响下游任务的具体表现
完整解析（含追问与踩坑）→
讲一下Function call、MCP、skill、rules、vibe coding、spec coding、harness engineering的概念以及解决了什么问题。

Function call是模型调用预定义工具API，解决确定性任务；MCP（Model Context Protocol）是标准化工具注册与调用协议，让不同模型能复用同一套工具；Skill是可组合的原子能力单元；Rules是硬性约束；Vibe coding靠提示词引导风格；Spec coding用结构化schema定义输入输出；Harness engineering指构建测试沙箱验证Agent行为。它们共同解决LLM不可控、难调试、难集成的问题。

回答要点
  1. Function call=调用API，MCP=工具通信协议
  2. Skill=可复用原子能力，Rules=不可违反约束
  3. Spec coding=Schema驱动，Harness=沙箱验证

大模型如何实现结构化输出？

我分三层：模型层用 JSON mode 微调或内置结构化能力；提示层强制 schema 描述 + 示例 + ‘只输出 JSON 不加解释’指令；代码层用 Pydantic 解析 + 异常捕获 + fallback 重试，比如解析失败时补全字段或调用函数校验，确保下游能稳定消费。

回答要点
  1. 必须包含模型能力、提示约束、后置校验三个层次
  2. 指出 JSON mode 并非所有模型原生支持，需确认 provider 文档
  3. fallback 策略需明确：是重试、降级为文本、还是调用确定性函数兜底

Agent架构 2 题

MCP、Skill、CLI 分别怎么理解？它们的区别是什么？

Skill是面向模型的原子能力说明书，比如‘用Python执行SQL’；MCP是标准化工具接入协议，让模型能统一调用不同系统；CLI是人机交互入口，属于执行层界面。三者分属知识层、协议层、交互层，不能混为一谈。

回答要点
  1. 明确区分Skill（能力描述）、MCP（通信标准）、CLI（操作界面）三层定位
  2. 指出Skill服务于模型推理，MCP解决跨系统互操作，CLI侧重用户/程序触发方式
  3. 举例说明三者不可替代性，如MCP不包含Skill语义，CLI不定义协议
完整解析（含追问与踩坑）→
对多 Agent 协作有什么理解？

多Agent协作不是简单堆叠，核心是任务拆解、角色隔离和结果仲裁。我实践过主Agent分发检索/编码/验证子任务，但发现状态共享和失败重试最难——比如一个Agent超时，其他Agent该等还是撤回？我们最后用轻量消息总线+超时兜底策略解决。

  2. 指出至少一个落地难点：状态同步、通信开销、冲突仲裁或失败传播
  3. 给出具体应对策略，而非泛泛而谈‘加监控’或‘做重试’

了解不了解Agent？

Agent不是更聪明的聊天机器人，它是‘目标驱动的自主工作流’：LLM负责拆解任务（比如‘订机票’→查天气→比价→填表），Tool Use调用API执行（航司接口、支付SDK），Planning模块做状态追踪和失败重试。关键在闭环——它得知道自己做到哪步了、下一步该调哪个工具、错了怎么回滚。现在主流框架像LangGraph，就是用图节点编排这个闭环。

回答要点
  1. 明确定义Agent=LLM+Tools+Planning三要素
  2. 举例说明‘目标驱动’与‘状态闭环’的必要性
  3. 指出1个主流实现框架（如LangGraph/LangChain）及其解决的问题
