其他题目 11 题

输入一个URL到网页加载之间发生了什么？

先DNS解析域名得IP；再TCP三次握手建连；然后TLS握手加密；接着HTTP发GET请求；服务器返回HTML，浏览器解析构建DOM树，下载CSS/JS，执行渲染流水线：样式计算、布局、绘制、合成；过程中可能触发重定向、缓存协商、预加载等优化。

回答要点
  1. DNS→TCP→TLS→HTTP四层递进
  2. 浏览器解析HTML时的阻塞与异步行为
  3. 关键渲染路径中layout/paint/composite分工
展开讲讲

DNS解析若采用递归查询但未启用缓存，每次请求都需遍历根→TLD→权威服务器，平均耗时可达100–300ms；而浏览器和OS级DNS缓存（遵循RFC 1034 §4.3.3中TTL语义）可将重复域名解析降至微秒级。TCP三次握手在高延迟链路（如跨太平洋）中引入至少2×RTT开销，HTTP/2默认要求TLS且强制使用TCP Fast Open（RFC 7413 §2.1），但若服务端未开启TFO或SYN Cookie干扰，首包仍需完整握手。TLS 1.3将密钥交换压缩至1-RTT（RFC 8446 §2.1），相比TLS 1.2的2-RTT显著缩短加密建立时间；若降级到TLS 1.2且未启用会话复用（RFC 5246 §7.4.1），则每次新建连接需完整证书验证与密钥协商。HTML解析中script标签默认同步阻塞（HTML Standard §12.2.5.4），但<script async>仅对非模块脚本生效（HTML Standard §12.2.5.5），而<script type="module">默认异步且自动defer（HTML Standard §12.2.5.7），此行为差异源于模块脚本的严格依赖图解析机制。

$ systemd-resolve --statistics | grep "Cache hits"
// TLS 1.3握手确认（OpenSSL）
$ openssl s_client -connect example.com:443 -tls1_3 2>/dev/null | grep "Protocol"

怎么理解长连接和短连接的区别？

短连接是一次请求响应完就断开，比如传统HTTP/1.0；长连接是建立一次后复用多次收发，像HTTP/1.1默认的Keep-Alive，核心区别在于是否跨请求维持TCP连接状态，这直接影响服务端资源开销和适用场景。

回答要点
  1. 明确点出‘是否跨多次通信复用TCP连接’是本质区别
  2. 指出短连接无状态、实现简单，长连接需维护状态、心跳和超时清理
  3. 各举一个典型场景：短连接用于普通网页请求，长连接用于IM或实时推送
完整解析（含追问与踩坑）→
了解HTTP的缓存吗？

分强缓存和协商缓存：强缓存用Cache-Control/max-age，命中直接读本地副本；协商缓存用ETag/Last-Modified，发请求带If-None-Match/If-Modified-Since，服务端比对后返回304告诉浏览器用缓存。关键看响应头是否含Cache-Control。

回答要点
  1. 区分强缓存（Cache-Control）与协商缓存（ETag+304）
  2. 说出304状态码含义及触发条件
  3. 指出强缓存优先级高于协商缓存
完整解析（含追问与踩坑）→
Socket、TCP、UDP 分别能解决什么问题？

Socket是应用层调用网络的编程接口；TCP提供可靠、有序、面向连接的字节流，适合HTTP、数据库这类不能丢数据的场景；UDP提供无连接、低延迟的报文传输，适合DNS查询、音视频推流这种可容忍丢包但怕延迟的场景。

回答要点
  1. Socket定位：API接口层
  2. TCP核心特性：可靠/有序/连接
  3. UDP核心特性：无连接/低延迟/报文
完整解析（含追问与踩坑）→
SSE 的原理是什么？如果不用 SSE 还有什么方法能立即推送？

SSE 是服务器通过持久 HTTP 连接单向推送文本事件，基于 text/event-stream MIME 类型，客户端用 EventSource API 接收；替代方案有 WebSocket（双向、低延迟）、长轮询（兼容老浏览器但开销大）、WebRTC DataChannel（P2P 场景），选型要看是否需要双向、兼容性和运维成本。

回答要点
  1. 说明 SSE 单向、HTTP 持久连接、text/event-stream 核心机制
  2. 列出 WebSocket / 长轮询 / WebRTC 三个替代方案
  3. 点出各方案关键差异（双向性、兼容性、复杂度）
完整解析（含追问与踩坑）→
实现 HTTP 206 Partial Content 响应。

接收 Range 请求头，解析 start-end 字节范围；校验范围合法性（不越界、end>=start）；读取文件对应片段；返回 206 状态码，Content-Range 头填 ‘bytes start-end/total’，Content-Length 设为片段大小，最后写入二进制数据流。注意处理单字节范围和多范围请求。

回答要点
  1. 正确解析 Range 头并提取字节区间
  2. 校验范围有效性（含 end==start 和越界）
  3. 设置正确的 Content-Range 和 Content-Length 响应头

HTTP 报文是怎么组成的？

HTTP 报文分请求和响应两类。请求报文四部分：请求行（比如 GET /api HTTP/1.1）、请求头（Host、User-Agent 等键值对）、空行（CRLF）、可选的请求体（如 POST 的 JSON）。响应报文也是四部分：状态行（HTTP/1.1 200 OK）、响应头（Content-Type、Set-Cookie 等）、空行、响应体（HTML 或 JSON 数据）。HTTP/2 虽改用二进制帧，但语义结构仍对应。

回答要点
  1. 完整列出请求/响应报文的四段式结构
  2. 举例说明请求行和状态行格式
  3. 指出空行是 CRLF 分隔符
完整解析（含追问与踩坑）→
介绍一下 400、499 状态码。

400 Bad Request 表示客户端请求语法错误，比如 JSON 格式错、必填参数缺失。499 是 Nginx 扩展码，表示客户端在服务端响应前主动断开连接，常见于前端取消请求、超时或网络中断。

回答要点
  1. 准确解释 400 的客户端错误本质
  2. 说明 499 是 Nginx 特有且代表 client closed
  3. 各举一个真实发生场景

WebSocket 和 HTTP 的区别是什么？

HTTP 是无状态、短连接、请求-响应模型；WebSocket 是全双工、长连接、服务端可主动推送。HTTP 基于 TCP，每次交互需完整握手；WebSocket 通过 HTTP Upgrade 协议升级连接，之后复用 TCP 连接双向通信。

回答要点
  1. HTTP：无状态、请求响应、短连
  2. WebSocket：全双工、长连接、服务端可推
  3. 建立方式：WebSocket 通过 HTTP Upgrade 升级
完整解析（含追问与踩坑）→
WebSocket 是怎么建立连接的？

客户端先发 HTTP GET 请求，带 Upgrade: websocket 和 Sec-WebSocket-Key 头；服务端校验后返回 101 Switching Protocols 响应，含 Sec-WebSocket-Accept 头，该值是 key 经固定算法哈希生成；之后 TCP 连接升级为 WebSocket 连接，开始帧通信。

回答要点
  1. 客户端发 Upgrade 请求 + Sec-WebSocket-Key
  2. 服务端回 101 + Sec-WebSocket-Accept 认证
  3. Sec-WebSocket-Accept 是 key 与固定字符串拼接后 SHA1 base64
完整解析（含追问与踩坑）→
HTTP如果访问不了，如何检测哪里出了问题？

我一般四步查：第一ping域名看DNS和基础连通性；第二curl -v加目标URL，看是否卡在TCP握手或收到HTTP状态码；第三用telnet或nc测目标IP+端口，确认服务端口是否开放；第四查浏览器开发者工具Network面板，看是DNS失败、连接超时还是返回502/503。每步都能定位一层——比如ping通但curl超时，基本就是服务没起来或防火墙拦了。

回答要点
  1. 覆盖DNS解析、TCP连接、HTTP协议、服务状态四层检查
  2. 准确说出至少两个命令及其关键参数（如curl -v、telnet host port）
  3. 能根据现象反推故障层级（如ping通但curl失败→端口或应用层问题）

HTTPS 与 TLS 4 题

HTTP 和 HTTPS 有什么区别？
回答要点
  1. HTTPS = HTTP + TLS，默认 443 端口
  2. HTTP 明文传输，HTTPS 加密，防窃听、防篡改、防冒充
  3. HTTPS 通过证书链验证服务端身份，HTTP 没有身份验证
  4. 代价：握手增加 RTT，有加解密开销，需要证书维护
展开讲讲
HTTPS 的证书链验证机制依赖于信任锚（trust anchor）——即操作系统或浏览器内置的根证书颁发机构（CA）公钥。客户端收到服务器证书后，逐级向上验证签名：用上级证书的公钥解密当前证书的签名，比对摘要值；若匹配，则继续用再上级证书验证该上级证书，直至到达一个受信根证书（RFC 5280 §6.1）。若缺少任一环节（如中间证书未发送、根证书不在信任库），验证失败，连接中止。例如 Nginx 配置中需显式拼接中间证书：ssl_certificate fullchain.pem;（其中 fullchain.pem = server.crt + intermediate.crt），否则 iOS 和 Java 客户端可能因无法构建完整链而报 CERTIFICATE_VERIFY_FAILED（Apple TLS Security Guidelines, 2023-04；OpenJDK 17 PKIXValidator 源码注释）。不这样做会导致部分客户端（尤其移动设备）TLS 握手失败，而非降级为 HTTP——协议层无回退机制（RFC 9110 §15.5 明确禁止 HTTP/HTTPS 自动降级）。TLS 1.3 进一步移除了重协商和降级信号，强化了前向安全性（RFC 8446 §1.3）。
完整解析（含追问与踩坑）→
HTTPS 的 TLS 加密是对称加密还是非对称加密。

TLS 是混合加密：握手阶段用非对称加密（RSA/ECDHE）交换密钥并认证身份；数据传输阶段用对称加密（AES/ChaCha20）加密 HTTP 报文。这样既保证安全又兼顾性能。

回答要点
  1. 明确分阶段说明：握手非对称、传输对称
  2. 指出非对称用于密钥交换和认证，对称用于数据加密
  3. 举例常见算法（ECDHE + AES）
完整解析（含追问与踩坑）→
HTTPS 是怎么加密的，为什么不是全程使用非对称加密？
回答要点
  1. 非对称加密只用于握手阶段协商出对称密钥，之后用对称加密传输
  2. 非对称加密计算开销大，比对称慢几个数量级，不适合传大量数据
  3. TLS 1.2 用 ECDHE 做密钥交换，TLS 1.3 精简为更少的握手往返
  4. 对称密钥是每次会话新生成的，泄露也只影响单次会话
完整解析（含追问与踩坑）→
浏览器输入网址到页面展示，中间经历了哪些完整过程？
回答要点
  1. URL 解析 → 缓存检查 → DNS 解析（浏览器/系统/递归）
  2. 建立 TCP 连接（三次握手），HTTPS 再加 TLS 握手
  3. 发送 HTTP 请求，服务端处理并返回响应
  4. 浏览器解析 HTML 构建 DOM、CSSOM，合成渲染树，布局、绘制、合成
  5. 连接复用或关闭，静态资源并行加载

应用层 3 题

应用层还有哪些协议？

除了HTTP，常见的还有：HTTPS（加密HTTP）、DNS（域名解析）、FTP（文件传输）、SMTP/POP3/IMAP（邮件收发）、SSH（安全远程登录）、WebSocket（全双工通信）。

  3. 避免混入传输层协议（如TCP）

DNS 是做什么的？

DNS（域名系统）是互联网的电话簿，负责把人类易记的域名（比如www.baidu.com）解析成机器可识别的IP地址（比如180.101.49.12），让客户端能准确找到目标服务器。

回答要点
  1. 明确类比为‘电话簿’或‘名字到地址的映射’
  2. 指出输入是域名、输出是IP地址
  3. 强调‘人类友好→机器可读’的转换目的
完整解析（含追问与踩坑）→
DNS 的流程是什么？

流程是：浏览器查本地缓存→查系统Hosts→查本地DNS服务器；若未命中，本地DNS递归查询根域名服务器→顶级域（如.com）→权威域名服务器，最终拿到IP并缓存返回。

回答要点
  1. 覆盖5个关键环节：浏览器缓存、Hosts、本地DNS、根、顶级域、权威
  2. 区分‘递归查询’（客户端发起）和‘迭代查询’（DNS服务器间）
  3. 点出结果会逐级缓存
