其他题目 12 题

TCP 为什么要四次挥手？如果省略第四次挥手，会有什么问题？

四次挥手因 TCP 全双工，双方需独立关闭发送方向。第一次 FIN 关 A→B 发送，第二次 ACK 确认，第三次 FIN 关 B→A 发送，第四次 ACK 确认。若省略第四次，B 不知 A 是否收到 FIN，可能重发 FIN，导致 A 无法进入 CLOSED，B 卡在 LAST_ACK，连接异常残留。

回答要点
  1. 说明全双工导致需双方独立关闭发送通道
  2. 准确描述四次交互中每次的发起方和含义
  3. 指出省略第四次会导致 B 卡在 LAST_ACK、A 无法释放资源
展开讲讲

TIME_WAIT状态必须持续2MSL（Maximum Segment Lifetime），是因为需要同时满足两个独立的安全目标：第一，确保主动关闭方发送的最后ACK能被被动方收到（若丢失，被动方会重传FIN，主动方需在TIME_WAIT内响应）；第二，确保网络中所有属于该连接的旧报文（尤其是延迟的FIN或数据）都已消亡，避免干扰新连接（新连接可能复用相同四元组）。若仅设为1MSL，则无法覆盖ACK丢失后被动方重传FIN的时间窗口——因为被动方在超时（约1MSL）后重传FIN，此时主动方若已离开TIME_WAIT，将响应RST，导致被动方连接异常终止（RFC 9293 §3.5, Figure 14）。MSL是IP层对报文生存时间的保守上限，TCP实现中Linux默认MSL=30s，故TIME_WAIT=60s。验证示例：ss -tan state time-wait | wc -l 可统计当前TIME_WAIT连接数；net.ipv4.tcp_fin_timeout 仅影响FIN_WAIT_2，不改变TIME_WAIT时长（Linux内核文档：networking/ip-sysctl.txt）。

四次挥手的ACK与FIN合并并非协议强制，而是TCP实现优化：当被动方在收到FIN后立即调用close()且无待发数据，内核可将ACK+FIN合并在一个报文中发出（即‘捎带’），这符合RFC 9293 §3.5关于‘sending an ACK and a FIN in the same segment is permitted’的规定。

TCP是怎么保证可靠传输的？

TCP靠八种机制协同保障可靠：序列号确保字节流有序；ACK确认应答反馈接收状态；超时重传应对丢包；快速重传加速丢包恢复；滑动窗口提升吞吐；流量控制防接收方溢出；拥塞控制适配网络状况；校验和检测传输错误。其中前四条解决‘传得准’，后四条解决‘传得稳’和‘传得快’。

回答要点
  1. 覆盖序列号、ACK、重传（含超时+快速）、滑动窗口
  2. 区分流量控制（接收方能力）和拥塞控制（网络状态）
  3. 强调校验和防错
  4. 指出机制间的协作关系
展开讲讲

TCP 选择累积 ACK 而非 NAK，根本原因在于网络丢包率低时 ACK 的带宽效率与实现鲁棒性更优：单个 ACK 可确认多个连续字节（如 ACK=1001 表示已成功接收序号 <1001 的所有数据），而 NAK 需为每个丢失段单独反馈，易引发反馈爆炸；RFC 9293 §3.5 明确要求 ’the receiver sends acknowledgments for the highest in-order sequence number received’，这是协议设计对典型互联网丢包模式（偶发、局部）的适配。若强制用 NAK，在高丢包场景下可能触发大量重复 NAK 冲突，且无法天然支持选择性确认（SACK）的扩展——SACK 正是作为 ACK 的增强而非替代被引入（RFC 2018）。TIME_WAIT 状态必须持续 2×MSL（Maximum Segment Lifetime），其核心作用是：(1) 确保网络中残留的旧连接报文（如延迟重传的 FIN 或数据）不会干扰新连接（RFC 9293 §3.5）；(2) 保证被动关闭方能收到最后 ACK 的确认，否则可能因 FIN 丢失导致对方卡在 LAST_ACK。Linux 默认 MSL=30s，故 TIME_WAIT 持续 60s（net.ipv4.tcp_fin_timeout 不影响此值，见 Linux kernel source net/ipv4/tcp.c 中 TCP_TIMEWAIT_LEN 定义）。

校验和仅覆盖 TCP 头部+数据+伪头部，不校验 IP 层以下，因此无法检测链路层 CRC 错误后的静默损坏——这正是应用层需额外校验（如 TLS record MAC）的原因（RFC 9293 §4.1）。

滑动窗口与拥塞控制解耦：接收窗口（rwnd）由接收方通告，纯流量控制；拥塞窗口（cwnd）由发送方根据网络反馈动态调整，二者共同决定实际发送上限（min(cwnd, rwnd)），此分离设计使 TCP 能同时响应接收方内存限制与网络瓶颈（RFC 5681 §3）。

超时重传（RTO）基于 RTT 采样动态估算，若固定超时（如统一设 1s）将导致高延迟链路过度重传或低延迟链路响应迟缓（RFC 6298 §2.2）。

快速重传依赖重复 ACK（≥3 个相同 ACK）触发，避免等待 RTO 超时，但若接收方禁用延迟 ACK（TCP_QUICKACK），可能减少重复 ACK 数量，影响其触发时机（RFC 1122 §4.2.3.2）。

校验和算法使用 16 位反码和（one’s complement sum），可检测所有单比特错误及多数多比特错误，但无法保证 100% 检错（RFC 793 §3.1）。

拥塞控制算法（如 Cubic、BBR）不改变 TCP 基础可靠机制，仅替换 cwnd 增长逻辑，体现 RFC 5681 允许‘congestion control algorithm’可插拔的设计哲学。

完整解析（含追问与踩坑）→
拥塞控制讲一下？

拥塞控制核心是通过cwnd动态调节发送速率。慢启动阶段cwnd指数增长，直到达到ssthresh；之后进入拥塞避免，cwnd线性增长；一旦收到3个重复ACK，触发快速重传并进入快速恢复，将ssthresh设为当前cwnd一半，cwnd设为ssthresh+3个MSS，再逐步恢复。关键是它始终在试探网络承载上限，和流量控制互不替代。

回答要点
  1. 准确描述慢启动、拥塞避免、快速重传/恢复三阶段行为
  2. 说明ssthresh的更新规则
  3. 强调cwnd与ssthresh的数值关系
  4. 点明与流量控制的本质区别
展开讲讲

TCP拥塞控制的核心设计动机是避免全局同步（global synchronization）和避免网络过载崩溃。若没有慢启动，所有连接初始即以高cwnd发送，会瞬间压垮瓶颈链路缓冲区，引发大量丢包与重传风暴——这正是1986年‘van Jacobson事件’中观察到的吞吐量骤降至5%的现象（RFC 896 §2.2）。慢启动通过指数增长cwnd（每收到一个ACK增1，每RTT翻倍）让发送方主动探测可用带宽，而非依赖丢包反馈；而拥塞避免阶段改为线性增长（每RTT仅增1 MSS），因此时已接近链路容量，线性步进可降低超调风险（RFC 5681 §3.2）。ssthresh设为丢包时cwnd的一半，是折中：太小导致带宽利用率低（如设为1/4），太大则易再次触发丢包（RFC 5681 §3.1）。快速重传不等待RTO超时，而是基于3个重复ACK触发，因重复ACK比超时更早、更可靠地指示单个分组丢失（RFC 5681 §3.2）。流量控制（rwnd）由接收方通告窗口决定，解决的是端系统处理能力问题；而拥塞控制（cwnd）由发送方根据网络反馈动态调整，解决的是中间网络资源竞争问题（RFC 793 §2.8, RFC 5681 §1）。

示例：Linux中启用CUBIC时，ssthresh更新逻辑为 ssthresh = max(2*SMSS, cwnd/2)（Linux kernel 6.1 net/ipv4/tcp_cubic.c）；BBR则完全弃用丢包信号，改用min_rtt和bw估算来驱动pacing rate（RFC 8985 §4.2）。

TCP为什么要三次握手，而不是两次？

两次握手无法防止旧SYN报文在网络中滞留后突然到达服务端，导致服务端误建连接并浪费资源；三次握手让客户端确认服务端收到了自己的SYN，也确认了服务端的SYN，双方都确保对方收发能力正常，且能同步初始序列号。

回答要点
  1. 解决‘已失效的连接请求’问题
  2. 双向确认收发能力
  3. 同步ISN（初始序列号）防数据混淆
展开讲讲

三次握手的设计源于 TCP 需要双向确认初始序列号（ISN）并防止历史报文干扰。若仅两次握手（SYN → SYN+ACK），服务端无法验证客户端是否成功接收了 SYN+ACK，即无法确认客户端的接收能力；此时若客户端未收到 SYN+ACK 而重发 SYN，服务端可能误建多个连接（RFC 9293 §3.5 明确指出：‘The three-way handshake is required to synchronize sequence numbers and prevent old duplicate segments from causing confusion’）。更关键的是，两次握手无法解决「网络中滞留的旧 SYN 报文」问题：假设某客户端上次连接的 SYN 因网络延迟迟到，服务端若仅凭该 SYN 就建立连接（分配 TCB、进入 ESTABLISHED），将导致状态不一致和资源泄漏——而三次握手中，客户端必须用 ACK 携带对服务端 ISN 的确认，服务端可据此校验该 ACK 是否对应本次握手（而非旧连接），从而拒绝过期请求（TCP RFC 9293 §3.5, §4.2.2.13）。最小示例：Linux 内核中 net.ipv4.tcp_syncookies=1 启用 SYN Cookie 时，服务端在 SYN+ACK 中将时间戳、MSS 等编码进初始序列号低 24 位，避免维护半连接队列（Linux Kernel Documentation: networking/ip-sysctl.txt）。

四次握手虽能进一步增强可靠性，但会增加 RTT 延迟且无实质收益：第三次 ACK 已完成双向 ISN 同步与接收确认，第四次纯属冗余，违背 TCP 设计目标 ‘minimize latency while ensuring reliability’（RFC 9293 §3.5）。

SYN Flood 攻击利用半连接队列耗尽资源，其本质是服务端为每个 SYN 分配内存（如 struct request_sock），而客户端不完成第三次 ACK。Linux 通过 SYN Cookie（tcp_syncookies=1）绕过队列分配，在 SYN+ACK 序列号中编码必要信息，使服务端无需保存半连接状态（RFC 4987 §3.1）。

半连接队列满时，内核默认丢弃新 SYN（除非启用 SYN Cookie），并可能发送 RST 或静默丢包，具体行为由 net.ipv4.tcp_abort_on_overflow 和 tcp_syncookies 共同决定（Linux Kernel Documentation: networking/ip-sysctl.txt）。

完整解析（含追问与踩坑）→
挥手中的 `TIME_WAIT` 是做什么用的？

TIME_WAIT 有两个硬作用：一是保证最后那个 ACK 丢了能重传，让被动关闭方可靠进入 CLOSED；二是等网络中所有属于旧连接的延迟报文自然消失，避免它们干扰新连接——特别是当新连接复用相同四元组时。

回答要点
  1. 明确写出两个作用：ACK 重传保障 + 旧报文清理
  2. 点出‘四元组复用’这个触发场景
  3. 强调这是主动关闭方必须承担的状态
展开讲讲

TIME_WAIT 的 2MSL 持续时间（通常为 60 秒）直接源于 TCP 协议对网络最大报文生存期（Maximum Segment Lifetime, MSL）的保守估计。RFC 9293 §3.5 明确规定：TIME_WAIT 状态必须持续至少 2×MSL，以确保两个目的：一是让主动关闭方能重传最后的 ACK（若丢失，被动方会重发 FIN，此时主动方仍处于 TIME_WAIT 可响应）；二是保证该连接的所有旧报文在网络中彻底消亡，避免其在新连接（相同四元组复用时）被误收——若时间不足，残留报文可能被当作新连接的数据或 ACK，破坏可靠性。Linux 内核将 MSL 硬编码为 30 秒（net/ipv4/tcp_timer.c 中 TCP_TIMEWAIT_LEN 定义），故 TIME_WAIT 固定为 60 秒；可通过 net.ipv4.tcp_fin_timeout 调整（仅影响非标准路径，如连接异常终止），但不能缩短标准 TIME_WAIT 时长，因违反 RFC 9293 §3.5 对 2MSL 的强制要求。禁用 net.ipv4.tcp_tw_reuse 或 tcp_tw_recycle（后者已在 Linux 4.12+ 移除）并不能跳过 2MSL，仅影响 TIME_WAIT 套接字是否可被快速重用，而重用前提仍是其已自然超时或满足严格时间戳验证（RFC 1323 §4.1）。

示例：sysctl -w net.ipv4.tcp_fin_timeout=30 不改变 TIME_WAIT 时长，仅影响 FIN_WAIT_2 等状态超时；真正控制 TIME_WAIT 行为的是 net.ipv4.tcp_tw_reuse = 1（需 net.ipv4.tcp_timestamps = 1）——它允许内核在时间戳严格递增前提下复用处于 TIME_WAIT 的端口（Linux 内核文档 Documentation/networking/ip-sysctl.txt）。

流量控制和拥塞控制的区别是什么？

流量控制是点对点的，接收方通过窗口字段告诉发送方‘我还能收多少’，防接收方缓冲区溢出；拥塞控制是全局的，发送方通过慢启动、拥塞避免等算法感知网络状况，防路由器队列过载。前者看接收方能力，后者看网络链路状态。

回答要点
  1. 明确流量控制主体是接收方，拥塞控制主体是发送方
  2. 指出流量控制依赖rwnd字段，拥塞控制依赖cwnd计算
  3. 区分二者目标：防接收方溢出 vs 防网络中间节点拥塞

TCP payload 常见最大值是 MSS，通常为多少字节？

TCP payload 常见最大值就是 MSS，计算方式是链路 MTU 减去 IP 头（20 字节）和 TCP 头（20 字节），以太网下 MTU=1500，所以 MSS 通常是 1460 字节；这是避免 IP 层分片的关键阈值。

回答要点
  1. 明确 MSS 是 TCP payload 最大值，不含头
  2. 准确写出 1500−20−20=1460 的计算过程
  3. 点明 MSS 的核心目标是避免 IP 分片

请描述 TCP 连接建立的三次握手过程。

客户端发 SYN，服务端回 SYN+ACK，客户端再发 ACK。三次之后双方都进入 ESTABLISHED 状态。SYN 消耗一个序号，ACK 不消耗，所以第二次回复是 SYN+ACK，第三次只确认不带 SYN。

回答要点
  1. 明确说出三步报文及标志位（SYN、SYN+ACK、ACK）
  2. 指出每步对应的状态变化（SYN_SENT → SYN_RCVD → ESTABLISHED）
  3. 说明 SYN 消耗序号而 ACK 不消耗

TCP 挥手时，为什么不能将 ACK 和 FIN 合并在一次报文中发送？

因为收到 FIN 只代表对方不再发数据，但本端可能还有未发送完的应用数据。必须先 ACK 确认收到 FIN，等自己应用层写完、调用 close 后，才能发自己的 FIN。强行合并会丢数据或违反半关闭语义。

回答要点
  1. 指出 ACK 是对对方 FIN 的响应，FIN 是本端主动关闭信号
  2. 强调应用层数据可能尚未发完
  3. 说明合并会导致无法支持半关闭（shutdown(SHUT_WR)）

TCP 粘包是什么，为什么会粘包，怎么解决？
回答要点
  1. TCP 面向字节流，没有消息边界，多次 send 可能被合并或拆分
  2. Nagle 算法和接收缓冲区都会加剧这一现象
  3. 解决：固定长度、分隔符、长度前缀（最常见）
  4. 本质是应用层要自己定义消息边界，不是 TCP 的缺陷
