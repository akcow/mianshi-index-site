其他题目 5 题

视频流系统某一天突然很卡，从用户角度看网络延迟很高，站在你的视角怎么排查？排查逻辑是什么？

我按链路分五层查：先看用户侧监控（地域耗时、首包时间）；再查网关QPS和P99；接着看服务CPU、GC、goroutine堆积；然后盯Redis命中率、慢查询、连接池打满；最后查MySQL慢SQL、主从延迟、CDN下载耗时。每层用指标交叉验证，比如Redis命中率骤降+服务GC飙升，大概率是大Key引发OOM。

回答要点
  1. 清晰分层（用户→网关→服务→中间件→存储/CDN）
  2. 每层列出1–2个关键指标（如Redis命中率、MySQL主从延迟）
  3. 体现指标关联分析（如命中率下降+GC飙升指向大Key）
完整解析（含追问与踩坑）→
告警分析的数据源有哪些？

核心是日志系统（如ELK）和指标系统（如Prometheus），还有链路追踪（Jaeger/SkyWalking）提供调用路径，以及CMDB提供服务拓扑关系。告警本身来自Alertmanager，但根因分析必须融合这四类数据。

回答要点
  1. 列出日志、指标、链路追踪、CMDB四类
  2. 各举一个典型系统（ELK/Prometheus等）
  3. 点明告警源（Alertmanager）与根因数据源的区别
完整解析（含追问与踩坑）→
如果是网络慢，有什么优化思路吗？

四招：1. 升级HTTP/3减少握手延迟；2. 模型服务部署到离用户近的边缘节点（如微信CDN）；3. 前端开启TCP Fast Open和QUIC连接复用；4. 对非敏感query启用HTTP缓存，比如常见FAQ直接返回缓存答案

回答要点
  1. 提出协议升级（HTTP/3或QUIC）
  2. 给出就近部署方案（边缘节点）
  3. 说明连接复用或缓存等具体技术
完整解析（含追问与踩坑）→
HTTP 和 TCP 分别是在什么层的协议？

HTTP是应用层协议，负责定义客户端和服务器之间如何交换超文本数据；TCP是传输层协议，提供可靠的、面向连接的字节流传输服务，为HTTP等上层协议兜底。

回答要点
  1. HTTP明确归为应用层
  2. TCP明确归为传输层
  3. 点出二者上下依赖关系（HTTP跑在TCP之上）
完整解析（含追问与踩坑）→
HTTP、TCP、IP 与网络问题排查

IP管网络层寻址路由，TCP在IP上建可靠连接，三次握手、序号确认、滑动窗口保证有序可靠；HTTP是应用层协议，跑在TCP上。排查时分层：先curl -v看DNS、连接、TLS、状态码；状态码4xx看参数或权限，5xx查服务日志；再用ss看端口监听和连接数，用tcpdump抓包确认握手是否完成、有没有重传。比如502通常是反向代理连不上上游，得查上游服务是否存活。

回答要点
  1. 清晰描述IP/TCP/HTTP三层职责和依赖关系
  2. 给出分层排查的具体命令和判断依据（如curl/ss/tcpdump）
  3. 用典型状态码（401/429/502）说明定位思路
完整解析（含追问与踩坑）→

DNS 2 题

DNS解析的完整过程是怎样的？

浏览器查本地host→查本机DNS缓存→查ISP DNS递归服务器；递归服务器先查根域名服务器（.）→查顶级域（.com）→查权威域名服务器（xxx.com）→返回A记录；全程涉及UDP53端口，超时换TCP；结果带TTL，各级缓存按TTL失效。

回答要点
  1. 明确递归查询由本地DNS发起，根→顶级→权威的迭代路径
  2. 指出TTL控制缓存生命周期，非永久
  3. 说明UDP为主、TCP为备的传输机制
完整解析（含追问与踩坑）→
什么是域名解析？它和IP地址的关系是什么？

域名解析就是把人类易记的域名（如www.example.com）转换成机器可识别的IP地址（如192.0.2.1）的过程；它是应用层服务，依赖DNS协议和分布式服务器体系；没有域名解析，用户只能记IP访问网站，IP是网络层寻址依据，域名是它的抽象别名。

回答要点
  1. 明确定义：域名→IP的映射过程
  2. 指出DNS是应用层协议，运行在UDP/TCP之上
  3. 强调域名是IP的语义别名，非替代关系
完整解析（含追问与踩坑）→

传输层 2 题

UDP和TCP的主要区别是什么？

TCP面向连接、可靠、有序、有流量控制和拥塞控制，适合HTTP/FTP等；UDP无连接、不可靠、无序、无控制，但开销小、延迟低，适合DNS、视频流、游戏。TCP通过三次握手建连、四次挥手断连；UDP直接发包，不保证到达。

回答要点
  1. 必须涵盖连接性、可靠性、有序性、控制机制四维度
  2. 各举一个典型应用案例
  3. 指出头部开销差异（TCP20字节 vs UDP8字节）
完整解析（含追问与踩坑）→
TCP 和 UDP 属于哪一层的协议？它们的主要区别是什么？

TCP和UDP都属于传输层协议。TCP是面向连接、可靠、有序、有流量和拥塞控制的协议，适合金融、HTTP等要求不丢不乱的场景；UDP是无连接、不可靠、无序、低开销的协议，适合直播、语音通话等容忍丢包但追求低延迟的场景。

回答要点
  1. 明确指出二者均在传输层
  2. 对比连接性（有/无）、可靠性（确认重传/无保障）、有序性（保证/不保证）
  3. 各举一个典型业务场景
完整解析（含追问与踩坑）→

浏览器原理 2 题

一个网址从输入到渲染的过程是怎样的？

分五步：1. DNS解析域名得IP；2. TCP三次握手建连；3. 发送HTTP/HTTPS请求；4. 服务端返回HTML，浏览器解析构建DOM/CSSOM，合并成渲染树；5. 布局、绘制、合成上屏。中间穿插预加载、JS阻塞、重排重绘等关键影响点。

回答要点
  1. 完整覆盖DNS→TCP→HTTP→解析→渲染五大阶段
  2. 指出关键阻塞点（如JS执行阻塞解析）
  3. 提及渲染树生成需DOM+CSSOM合并
完整解析（含追问与踩坑）→
了解浏览器的渲染流程吗？

核心三阶段：Layout计算每个元素位置大小；Paint将样式转为图层像素；Composite合成图层上屏。关键优化点：CSS触发重排（如width）比重绘（如color）代价高；will-change提示浏览器提前升层；GPU加速依赖Composite阶段。

回答要点
  1. 准确说出Layout/Paint/Composite三阶段名称和作用
  2. 区分重排与重绘的触发属性（如width vs color）
  3. 提到至少一个性能优化手段（如图层分离、will-change）
完整解析（含追问与踩坑）→

消息队列 2 题

RabbitMQ 的生产消费模型是什么？

四步走：Producer发消息到Exchange，Exchange按routing key和Binding规则路由到Queue，Consumer从Queue拉取消息，处理完发ack确认。关键要记住Exchange是路由中枢，Queue才是实际存储，Consumer必须主动拉取或订阅。

回答要点
  1. 完整说出Producer→Exchange→Queue→Consumer链路
  2. 强调Exchange的路由决策作用（非直连Queue）
  3. 指出Consumer需显式ack，否则消息可能重复投递
完整解析（含追问与踩坑）→
RabbitMQ 如何保证顺序消费？

RabbitMQ本身只保证单Queue内入队顺序，不保证消费完成顺序。我们做法是：用一致性哈希把同一业务ID的消息路由到固定Queue，再配单Consumer；若必须多Consumer，则在消费端用内存队列按ID串行处理。但得提醒面试官——强顺序往往牺牲吞吐，建议先评估业务是否真需要全局有序。

回答要点
  1. 承认RabbitMQ天然不保证消费完成顺序
  2. 给出至少一种可行方案（单队列单消费者 或 消费端内存排序）
  3. 指出方案代价：吞吐下降/延迟增加/复杂度上升
