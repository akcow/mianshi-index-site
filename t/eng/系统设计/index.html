发件箱模式（Outbox）是如何解决业务数据落库与消息投递之间的一致性问题的？

我用发件箱模式把业务写库和消息记录放在同一个MySQL本地事务里，事务提交成功时，业务数据和outbox消息一定同时存在；再由独立worker异步扫描outbox表投递MQ。这样既避免了两阶段提交，又保证了至少一次投递，消费端靠message_id幂等去重。

回答要点
  1. 业务表和outbox_messages必须同事务提交
  2. worker需支持并发抢任务（如SELECT ... FOR UPDATE SKIP LOCKED）
  3. 投递失败必须指数退避+最大重试次数+死信归档
  4. 生产侧用message_id唯一索引防重复，消费侧用processed_messages表保幂等

限流器的令牌怎么算？令牌桶的核心思想是什么？

令牌桶就像水龙头往桶里匀速滴水，桶有容量上限。请求来时必须拿令牌，拿到就放行，拿不到就拒绝或等待。核心是允许突发流量——比如桶里存了100个令牌，就能扛住瞬间100QPS，之后回落到匀速填充速率。

回答要点
  1. 说清令牌生成速率（r/s）和桶容量（burst）两个参数
  2. 强调‘允许突发’这一关键优势（对比漏桶的刚性限制）
  3. 指出令牌获取是原子操作，需线程安全

LRU 缓存淘汰策略有哪些主要缺点？

LRU主要有三个问题：第一，容易被顺序扫描打穿，比如日志读取这种一次性的大量访问，会把真正高频的热点数据挤出；第二，它只看最近访问时间，无法识别长期稳定高频访问的‘常青树’热点；第三，标准实现依赖双向链表+哈希表，每次命中都要更新链表位置，在高并发下锁竞争严重。

回答要点
  1. 指出顺序扫描导致缓存击穿
  2. 指出LRU无法识别长期稳定热点
  3. 指出双向链表更新引发的并发锁瓶颈
完整解析（含追问与踩坑）→
消息队列如何保证消息不丢失？如何保证消息至少被消费一次？

发端要确认 broker 接收成功，比如 Kafka 要 ack=all；broker 端要持久化到磁盘+副本同步；消费端要手动提交 offset，且必须在业务逻辑执行成功后才提交，避免重复消费或丢消息。

回答要点
  1. 生产者端 ack 机制与重试策略
  2. Broker 端持久化与多副本同步
  3. 消费者端手动 commit offset 的时机控制

Agent自进化在沙箱环境做的目的是怎么考虑的？为什么一定得在沙箱环境做？

沙箱是唯一能同时满足三件事的环境：第一，完全隔离真实服务和用户数据，避免进化副作用外溢；第二，提供确定性时钟和可控故障注入，让每次进化可复现；第三，支持原子级快照回滚，确保无论进化多激进，都能秒级退回到上一稳定态——这三点缺一不可，线上环境根本做不到。

回答要点
  1. 指出隔离/可复现/可回滚三大不可替代价值
  2. 强调‘原子级快照回滚’是核心刚需
  3. 对比线上环境无法满足任一条件

Harness层现在是怎么构建的？

Harness是Go写的轻量框架：Input Parser把JSON test case转成统一ActionRequest，Executor按预设step顺序调用Agent SDK，Output Validator用预定义schema校验返回字段+正则匹配关键文本，最后Reporter把结果、耗时、trace ID写入ClickHouse；所有模块通过interface解耦，方便替换不同Agent后端。

  2. 明确各模块输入输出（如JSON→ActionRequest）
  3. 强调interface解耦设计目的

说一下模块和模块的依赖关系？这些模块是怎么做的？

分四层：最上是Adapter层，只做协议转换（HTTP/gRPC转内部Event）；中间是Orchestrator，负责状态机编排和retry策略；下面是ToolKit，每个工具封装成独立module，通过interface注册，比如SearchTool、DBTool；最底层是Storage，用Redis做session缓存，MySQL存长期日志；依赖全是单向的，上层调用下层，绝不反向。

回答要点
  1. 四层结构及每层职责（Adapter/Orchestrator/ToolKit/Storage）
  2. ToolKit通过interface注册
  3. 强调单向依赖原则

视频发布功能中的并发问题，能详细讲讲吗？

并发风险主要来自用户重复点击或网络重试。我的解法是：客户端带request_id，服务端在校验通过后，用author_id+request_id唯一索引插入publish_tasks表——重复请求直接查旧记录返回，不走插入。事务只包住元数据创建，转码、封面这些耗时操作全扔进MQ异步执行。这样既避免长事务锁表，又不用全局锁，不同用户的请求完全不互相阻塞。

回答要点
  1. 点明并发根源是客户端重复投递而非用户量大
  2. 唯一索引+查询兜底是核心幂等手段
  3. 明确事务仅保护元数据，异步解耦耗时操作
完整解析（含追问与踩坑）→
会用到哪些设计模式？

  3. 策略模式体现在可插拔的遍历/压缩/读取行为
  4. 观察者模式用于解耦文件变更与索引更新
  5. 仓储模式指FileRepository对MySQL的封装
