Cache Aside 模式存在哪些问题？如何解决延迟双删？

主要问题是并发写导致脏数据：先删缓存再更新 DB 时，若另一请求在删缓存后、DB 更新前读到旧值并回写缓存，就出错了。延迟双删是在更新 DB 后 sleep 一段时间再删一次缓存，靠时间差覆盖可能的脏写，但 sleep 时间难定，我们改用订阅 binlog 异步删缓存。

  2. 说明延迟双删的原理和固有缺陷（如 sleep 不确定性）
  3. 提出更优解如 binlog 监听或消息队列

为什么 Feed 流要先改库再发消息队列？

先写库再发 MQ 是为了保证源头数据真实可靠。数据库是唯一真相源，即使 MQ 丢消息或消费失败，也能通过扫表或日志补偿恢复；反过来，如果先发 MQ 再写库，MQ 成功但库写失败，下游就会拿到脏数据，且无法回滚。这本质是 outbox 模式的简化实现，用数据库事务兜底一致性。

回答要点
  1. 明确数据库作为 truth source 的定位
  2. 对比两种顺序的故障后果（尤其脏数据风险）
  3. 点出补偿机制是该方案的必要配套

如何实现浏览器的前进后退功能？

我用两个栈：后退栈存已访问页，前进栈存后退时弹出的页。每次跳转，把当前页压入后退栈，清空前进栈；点击后退，从后退栈弹出压入前进栈；前进则反向操作。关键要保证前进栈只在后退时更新，避免状态错乱。

回答要点
  1. 后退栈和前进栈严格隔离，互不交叉更新
  2. 新导航必清空前进栈
  3. 支持多次后退后仍能前进
  4. 时间复杂度 O(1) 每次操作

Web框架 2 题

请说明Gin框架拦截器（Middleware）的实现原理。

Gin用切片存储中间件函数，每个中间件接收context参数；执行时按注册顺序调用，每个中间件内必须显式调用c.Next()才能继续后续中间件；c.Next()本质是递归调用下一个函数，形成‘进入-业务-退出’的洋葱结构。

回答要点
  1. 中间件函数签名必须为func(*gin.Context)
  2. c.Next()是控制权移交的关键调用点
  3. 异常可通过c.Abort()中断后续中间件执行

Gin的路由是如何实现的？

Gin使用基于HTTP方法的多棵前缀树（Trie），每种Method（GET/POST等）维护独立的root；路由注册时按路径分段插入节点；匹配时逐字符比对路径，支持:param和*catchall通配，O(1)复杂度查找。

回答要点
  1. 按HTTP Method分树降低冲突
  2. 路径分段（/user/:id → ['user', ':id']）构建Trie
  3. 通配符节点（:param匹配单段，*catchall匹配多段）处理逻辑

我们在订单创建时要扣库存、发优惠券、写订单表，跨三个微服务。没用 Seata 全局事务，因为性能压不住。最后用 TCC 模式：Try 阶段预占资源（冻结库存、生成待发券），Confirm 真实扣减，Cancel 回滚预占。关键点是 Confirm/Cancel 必须幂等，且要有超时自动补偿。

  2. 说明选型理由（如放弃XA/Seata，选择TCC/Saga）
  3. 强调幂等、补偿、超时等生产级细节

Workers KV 的一致性模型是什么？会不会出现边界性的 bad case？

Workers KV 是最终一致性模型，写入后可能需要几秒才能在所有边缘节点同步。典型 bad case 是：用户 A 在东京节点写入后立刻从纽约节点读，可能读到旧值；或者并发写入时出现短暂状态不一致。

回答要点
  1. 明确说出‘最终一致性’而非强/线性一致性
  2. 指出同步延迟导致的跨区域读取不一致
  3. 举出至少一个具体 bad case 场景

数据库操作 2 题

AI Coding 场景题：给了一段几行代码，内容是对所有 user_ids 执行一条 update。这个实现的风险点是什么？

三大风险：一是单条SQL拼接百万ID导致SQL超长报错；二是事务锁住全表或大量行，阻塞其他业务；三是OOM——JDBC加载全部结果到内存。正确做法是分批（如1000条/批）、加事务粒度控制、用PreparedStatement防注入。

回答要点
  1. 指出SQL长度超限（max_allowed_packet）
  2. 说明行锁升级为表锁或长事务阻塞风险
  3. 识别内存溢出隐患（ResultSet全量加载）
完整解析（含追问与踩坑）→
AI Coding 场景题：怎么把它做成一个更工程化的版本？

四步改造：1. 分片：按user_id哈希分100批；2. 异步：用消息队列投递批次任务；3. 监控：记录每批成功数/失败ID/耗时；4. 回滚：保留原始ID快照，失败时可重试或人工介入。核心是‘可观察、可中断、可补偿’。

回答要点
  1. 提出分片+异步+监控+回滚四要素
  2. 说明分片依据（如哈希而非顺序，防热点）

什么是策略模式？

策略模式定义了一组算法，把每个算法封装成类，让它们可以互相替换；核心是用接口统一行为，运行时动态切换具体实现，比如支付方式选微信还是支付宝，都实现 PayStrategy 接口。

  3. 举出符合定义的业务例子（如支付、排序）
