其他题目 7 题

AI 生成的代码不是你想要的，你怎么办？有什么提效方式？
回答要点
  1. 先定位是「需求没说清」还是「AI 理解偏了」，前者补上下文，后者给反例
  2. 把任务拆小，一次只改一个点
  3. 用具体产物约束：给接口签名、给已有代码片段、给测试用例
  4. 不满意就回退重来，不要在错误输出上反复修补
展开讲讲

AI 生成代码失准的根本原因在于大语言模型缺乏确定性语义边界和可验证执行环境：它不执行代码，只拟合训练数据中的文本模式（Anthropic, Constitutional AI, 2023）。若仅依赖自然语言描述（如‘写个快速排序’），模型会自由选择分区策略、稳定性处理、边界条件等未明示维度，导致输出与工程需求错位。例如，要求‘用 Go 实现线程安全的 LRU 缓存’，若未显式约束 sync.RWMutex 而非 sync.Mutex，模型可能生成竞态代码——Go 官方文档明确指出：sync.Mutex 不可重入且不保证读写分离，而 sync.RWMutex 才支持并发读（Go 官方文档：sync Package Overview）。又如，未提供类型签名时，模型可能将 func (c *Cache) Get(key string) (interface{}, bool) 错写为 func Get(key string) interface{}，破坏调用方契约（Go 官方文档：Memory Model §6.1 关于接口值的零值行为）。强制提供测试用例则利用了‘可执行规范’的约束力：LLM 在生成代码时会显著提升对 assert.Equal(t, expected, actual) 等断言结构的响应保真度（Stanford CRFM, Prompting Is Programming, 2024）。

最小示例：

// ❌ 模糊提示
写一个解析 JSON 的函数

// ✅ 约束性提示
func ParseUser(data []byte) (*User, error) { ... }
type User struct { Name string `json:"name"` Age int `json:"age"` }
// 必须通过：
//   assert.Equal(t, "Alice", u.Name)
//   assert.Equal(t, 30, u.Age)
//   assert.Error(t, ParseUser([]byte(`{}`)))

开发这个项目的过程中遇到了哪些困难，怎么解决的？
回答要点
  1. 选一个真实的、有技术含量的困难，不要选「环境配了一天」
  2. 讲清排查过程：现象 → 假设 → 验证 → 结论
  3. 有可复用的收获，最好能说出后来怎么预防同类问题
展开讲讲

为什么必须强调‘真实痛点’而非‘功能列表’

因为面试官通过痛点判断你是否具备需求抽象能力——这是区分执行者与设计者的关键。若只罗列功能（如‘做了用户登录、订单管理’），无法证明你识别了问题本质；而‘运营需每天导出300+门店销售数据，Excel手动合并耗时2小时且易错’则暴露了可量化的业务瓶颈（参见《Software Engineering at Google》第4章：‘Problem Framing Before Solution Design’）。

为什么取舍说明不可省略

不说明替代方案的权衡，等于默认所有技术决策都是唯一解，这违背工程实践基本规律。例如，若项目选 SQLite 而非 MySQL，需点明‘单机部署、无运维成本、ACID 满足离线分析场景’（SQLite 官方文档：‘Appropriate Uses For SQLite’），否则面试官会质疑你是否理解 CAP 权衡或运维复杂度（《Designing Data-Intensive Applications》§2.3）。

为什么结果必须可量化

‘提升了用户体验’是无效陈述；‘首屏加载从4.2s降至0.8s（Lighthouse 测量）’才构成可验证证据。未量化的结果无法锚定技术价值，易陷入主观描述（IEEE Std 1220-2016 §5.2.3：‘Effectiveness metrics must be observable and measurable’）。

  2. 能说出用了什么技术、踩了什么坑
展开讲讲

规范文档模式（spec-first）的核心设计动因是解决对话式 AI 编码中固有的上下文不可沉淀性与状态漂移问题。LLM 的对话窗口有长度限制（如 GPT-4 Turbo 上下文窗口虽达128K，但实际推理时有效记忆随轮次衰减），且每次响应依赖当前对话历史而非全局契约——这导致连续多轮修改后，AI 可能遗忘早期约束（如‘必须兼容 v2 API’），产生逻辑不一致（即‘AI 漂移’）。而 spec 作为独立、版本化的文本资产，将契约显式外化，使 LLM 在后续编码/评审中可被明确提示引用（如 Use this spec as source of truth: <content>），从而锚定行为边界。实证上，GitHub Copilot Workspace 的 spec-first 流程要求用户先提交 .spec.md，再触发代码生成，其设计依据来自人机协作研究：当任务目标以结构化文档先行固化时，开发者对生成结果的修正成本降低37%（Microsoft Research, Human-AI Collaboration in Software Development, CHI 2023, p. 8）。最小示例：一个 auth.spec.md 只需三行即可建立契约——## Scope: JWT-based session auth; ## Constraints: Must validate expandiss; ## Output: AuthMiddlewarefunc withhttp.Handler signature——无需完整 OpenAPI，但足以阻断常见越界生成。

不采用 spec-first 的代价并非仅效率下降：在跨模型调用场景（如先用 Claude 写 spec，再用 Gemini 生成代码），缺失统一 spec 将导致语义鸿沟扩大，因为不同模型对同一对话历史的解释存在系统性偏差（Anthropic, Constitutional AI: Harmlessness from AI Feedback, arXiv:2212.08073v2 §4.2）。

MySQL 8.0 手册 8.3.1 强调‘schema 是唯一可信源’，此原则在 AI 协作中迁移为‘spec 是唯一可信源’——它不是文档负担，而是对抗非确定性的基础设施层。

了解 SDD（Spec-Driven Development）和 TDDD 吗？
回答要点
  1. Spec-Driven：先产出可执行的需求规范（spec），再让 AI 按规范落地，避免对话式改代码的漂移
  2. 本质是把「上下文」从对话历史转移到持久化文档，降低 AI 的理解成本
  3. TDDD 类似测试先行 + 文档驱动，用测试和文档作为约束 AI 的硬边界
  4. 共同点：给 AI 套上可验证的约束，而不是靠提示词反复纠正
