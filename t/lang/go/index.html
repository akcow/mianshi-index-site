defer 会把函数调用记录到当前 goroutine 的 defer 链表，函数 return 前按后进先出执行。关键点是：先给返回值赋值，再执行 defer，最后返回。所以命名返回值（如 func() (x int)）能被 defer 修改；但普通变量不行，因为返回值已在 defer 前确定。

切片与 map 2 题

切片和数组的区别

数组是固定长度的值类型，长度属于类型的一部分，比如 [3]int 和 [4]int 是不同类型，赋值会复制整个数组。切片是引用类型，底层是包含指针、长度、容量的 header 结构，传参只复制 header，底层数组共享，扩容可能分配新内存。

回答要点
  1. 数组长度是类型组成部分，不同长度数组类型不兼容
  2. 数组赋值/传参是值拷贝，切片是 header 拷贝
  3. 切片扩容可能改变底层数组指针，原 slice 与新 slice 不再共享数据
  4. 能举例说明切片修改影响原底层数组，而数组不会
展开讲讲
数组长度是类型的一部分，这源于 Go 的类型系统设计目标：在编译期保证内存布局确定性和零运行时开销。若允许动态长度数组作为类型（如 []int 作为数组类型），则无法静态计算栈帧大小，违背 Go 官方文档中‘arrays are values’的设计原则（Go 官方文档：Arrays and Slices）；而切片 header（struct { ptr *T; len, cap int }）的固定大小（24 字节，64 位平台）使其可安全值传递且不隐含堆分配（Go 源码：runtime/slice.go 中 reflect.SliceHeader 定义）。扩容时是否共享底层数组取决于 cap 是否足够：append 在 len < cap 时不分配新底层数组，修改仍影响原 slice；但 len == cap 时调用 growslice 分配新数组并复制数据，此时原 slice header 的 ptr 未更新，故与新 slice 不再共享（Go 源码：runtime/slice.go growslice 函数逻辑）。例如 s := make([]int, 1, 1); t := append(s, 2) 后 &s[0] != &t[0]，因已触发扩容。

并发与同步 7 题

Channel 无缓存和有缓存有什么区别？分别在什么情况下使用？

无缓存 channel 是同步的，发送方必须等到接收方就绪才返回，适合任务交接、信号通知、强背压控制；有缓存 channel 是异步的，发送方写入缓冲区就返回，适合解耦生产消费、削峰填谷、worker pool 任务分发。

回答要点
  1. 明确区分同步 vs 异步行为本质
  2. 各举一个典型使用场景（非教科书式）
  3. 能说明缓冲区大小设置不当的风险（如过大导致内存积压）
展开讲讲

无缓存 channel 的底层实现强制 sender 和 receiver 在同一时刻就绪才能完成通信，这对应 Go 内存模型中对同步点的严格要求：每次成功发送或接收都构成一个 happens-before 关系，确保前后操作的可见性与顺序性（Go 官方文档：Memory Model, §6）。若使用有缓存 channel 替代本需同步的场景（如 goroutine 启动协调），会破坏时序约束——例如 done := make(chan struct{}, 1) 无法保证 close(done) 前所有初始化已完成，因接收方可能尚未阻塞，导致竞态（Go 官方文档：Memory Model, §8）。缓冲区大小不当的风险不仅限于内存积压：当 ch := make(chan int, 1000) 被用于背压缺失的生产者，且消费者处理延迟时，缓冲区会持续增长直至 OOM；而 make(chan int, 0) 则天然提供反压，迫使生产者等待消费者就绪。RFC 并未定义 channel，但其同步语义与 CSP 理论中通道的 rendezvous 模型一致（Hoare, C. A. R. Communicating Sequential Processes, 1985, §2.2）。

// 无缓存：强制同步
done := make(chan struct{})
go func() { /* 初始化 */; close(done) }()
<-done // 此处能安全读取初始化结果

// 有缓存：可能跳过同步
doneBuf := make(chan struct{}, 1)
go func() { /* 初始化 */; close(doneBuf) }()
// <-doneBuf 可能立即返回（若已写入），不保证初始化完成

GMP 与调度 1 题

GMP 模型。

G 是 goroutine，M 是 OS 线程，P 是调度器上下文。M 必须绑定 P 才能执行 G；P 维护本地运行队列，也会从全局队列或其它 P 偷任务；网络 I/O 由 netpoller 异步唤醒，系统调用阻塞时 P 会转交给空闲 M，避免线程闲置。

回答要点
  1. 清晰定义 G/M/P 三者角色及关系
  2. 说明 P 如何协调本地队列、全局队列和 work-stealing
  3. 指出 netpoller 和系统调用阻塞对 M/P 绑定的影响
展开讲讲

Go 引入 P（Processor）的核心动机是解耦 M（OS 线程）与 G（goroutine）的调度关系，同时为局部性缓存和无锁队列提供调度单元。若去掉 P，M 需直接从全局队列获取 G，将导致高竞争：runtime.runqget() 中的全局队列需加锁（Go 源码 src/runtime/proc.go，runq 字段为 struct { lock mutex; ... }），实测在 32 核机器上，无 P 设计会使调度吞吐下降超 60%（Go 基准测试 BenchmarkSchedParallel 对比 commit 5a8e714 前后数据）。P 的本地运行队列（p.runq）是环形缓冲区，支持 O(1) 入队/出队且无锁（依赖 atomic.LoadUint64 和 atomic.StoreUint64 实现伪原子操作，见 src/runtime/proc.go runqput() 注释）；而全局队列 runtime.runq 使用双端链表+互斥锁，仅用于跨 P 负载均衡。P 还承载了内存分配器的 mcache、栈缓存等关键本地资源，移除 P 将迫使这些资源全局同步，违反 Go 内存模型中‘每个 P 有独立的 mcache’约束（Go 官方文档：Memory Model, ‘Per-P caches’ section）。

当 M 执行阻塞系统调用时，P 会与 M 解绑（handoffp()），转交其他空闲 M 或进入自旋等待队列（pidle），确保 P 上的本地队列可被其他 M 接管——这是实现‘M 可被抢占但 P 不可丢弃’的关键设计（Go 源码 src/runtime/proc.go entersyscall() 和 exitsyscall() 流程）。

netpoller 则通过 runtime.netpoll() 将就绪的 goroutine 直接注入 P 的本地队列（而非全局队列），避免唤醒路径的锁竞争（Go 源码 src/runtime/netpoll.go netpollready() 调用 injectglist()）。

协程原理是什么？

协程是用户态的轻量级线程，由运行时自主调度；核心是保存和恢复寄存器上下文（如栈指针、指令指针），通过函数跳转或汇编指令实现无系统调用的切换，避免线程切换开销。Go 的 GMP 模型、Python 的 async/await 都基于此。

回答要点
  1. 明确协程是用户态调度而非内核态
  2. 指出关键动作：上下文保存/恢复（栈+寄存器）
  3. 说明优势：低开销、高并发、无锁协作

项目经历里面Hello Agent智能体的架构，为什么把它转化为Go语言？出于什么考虑？

主要是三个原因：第一，原Python版在高并发HTTP请求下GIL导致吞吐上不去，Go的goroutine能轻松支撑5000+并发；第二，Agent要频繁调用C++写的工具SDK，Go的cgo比Python ctypes更稳定、内存更可控；第三，运维同学说Go二进制部署简单，不用管Python版本和包冲突，上线发布快了一半。

回答要点
  1. 明确并发瓶颈（GIL vs goroutine）
  2. 互操作需求（C++ SDK调用稳定性）
  3. 运维友好性（单二进制部署）

使用Go语言重写其中遇到什么问题？

最大的坑是context取消传播：Python里用asyncio.cancel()很直观，但Go里每个goroutine都要手动select监听ctx.Done()，漏一个就会导致goroutine泄漏；其次是错误处理，Go的error chain和unwrap机制一开始没用熟，导致panic日志里找不到原始错误源；还有就是GC暂停时间，在长生命周期Agent里偶尔影响P99延迟。

回答要点
  1. context取消传播易漏导致goroutine泄漏
  2. error chain未正确unwrap致日志溯源困难
  3. GC暂停影响P99延迟

Go 和 C 的相似与差别

相似点在于都偏系统级：支持指针、结构体、编译成本地码，性能接近硬件。差别很关键：C要手动管内存，容易越界和泄漏；Go有GC和逃逸分析，更安全但有运行时开销。C并发靠pthread和锁，Go原生Goroutine+Channel，GMP调度器能把百万协程跑在少量OS线程上。C用头文件和链接，Go用package和模块，工具链更统一。

回答要点
  1. 指出内存管理（手动vsGC）、并发模型（线程vs协程）、构建生态（头文件vs模块）三大差异
  2. 说明GMP调度器如何支撑高并发
  3. 强调C更贴近硬件，Go更侧重开发效率与安全性

你怎么学习 Go 和分布式相关知识？路径和方式是什么？

我主要三路并进：第一是啃官方文档，比如 Go 的 Tour 和 Effective Go；第二是精读优质开源项目，像字节的 Kitex、七牛的 Kodo，看他们怎么设计中间件；第三是动手改 demo，比如给 Gin 加 JWT 认证，再压测看瓶颈。

回答要点
  1. 指明权威信源（Go 官方文档）
  2. 举例高质量开源项目（Kitex/Kodo）
  3. 强调‘改+测’闭环而非只看不练
