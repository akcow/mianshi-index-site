TCP是怎么保证可靠传输的？

知识题 被 5 场面试问到 专业知识 计算机网络 / TCP
面试官想考什么
考察对TCP可靠性设计的整体性认知，而非零散罗列机制
跳到： 回答重点 扩展知识 追问 常见踩坑 来源
答案

可以直接说

TCP靠八种机制协同保障可靠：序列号确保字节流有序；ACK确认应答反馈接收状态；超时重传应对丢包；快速重传加速丢包恢复；滑动窗口提升吞吐；流量控制防接收方溢出；拥塞控制适配网络状况；校验和检测传输错误。其中前四条解决‘传得准’，后四条解决‘传得稳’和‘传得快’。

回答重点

答到这几点就算过关，顺序不重要。

  1. 覆盖序列号、ACK、重传（含超时+快速）、滑动窗口
  2. 区分流量控制（接收方能力）和拥塞控制（网络状态）
  3. 强调校验和防错
  4. 指出机制间的协作关系

扩展知识

TCP 选择累积 ACK 而非 NAK，根本原因在于网络丢包率低时 ACK 的带宽效率与实现鲁棒性更优：单个 ACK 可确认多个连续字节（如 ACK=1001 表示已成功接收序号 <1001 的所有数据），而 NAK 需为每个丢失段单独反馈，易引发反馈爆炸；RFC 9293 §3.5 明确要求 ’the receiver sends acknowledgments for the highest in-order sequence number received’，这是协议设计对典型互联网丢包模式（偶发、局部）的适配。若强制用 NAK，在高丢包场景下可能触发大量重复 NAK 冲突，且无法天然支持选择性确认（SACK）的扩展——SACK 正是作为 ACK 的增强而非替代被引入（RFC 2018）。TIME_WAIT 状态必须持续 2×MSL（Maximum Segment Lifetime），其核心作用是：(1) 确保网络中残留的旧连接报文（如延迟重传的 FIN 或数据）不会干扰新连接（RFC 9293 §3.5）；(2) 保证被动关闭方能收到最后 ACK 的确认，否则可能因 FIN 丢失导致对方卡在 LAST_ACK。Linux 默认 MSL=30s，故 TIME_WAIT 持续 60s（net.ipv4.tcp_fin_timeout 不影响此值，见 Linux kernel source net/ipv4/tcp.c 中 TCP_TIMEWAIT_LEN 定义）。

校验和仅覆盖 TCP 头部+数据+伪头部，不校验 IP 层以下，因此无法检测链路层 CRC 错误后的静默损坏——这正是应用层需额外校验（如 TLS record MAC）的原因（RFC 9293 §4.1）。

滑动窗口与拥塞控制解耦：接收窗口（rwnd）由接收方通告，纯流量控制；拥塞窗口（cwnd）由发送方根据网络反馈动态调整，二者共同决定实际发送上限（min(cwnd, rwnd)），此分离设计使 TCP 能同时响应接收方内存限制与网络瓶颈（RFC 5681 §3）。

超时重传（RTO）基于 RTT 采样动态估算，若固定超时（如统一设 1s）将导致高延迟链路过度重传或低延迟链路响应迟缓（RFC 6298 §2.2）。

快速重传依赖重复 ACK（≥3 个相同 ACK）触发，避免等待 RTO 超时，但若接收方禁用延迟 ACK（TCP_QUICKACK），可能减少重复 ACK 数量，影响其触发时机（RFC 1122 §4.2.3.2）。

校验和算法使用 16 位反码和（one’s complement sum），可检测所有单比特错误及多数多比特错误，但无法保证 100% 检错（RFC 793 §3.1）。

拥塞控制算法（如 Cubic、BBR）不改变 TCP 基础可靠机制，仅替换 cwnd 增长逻辑，体现 RFC 5681 允许‘congestion control algorithm’可插拔的设计哲学。

面试官会怎么追问

  • 为什么TCP不用负确认NAK而用ACK？
  • TIME_WAIT状态存在的必要性？

为什么TCP不用负确认NAK而用ACK？

应指向网络模型假设与协议开销权衡：TCP 设计基于‘丢包稀疏’假设（RFC 9293 §3.5），ACK 的累积特性天然压缩反馈信息量；NAK 在低丢包率下产生大量空反馈，且无法像 ACK 那样承载接收窗口更新。可对比 SCTP 的显式 NAK 支持（RFC 4960 §6.2），说明其适用场景（高丢包实时流）不同。

TIME_WAIT状态存在的必要性？

需分两点回应：(1) 防止旧连接报文混淆新连接——引用 RFC 9293 §3.5 ‘to prevent delayed segments from one connection being accepted by a later connection’；(2) 确保四次挥手终结可靠性——若最后 ACK 丢失，主动关闭方需重发 FIN，TIME_WAIT 使其能响应重传的 FIN（RFC 793 §3.5）。可补充：Linux 通过 net.ipv4.tcp_tw_reuse（仅客户端）和 tcp_tw_recycle（已移除）尝试优化，但违背 RFC 严格性，易致 NAT 下连接失败（Linux kernel commit 8aedd0f）。

推测：如果 ACK 丢失了怎么办？

答方向：发送方依赖超时重传（RTO）兜底，但接收方会持续发送重复 ACK（如 ACK=1001）提示缺失，触发快速重传；强调 ACK 本身不可靠，TCP 可靠性不依赖 ACK 可靠送达（RFC 9293 §3.5）。

推测：滑动窗口大小由谁决定？如何动态调整？

答方向：接收窗口（rwnd）由接收方 TCP 栈根据自身缓冲区剩余空间通告（recv() 后调用 setsockopt(SO_RCVBUF) 影响）；发送方取 min(cwnd, rwnd) 为实际窗口，其中 cwnd 由拥塞控制算法（如 Reno/Cubic）依据丢包/延迟信号调整（RFC 5681 §3）。

推测：校验和能发现所有错误吗？

答方向：不能，16 位反码和存在碰撞概率（如两处错误相互抵消），RFC 793 §3.1 明确指出其检错能力有限；现代链路层（如以太网 CRC-32）和应用层（如 TLS MAC）提供更强保障。
