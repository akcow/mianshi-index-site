手写LRU缓存

手撕题 被 5 场面试问到 编码实现 手撕 / 数据结构
面试官想考什么
考察哈希表与双向链表的组合运用能力，以及边界处理的严谨性
跳到： 回答重点 扩展知识 追问 常见踩坑 来源
答案

可以直接说

用哈希表O(1)查节点，双向链表O(1)移位和删尾。头结点最新访问，尾结点最久未用。Get命中就移到头；Put时若存在则更新值并移到头，若不存在且超容，先删尾节点再插入新节点到头。关键细节：哨兵头尾节点避免空指针判断，删除节点要同时解哈希表映射。

回答重点

答到这几点就算过关，顺序不重要。

  1. 哈希表+双向链表结构选型合理
  2. Get/Put操作时间复杂度均为O(1)
  3. 正确处理容量超限时的尾部淘汰
  4. 哨兵节点或空指针防护到位

扩展知识

LRU缓存采用哈希表+双向链表的核心设计，本质是为同时满足O(1)随机访问与O(1)有序淘汰两个正交需求：哈希表提供键到节点的直接映射（避免遍历），而双向链表支持在任意位置O(1)删除和移动节点（单向链表无法在已知节点引用时O(1)删除前驱）。若仅用哈希表+单向链表，淘汰尾部节点时需从头遍历至倒数第二节点，退化为O(n)；若仅用有序数组，则Get/Put均需O(n)移动元素。哨兵节点（dummy head/tail）消除空指针分支判断，使插入/删除逻辑统一，符合Go标准库container/list的设计实践（Go 官方文档：container/list）；其存在使Remove(e *Element)无需检查e.prev/e.next是否为nil，显著降低边界错误概率。过期时间与LRU淘汰属不同维度——LRU管理访问序，TTL管理生存期，二者不可合并为单一排序依据（如按访问时间排序则无法及时清理过期项），必须正交处理（Redis 7.0 设计文档：Eviction and Expiration Separation）。

// 最小示例：哨兵初始化
type LRUCache struct {
    head, tail *Node
}
func Constructor() LRUCache {
    h, t := &Node{}, &Node{}
    h.next = t
    t.prev = h
    return LRUCache{head: h, tail: t}
}

面试官会怎么追问

  • 如何支持带过期时间的LRU？
  • 并发场景下怎么线程安全地实现LRU？

如何支持带过期时间的LRU？

应明确区分‘逻辑过期’与‘物理删除’：在节点中增加expireAt time.Time字段，Get时惰性检查并驱逐（避免定时器开销）；Put时若新值带TTL则设置该字段。需注意时钟漂移问题，建议使用单调时钟（Go time.Now()返回wall clock，但time.Since()基于单调时钟，见Go 官方文档：Time Package）。

并发场景下怎么线程安全地实现LRU？

优先采用读写锁（sync.RWMutex）保护整个结构，而非细粒度锁——因LRU操作常需同时修改哈希表和链表，锁分离易致状态不一致（如哈希表更新而链表未同步）。可参考Go sync.Map不适用于此场景的原因：它不支持按访问序淘汰（Go 官方文档：sync.Map FAQ）。

（推测）能否用跳表替代双向链表？

不能。跳表虽支持O(log n)有序操作，但LRU要求严格O(1)的最近访问节点提升（move-to-head），而跳表无O(1)节点提升能力；且跳表空间开销更大，违背LRU轻量定位目标（Redis 7.0 手册：Why not skip list for LRU?）。

（推测）内存占用能否进一步优化？

可将双向链表嵌入value结构体（intrusive list），避免额外节点分配；但需权衡GC压力——Go中unsafe.Pointer手动管理链表指针需禁用GC扫描，风险高（Go 官方文档：unsafe.Pointer Rules）

常见踩坑

  • 用数组或单链表导致O(n)操作
  • 忘记更新哈希表映射
  • Put时未区分key存在/不存在两种分支
