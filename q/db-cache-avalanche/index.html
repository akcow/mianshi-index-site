缓存穿透、缓存击穿、缓存雪崩分别是什么，如何应对？

知识题 被 2 场面试问到 专业知识 数据库 / Redis
面试官想考什么
三个词经常被混着背，面试官想看你有没有真的区分开「查不存在的 key」「热点 key 过期」「大批 key 同时过期」
跳到： 回答重点 扩展知识 追问 常见踩坑 来源
答案

回答重点

答到这几点就算过关，顺序不重要。

  1. 穿透：查不存在的数据，请求绕过缓存直打 DB。解法：布隆过滤器、空值缓存
  2. 击穿：单个热点 key 过期瞬间大量请求打到 DB。解法：互斥锁重建、逻辑过期不失效
  3. 雪崩：大批 key 同时过期或缓存服务整体挂掉。解法：过期时间加随机、多级缓存、熔断降级
  4. 能说出三者的触发条件差异，而不是只背解法

标准答案

穿透是查不存在的 key，击穿是单个热点 key 失效，雪崩是大面积 key 同时失效或缓存宕机。

扩展知识

缓存穿透中使用布隆过滤器，本质是用空间换确定性：它通过 k 个哈希函数将 key 映射到位数组，查询时只要任一位置为 0 就可确定该 key 不存在（无假阴性），但所有位置为 1 时仅表示‘可能已存在’（有假阳性）——这是概率型数据结构的固有设计，无法消除误判，只能控制误判率。误判率公式为 $ (1 - e^{-kn/m})^k $，其中 m 是位数组长度，n 是插入元素数，k 是哈希函数数；实践中通过调整 m/n 比值（如 10–20）和 k（通常 3–7）可将误判率压至 1% 以下（《Network Applications of Bloom Filters: A Survey》, IEEE Communications Surveys & Tutorials, 2003, §III-A）。若用空值缓存替代布隆过滤器，则需承担存储膨胀与一致性维护成本：Redis 中大量空值会显著增加内存占用，且需设置较短 TTL（如 2–5 分钟），否则可能长期阻塞真实数据写入（Redis 官方文档：SET key value [EX seconds] 行为说明）。逻辑过期方案中，value 内嵌 expireTime 字段而非依赖 Redis TTL，是因为 Redis 的 EXPIRE 命令在 key 被驱逐或主从切换时可能丢失过期语义，而应用层控制能确保‘逻辑过期’状态始终与业务数据共存于同一序列化体中（Redis Design Docs: ‘Expiration’ section, redis.io）。

雪崩防护中‘过期时间加随机’必须作用于初始设值阶段，而非每次读取时重算；若在 SET key value EX 3600 中动态加随机，会导致同一 key 多次写入不同 TTL，破坏预期内存释放节奏（Redis 8.0 手册：EX 参数语义明确为‘设置绝对过期时长’）。

多级缓存（如本地 Caffeine + Redis）并非简单叠加，而是利用 L1 缓存的纳秒级响应规避网络往返，但需解决双写不一致：Caffeine 的 refreshAfterWrite 仅触发异步加载，不阻塞读请求，因此旧值可能被持续返回直至刷新完成（Caffeine GitHub Wiki: Refresh）。

熔断降级在缓存层失效时启用，其阈值（如 50% 请求超时）需基于服务 SLO 设定，而非固定值；Hystrix 等库的默认半开窗口可能引发雪崩式重试，应改用滑动窗口计数（Netflix Hystrix Documentation: ‘Circuit Breaker’）。

面试官会怎么追问

  • 布隆过滤器有误判怎么办
  • 逻辑过期怎么保证读到的是新数据

布隆过滤器有误判怎么办

答方向：承认误判不可消除，转而说明如何量化与约束影响——给出误判率计算公式及典型参数配置（如 m/n=15, k=4 → ~0.9%），并强调业务容忍度（如搜索场景允许少量 404，但支付场景需结合空值缓存兜底）。引用《Bloom Filters — Lessons Learned》（ACM Queue, 2014）指出：生产系统应监控误判率实际值，当观测值持续高于理论值时，表明哈希分布不均或位图复用冲突，需扩容或更换哈希算法。

逻辑过期怎么保证读到的是新数据

答方向：聚焦‘读写分离’下的状态同步机制——读请求先校验内嵌 expireTime，若逻辑过期则尝试获取互斥锁（如 Redis SET key val NX EX 30），成功者异步重建缓存并更新 expireTime；未获锁者继续返回旧值，但需设置最大陈旧时长（如 2 秒）后强制重试。关键点在于：逻辑过期不等于数据过时，expireTime 更新与新 value 写入必须原子提交（参考 Redis 官方文档：EVAL 脚本保证 Lua 原子性）。

（推测）如果布隆过滤器容量不足，频繁扩容是否影响性能？

答方向：指出布隆过滤器不可原地扩容，需重建——应预估峰值 key 数并预留 30% 空间；若动态扩容，可用分片布隆过滤器（如每 100 万 key 一个实例）避免全局重建（Google Guava BloomFilter 实现注释：‘Not thread-safe for resizing’）。

（推测）逻辑过期方案下，后台重建失败如何处理？

答方向：说明需引入失败重试队列与告警，且 expireTime 应设为‘上次成功更新时间 + 基础 TTL’，而非固定偏移，防止时钟漂移导致永久逻辑过期（RFC 868 §3.1 时间同步要求）。

（推测）多级缓存中本地缓存与 Redis 数据不一致，如何快速修复？

答方向：采用‘主动失效’而非被动更新——DB 写入后发 MQ 消息清除两级缓存，本地缓存用 Caffeine 的 invalidateAll() 配合分布式锁防重复清除（Caffeine 3.0+ 支持 CacheWriter 接口）；注意消息延迟需小于本地缓存 TTL（Kafka 官方文档：acks=all 保障消息不丢）
