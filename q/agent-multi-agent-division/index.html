Multi-Agent 系统中，不同 Agent 之间应该怎么划分职责，任务怎么拆分？

场景题 被 2 场面试问到 方案设计 大模型应用 / 多Agent
面试官想考什么
考你是不是真的拆过，而不是把单 Agent 硬塞成多个
跳到： 回答重点 扩展知识 追问 常见踩坑 来源
答案

回答重点

答到这几点就算过关，顺序不重要。

  1. 按能力边界拆（检索、编码、审核）而非按步骤流水拆
  2. 拆分的判据：子任务是否可独立验证、是否需要不同工具集或不同模型
  3. 要有明确的输入输出契约，否则接口处会大量信息丢失
  4. 别为了多 Agent 而多 Agent，单 Agent 能解决就别拆

扩展知识

按能力边界而非流程步骤划分 Agent 职责，本质是遵循关注点分离原则在分布式智能体系统中的落地：流程式拆分（如‘先检索→再写代码→最后测试’）会将领域知识与执行逻辑耦合，导致单个 Agent 承担跨模态推理压力，违背 LLM 的 token-level 预测本质——模型在长上下文下对中间步骤的保真度呈指数衰减（Anthropic, Constitutional AI: Inference-Time Intervention, 2023, §4.2）。而能力边界拆分（如 RetrieverAgent 仅调用向量库 API、ValidatorAgent 仅执行 pytest 命令）使每个 Agent 的输入输出可被形式化约束，例如用 JSON Schema 定义契约：{"input": {"type": "object", "properties": {"query": {"type": "string"}}}, "output": {"type": "array", "items": {"type": "object", "properties": {"doc_id": {"type": "string"}}}}}。若不强制契约，Agent 间易出现隐式依赖（如 CoderAgent 默认 RetrieverAgent 返回 Markdown 格式），违反 RFC 9110 §3.1 ‘HTTP 消息应自描述’ 的设计哲学，导致调试时无法定位信息丢失发生在序列化、提示词解析还是工具调用环节。

面试官会怎么追问

  • 子任务失败了怎么向上汇报
  • 怎么避免职责重叠

子任务失败了怎么向上汇报

应答方向：强调结构化错误传播机制——失败 Agent 必须返回带 error_code（如 RETRIEVAL_TIMEOUT=408）、retriable: bool 和 suggestion 字段的标准化响应体，而非原始异常栈；引用 OpenAI Function Calling 规范要求 error payload 必须可被 schema 验证（OpenAI API Docs: Function calling, 2023-11）。

怎么避免职责重叠

应答方向：用‘最小权限原则’定义每个 Agent 的工具集白名单（如 ValidatorAgent 工具集仅含 run_pytest, parse_coverage），并在启动时通过 tools_schema 与 LLM 的 system prompt 双重校验；参考 Linux capability model 设计思想（Linux man-pages 7.65: capabilities），避免赋予 Agent 超出其能力边界的工具访问权。

（推测）如何评估拆分是否合理

应答方向：提出可观测性指标——测量各 Agent 输入/输出 token 长度比值是否稳定在 0.8–1.2 区间（偏离说明契约模糊），并检查跨 Agent 调用中 tool_call_id 的链路追踪完整率（需 ≥99.5%，参照 OpenTelemetry Spec v1.22 §5.3）。

常见踩坑

  • 把多 Agent 当成必然更优
  • 没有定义交接契约
