TCP为什么要三次握手，而不是两次？

知识题 被 3 场面试问到 专业知识 计算机网络 / TCP
面试官想考什么
考察对连接建立可靠性与历史报文干扰问题的本质理解
跳到： 回答重点 扩展知识 追问 常见踩坑 来源
答案

可以直接说

两次握手无法防止旧SYN报文在网络中滞留后突然到达服务端，导致服务端误建连接并浪费资源；三次握手让客户端确认服务端收到了自己的SYN，也确认了服务端的SYN，双方都确保对方收发能力正常，且能同步初始序列号。

回答重点

答到这几点就算过关，顺序不重要。

  1. 解决‘已失效的连接请求’问题
  2. 双向确认收发能力
  3. 同步ISN（初始序列号）防数据混淆

扩展知识

三次握手的设计源于 TCP 需要双向确认初始序列号（ISN）并防止历史报文干扰。若仅两次握手（SYN → SYN+ACK），服务端无法验证客户端是否成功接收了 SYN+ACK，即无法确认客户端的接收能力；此时若客户端未收到 SYN+ACK 而重发 SYN，服务端可能误建多个连接（RFC 9293 §3.5 明确指出：‘The three-way handshake is required to synchronize sequence numbers and prevent old duplicate segments from causing confusion’）。更关键的是，两次握手无法解决「网络中滞留的旧 SYN 报文」问题：假设某客户端上次连接的 SYN 因网络延迟迟到，服务端若仅凭该 SYN 就建立连接（分配 TCB、进入 ESTABLISHED），将导致状态不一致和资源泄漏——而三次握手中，客户端必须用 ACK 携带对服务端 ISN 的确认，服务端可据此校验该 ACK 是否对应本次握手（而非旧连接），从而拒绝过期请求（TCP RFC 9293 §3.5, §4.2.2.13）。最小示例：Linux 内核中 net.ipv4.tcp_syncookies=1 启用 SYN Cookie 时，服务端在 SYN+ACK 中将时间戳、MSS 等编码进初始序列号低 24 位，避免维护半连接队列（Linux Kernel Documentation: networking/ip-sysctl.txt）。

四次握手虽能进一步增强可靠性，但会增加 RTT 延迟且无实质收益：第三次 ACK 已完成双向 ISN 同步与接收确认，第四次纯属冗余，违背 TCP 设计目标 ‘minimize latency while ensuring reliability’（RFC 9293 §3.5）。

SYN Flood 攻击利用半连接队列耗尽资源，其本质是服务端为每个 SYN 分配内存（如 struct request_sock），而客户端不完成第三次 ACK。Linux 通过 SYN Cookie（tcp_syncookies=1）绕过队列分配，在 SYN+ACK 序列号中编码必要信息，使服务端无需保存半连接状态（RFC 4987 §3.1）。

半连接队列满时，内核默认丢弃新 SYN（除非启用 SYN Cookie），并可能发送 RST 或静默丢包，具体行为由 net.ipv4.tcp_abort_on_overflow 和 tcp_syncookies 共同决定（Linux Kernel Documentation: networking/ip-sysctl.txt）。

面试官会怎么追问

  • 如果第三次ACK丢了，连接能建立成功吗？
  • TCP Fast Open如何绕过部分握手？

为什么是三次不是四次

应指向协议开销与收益权衡：三次已满足 ISN 双向同步和接收确认的最小必要条件，四次不提升正确性，却增加 1-RTT 延迟和状态管理成本；引用 RFC 9293 §3.5 强调 ’three-way handshake is the minimum required’。

SYN Flood 怎么防

需分层回答：应用层限速（如 Nginx limit_conn）、传输层 SYN Cookie（内核参数 tcp_syncookies=1，RFC 4987 §3.1）、防火墙连接跟踪（如 iptables --syn 匹配）；重点说明 SYN Cookie 如何用密码学方式将半连接状态编码进序列号，避免内存分配。

半连接队列满了会怎样

明确内核行为：默认丢弃新 SYN（tcp_syncookies=0 时），或启用 SYN Cookie 后正常响应；若 tcp_abort_on_overflow=1 且全连接队列也满，则对已完成三次握手的 SYN+ACK 后续 ACK 发送 RST（Linux Kernel Documentation: networking/ip-sysctl.txt）。

常见踩坑

  • 只答‘为了可靠’没讲清具体风险
  • 认为三次握手是为了分配资源
  • 混淆四次挥手的必要性

同一考点的其他问法

  • TCP 三次握手的过程是怎样的，为什么不能是两次？
